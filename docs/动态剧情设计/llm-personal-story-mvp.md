# LLM 玩家独立剧情 MVP 设计

> - 状态：已确认 MVP v0.1
> - 核心目标：用最小范围证明“同一剧情 Base 能为不同玩家生成因果连续、彼此隔离的个人故事”。
> - 第一版渠道：剧情信件、剧情选择、关联秘境、结局回信。
> - 第一版周期：一条剧情线包含四个节点，可在数次游戏行为中完成。

## 0. 已确认决策

1. 第一份共享剧情 Base 定名为《前尘回响》，内部 ID 为 `past_echoes`。
2. MVP 只接入秘境结算事件；普通云游事件放到下一迭代。
3. MVP 唯一呈现流程为“剧情信件 → 关联秘境 → 结局回信”。
4. 第一版不增加云游途中弹窗、宗门 NPC 对话或地图世界变化渠道。
5. 剧情信只有“立即介入”和“先行调查”两个正式选择；关闭信件就是尚未决定，不会创建秘境，也不是剧情分支。
6. 新故人只能以“对方自称，玩家未证实”的方式开场。已死亡人物只在新事件与其地点、物件、势力或未结线索确实相关时，作为历史后果被提及。
7. 增加只读的“前尘录”作为主线纪事入口，供玩家查看当前进度和复盘已归档章节；剧情选择和秘境入口仍只由原有信件流程承载。
8. 首章由符合条件的秘境结算触发；后续章节只在玩家完成上一章后进入一天冷却，冷却到期后由后台异步生成，不需要再打一场普通秘境。

## 1. MVP 要验证什么

第一版不追求无限开放剧情，也不立即实现完整 MMORPG 世界模拟，只验证以下三个核心假设：

1. 两个玩家使用同一剧情 Base 时，能根据各自经历生成不同的人物、起因、选择条件和后果。
2. 玩家在前一个节点做出的选择，会成为后续节点不可推翻的权威事实。
3. LLM 超时、输出错误或暂时不可用时，游戏仍能结算、继续挂机和恢复剧情任务。

如果这三项无法稳定成立，继续增加 NPC 对话、开放世界变化和更多模型只会放大问题。

## 2. 一句话产品形态

玩家完成一次符合条件的云游或秘境后，系统结合其个人记忆生成一封专属剧情信；玩家选择处理方式，故事随后进入一个关联秘境，结束后再收到根据真实结果生成的结局回信，并留下可供未来剧情引用的记忆。

完整体验：

```text
普通玩法产生权威事件
  → 后台提取玩家记忆
  → 选择一份共享剧情 Base
  → 生成个人剧情引子
  → 通过信件通知玩家
  → 玩家作出明确选择
  → 生成关联秘境并完成冲突
  → 根据真实战斗和选择生成结局回信
  → 保存人物关系、结局和未解决伏笔
```

## 3. 第一版范围

### 3.1 包含

- 一份人工编写并版本化的剧情 Base。
- 每个角色独立的剧情状态、记忆、NPC 和剧情线。
- 消费已有服务端权威事件，不让 LLM 直接读取数据库。
- 后台提取三至六条相关记忆。
- 四阶段个人剧情：异兆、抉择、冲突、余波。
- 信件中的两个剧情选择。
- 一个与剧情线绑定的单人秘境。
- 结局回信和一条未解决伏笔。
- 一份从权威剧情状态实时投影的个人主线卷宗。
- 严格结构化输出、事实校验、幂等和降级模板。
- 基础管理员查询能力，至少能按角色查看剧情状态和失败原因。

### 3.2 不包含

- 多玩家共同修改同一个剧情世界。
- 实时开放世界中的 LLM 自主 NPC。
- 自由文本输入和无限对话。
- 向量数据库。
- 完整分支树。
- 语音、图片和视频生成。
- LLM 决定战斗胜负、奖励数量、爆落、死亡和资源变化。
- LLM 自动创建新的剧情 Base 并直接上线。
- 一开始接入所有宗门、炼器、市场、突破和 PvP 事件。

## 4. MVP 剧情 Base

第一版只提供一份足够通用的 Base：《前尘回响》：

```json
{
  "id": "past_echoes",
  "version": 1,
  "theme": "过去的一次选择重新找上玩家",
  "entryConditions": [
    "玩家至少完成过一次秘境或云游",
    "存在一条可以引用的个人记忆",
    "玩家当前没有其他活跃 MVP 剧情线"
  ],
  "stages": [
    {
      "type": "omen",
      "channel": "mail",
      "purpose": "旧人物、旧物或旧地点产生异常联系"
    },
    {
      "type": "choice",
      "channel": "mail",
      "purpose": "玩家选择立即介入或先行调查"
    },
    {
      "type": "confrontation",
      "channel": "dungeon",
      "purpose": "通过探索、交涉或战斗处理核心冲突"
    },
    {
      "type": "aftermath",
      "channel": "mail",
      "purpose": "写回人物关系、结局和后续伏笔"
    }
  ],
  "forbiddenClaims": [
    "替玩家决定选择",
    "改变已确认战斗结果",
    "直接发放资源",
    "复活已确认死亡的实体",
    "引用其他玩家的私有事实"
  ]
}
```

Base 固定故事节奏，不固定具体 NPC、地点、动机和结局。

## 5. 玩家如何产生不同剧情

### 5.1 个性化输入

每次生成最多输入以下玩家私有信息：

- 角色名、境界、宗门和主要修行方向。
- 一份长期剧情摘要。
- 三至六条与当前触发事件相关的记忆。
- 当前剧情线阶段和玩家已经确认的选择。
- 最多三名相关私有 NPC 或势力状态。
- 当前地图和可用秘境范围。
- 一个用于可重现随机选择的角色剧情种子。

### 5.2 真正的剧情分化

以下差异才算独立剧情：

- 求助者与玩家存在不同的旧关系。
- 玩家因过去行为获得不同的进入条件或线索。
- 某个选择只对持有特定记忆或信物的玩家开放。
- 同一场冲突可以由交涉、救援、追杀或调查触发。
- 结局改变不同 NPC 的信任、敌意、去向或生死状态。
- 后续伏笔引用玩家真实完成或放弃的事情。

只改变人物名字和文案措辞，但选择与后果完全相同，不算实现了玩家独立剧情。

## 6. 四个剧情节点

### 6.1 节点一：异兆信件

触发条件满足后，后台生成一封不阻塞挂机结算的剧情信件：

- 明确引用一条玩家旧记忆。
- 引入或复用一名玩家私有 NPC。
- 若引入新人物，其自称的过去关系必须保持未证实，初始关系为 `unknown`。
- 只陈述已经确认的事实和当前异常。
- 不自动替玩家接受任务。
- 信件显示“重要剧情”标记，可稍后处理。

### 6.2 节点二：玩家抉择

信件提供两个结构化选项：

- `立即介入`：及时赶到并抢得先机，但初始危险更高。
- `先行调查`：带着明确线索进入，但目标已察觉并做好准备。

玩家未选择时直接关闭信件即可，信件保留且不创建关联秘境。秘境开始后不再存在“暂缓”选项。

每个选项使用稳定 `choice_key`。玩家提交后由服务端保存，LLM 只能解释后果，不能改写已经选择的键。

### 6.3 节点三：关联秘境

系统根据 Base、玩家选择和相关记忆生成一份个人秘境蓝图：

- 秘境仍使用现有服务端战斗、消耗和奖励系统。
- LLM 只生成场景、人物动机、线索和合法行动建议。
- 战斗胜负、受伤、物品消耗和实际奖励由服务端裁决。
- 秘境结束时发布权威结算事件，推进剧情线。

### 6.4 节点四：余波回信

秘境结算后生成结局回信：

- 引用玩家最初选择和真实秘境结果。
- 更新一名 NPC 的关系或状态。
- 若权威战斗记录已确认 NPC 死亡，只生成归档记录；死者不得再回信、问候、嘱咐或提醒玩家注意安全。
- 将本次故事压缩为一至三条长期记忆。
- 解决当前核心问题。
- 最多留下一个明确但不强制立即触发的伏笔。

## 7. 最小数据模型

### 7.1 Base 保存在代码仓库

MVP 不建立在线剧情 Base 编辑器。Base 使用严格 Schema 的 TypeScript 或 JSON 配置，随代码审核和版本发布。

这样可以减少：

- 在线配置权限与审核系统。
- 错误 Base 直接影响所有玩家的风险。
- 数据库版本迁移和运行时提示词不一致的问题。

### 7.2 `story_states`

每个角色一行：

```text
cultivator_id
version
story_seed
canon_summary
active_thread_id
updated_at
```

### 7.3 `story_memories`

保存经过验证的长期事实：

```text
id
cultivator_id
source_type
source_id
fact_fingerprint
summary
tags
entity_ids
importance
evidence
occurred_at
```

唯一约束：

```text
(cultivator_id, fact_fingerprint)
```

### 7.4 `story_entities`

只保存进入 MVP 剧情的关键 NPC：

```text
id
cultivator_id
name
entity_type
state
relationship
life_status
version
```

### 7.5 `story_threads`

```text
id
cultivator_id
framework_id
framework_version
stage
status
premise
unresolved_question
entity_ids
version
```

阶段只允许：

```text
omen → choice → confrontation → aftermath → resolved
```

### 7.6 `story_intents`

保存已经校验、等待投递或处理的剧情节点：

```text
id
cultivator_id
thread_id
story_version
beat_type
payload
requires_choice
status
delivered_via
created_at
resolved_at
```

## 8. LLM 调用设计

### 8.1 只保留三个任务

| 任务         | 运行方式                 | 输出                     |
| ------------ | ------------------------ | ------------------------ |
| 记忆提取     | 后台                     | 结构化记忆候选和事实引用 |
| 剧情节点生成 | 后台优先，玩家等待时升级 | 信件、选项和连续性声明   |
| 秘境蓝图生成 | 玩家选择后预生成         | 与个人剧情绑定的秘境方向 |

结局回信可以继续复用“剧情节点生成”，不新增第四套模型协议。

### 8.2 单次上下文上限

```text
固定世界规则
+ 一份剧情 Base
+ 一份玩家剧情摘要
+ 三至六条相关记忆
+ 最多三名相关实体
+ 当前触发事件或秘境结算
+ 当前剧情节点与已确认选择
```

不传完整聊天记录、全部秘境历史或其他玩家信息。

### 8.3 输出约束

所有输出必须通过严格 Zod Schema，至少包含：

```text
framework_id
thread_id
beat_type
summary
memory_refs
entity_refs
continuity_claims
choices
recommended_channel
```

模型只能引用输入中提供的 ID。未知 ID、跨阶段推进和无证据事实直接拒绝。

### 8.4 模型建议

第一版使用一个约 7B～14B 的指令模型完成三类任务，暂不引入复杂多模型路由：

- 结构化 JSON 稳定性优先于文学文风。
- 最大输出控制在约800～1200 tokens。
- 固定世界规则和 Schema 放在提示词前部，便于 prefill/KV 前缀缓存。
- 玩家私有记忆放在后部，缓存和日志按角色隔离。
- 后台任务允许一次带错误原因的修正重试。

MVP 通过后，再比较更大的规划模型是否显著改善因果连续性。

## 9. 触发与频率

### 9.1 第一版触发来源

第一版只接入已经有稳定结算记录的秘境事件：

- 秘境成功结算。
- 秘境撤退或战斗失败结算。

普通云游完成事件明确放到下一迭代，不纳入 MVP v0.1。

### 9.2 频率限制

- 每个角色同时最多一条活跃 MVP 剧情线。
- 每个角色最多一条待处理重要剧情信件。
- 只有当前章已完成并进入归档，才设置一天冷却；未完成时不预生成下一章。
- 后台每小时扫描一次冷却已到期的角色，通过耐久命令异步调用 LLM；因此下一章通常在上章完成后 24～25 小时内投递。
- 普通挂机事件不会每次都触发 LLM。
- 玩家不打开信件时不继续生成后续节点。

## 10. 权威校验

服务端提交剧情节点前必须检查：

- `cultivator_id` 与所有记忆、实体和剧情线一致。
- 引用的来源事件真实存在且属于该玩家。
- 剧情线只前进一步。
- 信件没有宣称玩家已经接受尚未选择的任务。
- 结局没有伪造战斗胜利、物品取得和角色死亡。
- 模型输出不包含资源数量和直接数据库操作。
- 同一触发事件不会重复创建剧情线或重复发送信件。

模型失败不回滚原本的云游或秘境结算。

## 11. 降级方案

### 11.1 记忆提取失败

根据权威事件生成确定性摘要，例如：

```text
玩家在指定秘境选择了某行动，并以成功、撤退或失败结束。
```

### 11.2 剧情节点生成失败

- 保留待生成任务并后台重试。
- 超过重试次数后使用 Base 内置短模板。
- 不向玩家显示内部错误和残缺 JSON。

### 11.3 秘境蓝图生成失败

使用普通秘境模板，但继续携带当前剧情线、NPC 和选择作为叙事约束。故事可以完成，不因模型故障永久卡住。

## 12. 前端 MVP

### 12.1 信件列表

- 增加“重要剧情”标记。
- 显示未处理剧情数量。
- 不强制弹窗打断挂机。

### 12.2 信件详情

- 展示剧情正文和引用旧事的简短提示。
- 展示两个选择。
- 提交前二次确认不可立即撤销的选择。
- 已处理信件只读展示玩家当时的选择。

### 12.3 关联秘境入口

- 信件处理后提供“前往”按钮。
- 显示境界、灵气和风险要求。
- 未做选择时关闭信件即可暂缓；之后可重新打开信件。
- 秘境页面只显示当前关联剧情标题，不在秘境页内嵌入第二套剧情操作界面。

### 12.4 前尘录

- 在常规游戏导航的“见闻”分组中提供“主线纪事”入口，场景名为“前尘录”。
- 首屏优先展示当前章节、所处步骤和下一步行动；步骤固定为“来信 → 抉择 → 关联秘境 → 余波”。
- 玩家可展开完整卷宗，查看剧情信、已确认选择、结局回信、关键人物关系与生死状态、尚存线索。
- 已结束章节按时间倒序保存最近三十章，作为复盘记录；普通邮件和无关云游不进入卷宗。
- 前尘录只读，不在页面内复制“选择”或“开启秘境”按钮，避免产生两套剧情状态入口。
- 不新增剧情记录表。接口从 `story_states`、`story_threads`、`story_intents`、`story_entities` 和关联的 `dungeon_runs` 实时投影，数据库中的权威事实仍只有一份。

## 13. 可观测性与成本

至少记录：

- 每类 LLM 任务调用次数、耗时、输入和输出 tokens。
- 结构化输出首次通过率和修正重试率。
- 剧情信件生成、打开和选择转化率。
- 关联秘境开始率和完成率。
- 每次生成引用的记忆数量。
- 事实冲突与未知 ID 拒绝次数。
- Base 下不同选择和结局的分布。
- 跨角色私有数据泄漏次数；必须为零。

初始限流：

```text
每个角色同时最多1个剧情生成任务
每条剧情节点最多修正重试1次
队列拥堵时停止未打开信件的后续预生成
玩家已点击并等待的任务优先级最高
```

## 14. 开发阶段

### 阶段一：数据与记忆

1. 增加五张 MVP 表及迁移。
2. 实现按 `cultivator_id` 隔离的仓储层。
3. 消费一个已有秘境结算事件。
4. 提取、验证并保存结构化记忆。

完成标准：同一事件重复消费不会产生重复记忆，不同玩家无法互相检索。

### 阶段二：Base、导演与剧情信件

1. 在代码中定义《前尘回响》Base 和 Schema。
2. 实现最小 `NarrativeDirector`。
3. 生成并校验异兆信件和剧情选择。
4. 写入 `story_intents` 并投递现有信件系统。

完成标准：两个测试角色可以收到引用各自经历的不同信件。

### 阶段三：选择与关联秘境

1. 增加剧情信件选择接口。
2. 原子保存玩家选择并推进阶段。
3. 生成个人秘境蓝图。
4. 将剧情线和蓝图绑定到现有秘境运行状态。

完成标准：玩家选择不同选项时，秘境动机、线索或进入方式发生真实变化。

### 阶段四：余波与闭环

1. 消费关联秘境结算事件。
2. 生成结局回信。
3. 更新 NPC 关系、剧情线和长期记忆。
4. 解决剧情线并设置冷却。

完成标准：一条个人剧情可以完整经历四个节点，并被下一条测试剧情正确引用。

### 阶段五：运维与灰度

1. 增加管理员查询和失败任务重试。
2. 按白名单角色灰度开放。
3. 收集重复率、矛盾率、等待时间和完成率。
4. 根据数据决定是否增加第二份 Base 和更多触发来源。

## 15. MVP 验收标准

### 15.1 功能验收

1. 两个玩家使用同一 Base，收到的剧情分别引用各自真实经历。
2. 玩家选择会改变关联秘境的至少一个实际条件，而非只改正文。
3. 关联秘境真实结果会改变结局回信和 NPC 关系。
4. 一条剧情能够经历异兆、抉择、冲突和余波并正常结束。
5. 玩家未选择而关闭信件时，不创建秘境，挂机和其他玩法不受阻塞。

### 15.2 安全验收

1. 跨玩家记忆、实体和剧情线泄漏次数为零。
2. LLM 无法直接发放或扣除任何资源。
3. 无证据事实、未知 ID 和非法阶段推进不能提交。
4. 重复事件和重复请求不会生成多封相同信件。
5. LLM 完全不可用时仍能通过模板走完整条剧情。

### 15.3 质量验收

建议用至少20名内部测试角色完成测试：

- 同一 Base 的关键因果完全重复率低于30%。
- 有历史可用时，旧记忆有效引用率达到100%。
- 结构化输出首次通过率达到95%以上。
- 剧情事实冲突通过率为0%。
- 玩家点击选择后的 P95 等待时间目标由选定模型实测确定。

## 16. MVP 之后再讨论的内容

通过 MVP 后，再依次决定：

1. 增加宗门 NPC 对话和地图变化渠道。
2. 增加第二至第五份剧情 Base。
3. 接入突破、炼器、市场和 PvP 死亡事件。
4. 增加章节摘要和向量召回。
5. 引入更大的剧情规划模型或多模型路由。
6. 让不同玩家的个人剧情在受控条件下产生公共世界事件。

在 MVP 数据证明玩家愿意打开、选择并完成个人剧情之前，不进入第六项。

## 17. MVP v0.1 实现落点（2026-08-25）

当前第一条纵向闭环已经按本文档开始实现：

1. 新增 `story_states`、`story_memories`、`story_entities`、`story_threads`、`story_intents` 五张表，并为单角色单活跃剧情、事件记忆去重、关联秘境唯一绑定建立数据库约束。
2. `dungeon.run.settled` 由独立剧情投影消费。普通秘境结算先形成长期记忆；角色无活跃剧情且不在冷却期时，再生成《前尘回响》重要信件。LLM 失败时使用确定性模板，不影响原秘境结算。
3. 新信件只提供 `intervene_now`、`investigate_first` 两个稳定选择。`delay` 仅保留用于解析旧数据；新流程关闭信件即暂缓，未选择前不创建秘境。
4. 立即介入与先行调查会生成不同的关联秘境蓝图。立即介入为“抢得先机 + 初始危险更高”，先行调查为“获得明确线索 + 目标已有准备”；同时保留 `+10` 与 `-5` 的初始危险度修正。
5. 关联秘境状态携带剧情线、已确认选择、目标、开场钩子和主线索，每轮秘境 LLM 只能延续这些叙事约束，仍不得决定战斗、消耗、奖励或结算。
6. 关联秘境完成、撤退或主动放弃后都会发出结算事件，生成结局回信、更新人物关系、写入长期记忆并进入一天冷却。冷却到期后，每小时运行的耐久后台命令会异步生成下一章；当前章未完成时不会生成新章。
7. 现有邮件列表直接显示“重要剧情”，详情中完成选择和“前往关联秘境”；不增加挂机弹窗。另提供只读“前尘录”，集中复盘当前进度、玩家选择、余波回信和人物状态，但不承载剧情命令。
8. 剧情实体持久化 `life_status`。余波生成前会根据关联秘境的击败名单决定叙述者；已死亡实体强制使用系统归档视角，关系记为 hostile。
9. 新剧情只检索与当前地点、势力或核心物件共享具体标签的旧记忆。无关死者不进入 LLM 上下文；相关死者也只能作为历史后果出现。
10. 个人剧情事件奖励改为可选，线索不再强制物化。已得物品若被文案宣称炼化、粉碎或销毁，但服务端没有相应台账，该轮生成直接驳回。收束轮只打开新入口也不能视为完成。
11. `GET /api/story/archive` 从现有权威表投影最近三十章，不创建重复存档；前端路径为 `/game/story`，导航显示“主线纪事”。

生产环境默认关闭全量触发，可通过以下变量灰度：

```text
PERSONAL_STORY_ENABLED=true                  # 全量开启
PERSONAL_STORY_CULTIVATOR_IDS=uuid1,uuid2   # 只开放指定角色
```

开发与测试环境在未显式配置时默认开启。生产既未全量开启、也未填写白名单时不消费新剧情。

## 18. MVP v0.2：普通云游事件

### 18.1 目标与边界

在现有【外出历练】收益结算之后，有限度地生成一个玩家可选择的【途中异闻】。该事件用来验证【普通玩法中的小选择能否成为后续主线的真实旧事】，不扩张为第二套主线系统。

v0.2 严格限制为：

- 每次历练结算最多一个云游事件。
- 每个事件恰好两个选择，选择键由服务端分配并只能提交一次。
- 事件可在选择后发放一份额外灵石、修为或感悟奖励。LLM 只能为每个分支选择奖励类别，具体数值必须由服务端按境界、阶段和历练时长缩放。
- 不触发战斗，不改写 NPC 生死，不直接推进《前尘回响》的阶段。
- 已有活跃主线可以被当作叙事背景，但云游事件不能替玩家做主线抉择。

### 18.2 产品流程

```text
领取历练收益
  → 服务端先提交确定性资源结算
  → 发布 yield.claimed 权威事件
  → 后台按规则生成或跳过途中异闻
  → 历练归来弹窗展示正常收益
  → 玩家点击【查看途中异闻】
  → 逐字显示事件，点击【下一步】后显示两个选择
  → 服务端原子确认选择、按缩放曲线发放奖励并返回对应结果
  → 只将已选结果与实际奖励写入长期记忆
```

玩家关闭弹窗不代表放弃。未选事件保留，并通过现有首页【外出历练】区域继续处理；同一角色同时最多一个待处理云游事件。

### 18.3 触发规则

生产默认规则：

- 本次历练达到 4 小时后才可触发。
- 距上一个云游事件至少 12 小时。
- 普通情况使用基于 `actionInstanceId` 的确定性 35% 命中。
- 本次历练达到 20 小时时必定命中。
- 存在待处理云游事件时不生成新事件。

开发和测试环境允许将命中率设为 100%，但仍保留幂等和单待处理事件限制。

生产环境可用 `PERSONAL_STORY_TRAVEL_EVENT_CHANCE=0.35` 调整命中率；取值会被限制在 `0` 到 `1`。开发和测试环境未配置时默认为 `1`。

### 18.4 事件类型

首版只允许三种低影响类型：

1. `memory_echo`：与玩家某条旧记忆相关的遗迹、物件或传闻。
2. `roadside_encounter`：与临时人物进行帮助、试探或避让。
3. `wild_omen`：发现山野异常和未明线索，但不当场开启秘境。

每个选择都需要预生成一份只在选中后可见的结果、记忆摘要和奖励类别。一次结构化 LLM 调用同时生成事件与两个候选结果，玩家提交选择时不再发起第二次生成。

奖励使用现有 `YieldCalculator` 作为缩放基准：先以固定随机源计算同境界、同阶段、同历练时长的标准收益，再取 25% 作为云游事件奖励，且至少为 1。这使奖励随境界和历练时长增长，同一事件重试时又不会变动。首版不生成材料奖励，避免让 LLM 参与物品蓝图和背包幂等。

### 18.5 数据与幂等

不新建平行剧情表，将 `story_intents` 扩展为真正的渠道无关节点：

- `thread_id` 改为可空，普通云游事件不强制属于主线。
- 增加 `source_type` 与 `source_id`，以 `yield_claim + actionInstanceId` 标识来源。
- 对角色、来源类型、来源 ID 和节点类型建立唯一约束。
- 使用 `ready/delivered/resolved/failed` 状态，选择后将事件置为 `resolved`。
- 选中结果使用 `travel_event` 指纹写入 `story_memories`，证据同时记录服务端实际发放的奖励。重复请求不重复产生记忆或奖励。

### 18.6 LLM 边界与降级

LLM 输入只包含角色基本信息、本次历练时长、一条当前主线摘要、三至六条相关记忆和最多三个已知实体。LLM 输出必须经过严格 Schema 与连续性校验，禁止：

- 输出奖励数量、物品蓝图或属性增益。选项只允许从 `spirit_stones`、`cultivation_exp`、`comprehension_insight` 中选择一个奖励类别。
- 宣称战斗胜利、击杀或改变已知实体的生死。
- 引用未提供的记忆、实体或其他玩家事实。
- 替玩家选择或宣称未被服务端确认的后续已经发生。

生成超时、Schema 失败或连续性冲突时，改用内置的两选一短事件；原本历练收益已经提交，不因剧情生成失败而回滚。

### 18.7 前端与验收

云游事件继续使用现有【历练归来】弹窗，不新增独立页面：

1. 首先展示服务端已结算的常规收益。
2. 命中云游事件后显示【查看途中异闻】，不在收益首屏堆叠规则。
3. 事件正文逐字显示；正文结束后由【下一步】显示两个选择。
4. 确认后只展示选中结果，未选结果永不下发到浏览器。
5. 关闭后可在首页的外出历练区域恢复，新的收益领取不得覆盖待选事件。

验收标准：

- 重复消费同一 `yield.claimed` 不会创建第二个事件。
- 两次提交选择不会生成两条记忆，也不能改选。
- 奖励数值随境界、阶段和历练时长缩放，同一事件重试数值不变且只发放一次。
- 关闭弹窗后能继续处理，玩家不会被强制停留。
- 选择形成的记忆能被后续《前尘回响》信件或关联秘境引用。
- LLM 完全不可用时，历练收益和云游选择仍可正常完成。

## 19. 一期联动：主线云游、关联秘境与延迟回响

> 实现状态：已完成代码与数据迁移。本文若与 v0.1 的四节点流程冲突，以本节为准。

### 19.1 联动范围

一期只联动《前尘回响》的个人主线和该主线创建的关联秘境，不把所有普通秘境都串成主线。

- 普通秘境：继续产生权威结算记忆，可作为以后生成主线的种子。
- 普通云游：继续产生短异闻与长期记忆，不直接改变主线阶段。
- 主线云游：必须带有 `thread_id` 和联动类型，只能推进对应玩家的当前主线。
- 关联秘境：必须携带同一剧情线的 `storyContext`，其结算才有资格创建延迟回响。

### 19.2 新状态机

```text
重要剧情信
  → 玩家选择立即介入或先行调查
  → 主线云游前奏（两选一）
  → 关联秘境解锁并完成
  → 余波回信 + 延迟回响排期
  → 玩家回应延迟回响
  → 当前章节归档并进入下一章冷却
```

权威阶段改为：

```text
omen → choice → travel_prelude → confrontation → aftermath → resolved
```

主线纪事同步改为五步：

```text
来信 → 抉择 → 途中追查 → 关联秘境 → 延迟回响
```

### 19.3 主线云游如何影响秘境

剧情信选择确认后，服务端并行生成秘境蓝图和一条与当前剧情线绑定的云游前奏。此时秘境尚未解锁，玩家必须先在首页处理该线索。

两个云游选择的数值影响由服务端固定裁决：

| 云游选择 | 秘境初始危险修正 | 叙事意义                           |
| -------- | ---------------: | ---------------------------------- |
| 谨慎接近 |               -5 | 排除伪痕、确认更安全的进入路线     |
| 果断行动 |               +5 | 抢得先机，但让秘境中的存在提前警觉 |

该修正与信件选择原有的 `+10/-5` 合并，并被限制在 `-10` 到 `+10`。LLM 只负责解释已经确认的途中结果，不得自行修改危险值。选中的 `travelOutcome` 会随关联秘境状态传入每轮和结算提示词，秘境不能遗忘或要求玩家重复处理同一线索。

### 19.4 延迟回响

关联秘境结算后，系统先按真实战斗结果生成余波回信并更新人物状态，同时创建一个 `travel_echo` 剧情意图：

- 回响保存完整结构化内容、两个候选结果、来源秘境和对应剧情线。
- `available_at` 控制最早显现时间；生产默认延迟 12 小时，开发环境默认立即显现，便于测试。
- 可用 `PERSONAL_STORY_ECHO_DELAY_HOURS` 覆盖延迟小时数，最小为 0。
- 回响到期后优先于普通云游显示；首页每分钟检查一次，玩家刷新页面也会立即检查。
- 玩家回应前，剧情线停在 `aftermath`，不会提前归档或生成下一章。
- 玩家回应后，服务端原子写入回响记忆、发放缩放奖励、将剧情线置为 `resolved`、清除当前活跃剧情并开始一天冷却。

延迟回响只能承接权威秘境结算，不得制造第二场战斗、推翻死亡、凭空增加物品或改写胜负。

### 19.5 持久化与幂等

本期迁移增加：

```text
story_threads.linkage_context  # 保存前奏选择、秘境结算和回响排期
story_intents.available_at     # 控制延迟意图的显现时间
```

同一剧情线分别最多拥有一个 `travel_prelude` 和一个 `travel_echo`。所有云游选择继续通过玩家命令锁、资源幂等键、剧情意图状态和记忆指纹共同防重；重复请求只返回已提交结果，不能改选，也不会重复发奖。

### 19.6 一期验收点

1. 信件选择后不能直接进入秘境，必须先完成关联云游。
2. 两种云游选择会产生可验证的不同初始危险值，并写入秘境 LLM 上下文。
3. 普通秘境不会误推进当前主线，只保存可供以后引用的记忆。
4. 关联秘境结算后章节保持未归档，直到延迟回响被回应。
5. 回响未到 `available_at` 前，接口和前端都不能提前选择。
6. 回响到期后优先显示，完成后才开始下一章冷却。
7. LLM 失败时使用主线专用降级模板，整条状态机仍能闭环。

## 20. 后续动态剧情统一架构（强制约束）

> 状态：已确认为后续所有动态剧情事件的统一实施方案。突破、炼器、市场、宗门、秘境、云游以及将来新增的玩法，不得再各自建立独立的剧情生成器、奖励入口或前端弹窗协议。

### 20.1 固定实施顺序

每接入一种新的动态剧情来源，都必须按以下顺序完成：

1. 玩法先发布可验证、可幂等消费的权威领域事件。
2. 将事件转换成统一 `ActivityStory` 上下文，不把业务数据库或整段运行状态直接交给 LLM。
3. 统一剧情导演在同一根活动上裁决 `主线推进 / 活动短篇 / 忽略`，高优先级结果覆盖尚未展示的低优先级候选。
4. LLM 只能选择奖励类别；数值由服务端预算、境界缩放和上限校验决定。
5. 玩法结算完成后，通过同一个待处理队列和同一个剧情弹窗显示正文、选择与结果。
6. 上线前必须通过幂等、奖励上限、跨角色隔离和重复触发测试。

### 20.2 权威事件契约

每种活动事件至少包含：

```text
cultivator_id
activity_type
activity_id
root_activity_id
occurred_at
authoritative_summary
source_reference
```

- `activity_id` 标识当前事件。
- `root_activity_id` 标识整条根活动，用来合并“秘境结算”和“该秘境同时完成宗门委托”等派生事件。
- 派生事件必须保留根活动 ID，不得以新的随机 ID 绕过去重。
- 事件只能声明玩法已经提交的事实；模型生成的剧情文案不能反向成为权威事件。

第一条新增事件为 `sect.task.completed`。宗门任务达成时写入事务消息，与任务状态同事务提交；事件至少记录任务、宗门、角色和完成来源。若由秘境完成宗门任务，`root_activity_id` 必须继续指向该秘境运行。

### 20.3 统一 ActivityStory

所有活动短篇共享：

- 一套结构化生成 Schema。
- 一套选择键、隐藏候选结果和连续性校验。
- 一套待处理意图、恢复入口和选择幂等事务。
- 一套奖励预算函数和资源发放路径。
- 一套逐字正文 → 下一步 → 选择 → 结果的前端弹窗。

活动差异只通过结构化 `activity_type` 和权威摘要表达：

```text
travel      云游历练
sect_task   宗门任务
dungeon     普通秘境探索
```

主线云游前奏和延迟回响仍属于主线节点，但复用 ActivityStory 的显示、选择和奖励协议。

### 20.4 统一导演优先级

同一个 `root_activity_id` 最终只能保留一个剧情裁决：

```text
主线关联秘境结算
  > 新主线异兆
  > 宗门任务短篇
  > 普通秘境短篇
  > 普通云游短篇
```

示例：一次秘境同时完成宗门委托时，不能同时生成“普通秘境短篇”和“宗门任务短篇”；宗门任务短篇优先。若该秘境本身是当前主线关联秘境，则主线余波与延迟回响优先，宗门任务仍可正常结算奖励，但不再额外生成活动短篇。

导演裁决必须持久化。高优先级事件到达较晚时，可以替换尚未显现或尚未选择的低优先级候选；已经完成的选择不得被模型或迟到事件静默改写。

### 20.5 奖励预算

ActivityStory 不接受 LLM 输出数值。服务端按活动类型、角色境界、阶段和活动规模计算最大预算：

- 云游短篇：标准同档收益的 25%。
- 普通秘境短篇：标准同档收益的 20%。
- 宗门任务短篇：标准同档收益的 15%，不替代原宗门任务奖励。
- 任意活动短篇硬上限：标准同档收益的 25%。

实际奖励必须为正整数，且不超过当前活动类别预算与全局硬上限两者中的较小值。资源引擎提交前再次校验；校验失败时整笔剧情选择事务回滚，不允许“先发奖、后记失败”。

物品奖励还必须通过活动开始时锁定的境界基础档与活动层级校验。炼气普通秘境最多「玄品」，跨宗门比试可上浮到「真品」；跨宗门大秘境的服务端限定唯一奖励槽可例外产出「地品」。该例外属于正式活动结算，不进入 ActivityStory 额外奖励池，也不提高普通秘境的品阶上限。

限定唯一槽可在服务端奖励定义中获得使用豁免，但效果必须继续按角色当前境界缩放。炼气至渡劫共用同一规则；豁免仅适用于限定传承、功法或法器，不适用于会绕过药力承受上限的高阶丹药。

其他境界使用同一缩放函数：跨宗门比试和大秘境普通池在当前境界的普通秘境上限上增加一个品阶，大秘境限定唯一槽增加两个品阶，最高封顶为「神品」。封顶后通过数量、词缀稀有度和活动专属效果继续缩放。

### 20.6 后续事件接入清单

以后接入突破、炼器、市场、宗门人物或世界事件时，PR 必须同时说明：

1. 权威事件由哪一笔事务发布。
2. 根活动 ID 如何继承与去重。
3. 在统一导演中的优先级。
4. 哪些字段允许进入 LLM，哪些事实禁止改写。
5. 奖励预算来源和硬上限。
6. 结算后如何让统一弹窗发现待处理事件。
7. 重复消息、并发选择、跨角色请求和迟到高优先级事件的测试结果。

缺少其中任一项的新动态剧情来源，不进入生产启用范围。

### 20.7 与全游戏剧情总纲对齐后的当前修正项

继续实现前还必须完成：

1. 统一领域事件包络，让 `sect.task.completed` 显式携带 `activity_id`、`root_activity_id`、`authoritative_summary`、锁定境界档与活动层级。
2. 为 `story_threads` 增加 `thread_scope = personal | sect`，将开放剧情线唯一约束改为按角色与 scope 隔离。
3. 导演候选区分“个人主线”、“宗门主线”与“活动短篇”；一个根活动最多推进一条主线，另一条只能弱引用。
4. 持久化导演裁决，支持迟到高优先级事件替换尚未显现的低优先级短篇，但不改写已完成选择。
5. 建立共享活动奖励档配置，由“境界基础池 + 活动层级上浮 + 限定唯一奖励槽”裁决，不在 ActivityStory 、秘境和宗门服务中分别复制品阶表。
6. 限定唯一奖励必须具有稳定奖励定义 ID、活动期次 ID、服务端使用豁免和发放幂等约束；LLM 只能引用已确认的发放结果。
7. 统一弹窗要区分“玩法正式奖励”与“ActivityStory 额外回响奖励”，并覆盖幂等、跨角色隔离、超品阶拒绝、限定奖励重复领取与迟到事件测试。
