# 全游戏动态剧情、实时秘境与长期记忆设计

> - 状态：设计稿
> - 适用范围：全游戏剧情中枢，以及云游、信件、宗门 NPC、地图变化、任务和单人秘境等剧情出口
> - 目标：共用世界规则与剧情框架，为每个玩家生成并持续演化一条独立剧情；玩家过去的选择、人物关系和未完成事件会在后续玩法中产生影响。

## 1. 背景

当前秘境已经具备状态驱动的多轮生成流程：

```text
生成当前场景
  → 玩家选择行动
  → 服务端验证代价、执行战斗或资源变化
  → LLM 生成下一幕
  → 服务端保存当前秘境状态
```

现有实现已经解决了以下问题：

- 进行中秘境通过 `DungeonState` 和 `dungeonRuns` 保存权威状态。
- 模型返回结构化场景、选项、奖励蓝图和危险分。
- 战斗胜负、资源消耗、实际奖励由服务端裁决。
- 已击败敌人、当前战利品、最近选择会进入后续回合上下文。
- 秘境结束时写入 `dungeonHistories` 并发布 `dungeon.run.settled` 领域事件。

但当前上下文只包含本次秘境最近三轮历史，`dungeonHistories` 也属于短期归档数据并会被定时清理，因此现有系统不能形成跨秘境长期剧情。

本设计不是在普通云游旁边增加一个孤立的“云游剧情模块”，而是在现有玩法之上增加统一剧情中枢。云游、秘境、战斗、宗门、突破和炼器向中枢提交权威事件；信件、途中事件、NPC 对话、地图变化、任务和秘境则是剧情中枢选择的不同呈现出口。

在保留现有玩法规则边界的基础上，系统增加共享剧情框架、玩家私有剧情实例、长期记忆、剧情线、叙事导演、投递路由和后台预生成能力。

## 2. 设计目标

### 2.1 必须实现

1. 每次进入秘境都创建新的场景、事件和路线组合。
2. 玩家存在有效历史时，新秘境必须引用至少一条相关旧记忆或活跃剧情线。
3. 玩家过去的选择能够影响后续 NPC 态度、势力关系、事件条件和剧情走向。
4. 剧情能够经历伏笔、发展、冲突和解决，而不是反复引用同一段旧事。
5. 长期记忆不依赖即将过期的完整秘境日志。
6. 模型不能自行修改气血、法力、灵石、物品、境界、奖励数量和战斗结果。
7. 可以后台预生成，降低玩家进入秘境和选择行动后的等待时间。
8. 模型服务故障时，玩家仍可通过确定性模板继续游戏。
9. 所有玩家可以使用同一份剧情框架，但人物、起因、关系、分支、后果和结局由各自经历决定。
10. 同一条玩家剧情可以从信件开始，经宗门 NPC 推进，在秘境中冲突，并通过地图或势力变化留下结果。

### 2.2 暂不作为第一版目标

- 生成完整且永久存在的开放世界地图。
- 让模型直接调用数据库或任意游戏服务。
- 一次性生成所有可能的分支树。
- 第一版即依赖向量数据库或外部记忆服务。
- 让多个玩家共享并修改同一个全局剧情世界。

## 3. 核心原则

### 3.1 服务端事实高于模型叙事

模型输出始终是提案。只有服务端确认发生的行为才能成为长期记忆，例如：

- 玩家真正点击并提交的选择。
- 服务端确认的战斗胜负。
- 服务端确认死亡的敌人。
- 实际发放或扣除的资源和物品。
- 已提交的任务、境界和势力状态变化。

模型描述中出现但未被服务端确认的内容，不得进入世界事实。

### 3.2 记忆是结构化事实，不是完整聊天日志

完整日志只用于短期查看、追查和重新提炼。长期剧情使用经过验证的结构化记忆、实体状态、关系和剧情线。

### 3.3 蓝图负责方向，运行时负责演化

进入秘境前生成五幕左右的剧情蓝图，但不提前写死每一段正文和全部分支结果。运行过程中根据玩家真实选择、战斗结果和当前状态生成下一幕。

### 3.4 不预生成完整分支树

每轮最多只向前预测一层。完整分支树会随选项数量指数增长，并且大量内容最终不会被玩家看到。

### 3.5 共用框架不等于共用剧本

剧情框架只规定主题、阶段、合法冲突、进入条件和规则边界，不写死玩家必定遇到的 NPC、事件顺序、选择和结局。框架相当于可复用的叙事语法，玩家剧情实例才是实际发生的故事。

两个没有历史的新玩家在前期可能遇到相似的引子；随着选择、战斗结果、关系和持有线索不同，剧情会自然分化。系统不以随机改写文案伪造“不同”，而以因果状态不同产生真正不同的后续。

### 3.6 每个玩家拥有独立剧情实例

玩家的记忆、实体、关系、剧情线、待处理剧情和生成草稿全部以 `cultivator_id` 隔离。共享的只有世界设定、可用剧情框架和确定性游戏规则，不能把甲玩家生成的私有 NPC、秘密或结局当成乙玩家的事实。

### 3.7 剧情状态独立于呈现渠道

剧情线不属于云游、信件或秘境中的任何一个模块。剧情中枢先产生与界面无关的 `StoryIntent`，再根据玩家是否在线、当前所在场景和事件重要性选择渠道：

- 挂机或离线：通过信件通知，重大选择保持待处理。
- 正在云游：普通事件作为非阻塞途中事件出现。
- 回到宗门：由相关 NPC 主动对话或更新任务。
- 世界产生后果：修改地图节点、NPC 状态或势力可见信息。
- 需要玩家主动参与：生成任务或关联秘境。

重大选择不得在挂机期间自动替玩家决定。

## 4. 总体架构

```text
┌─────────────────────────────────────────────┐
│ 服务端权威事件                              │
│ 云游 / 秘境 / 战斗 / 突破 / 炼器 / 宗门任务  │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│ StoryMemoryProjector                        │
│ 收集证据、提取记忆、校验事实、更新剧情版本   │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│ 玩家私有剧情实例                            │
│ 记忆 / 实体 / 关系 / 剧情线 / 待处理选择     │
└──────────────────────┬──────────────────────┘
                       │        ┌────────────────────┐
                       │        │ 共享世界与剧情框架  │
                       │        └─────────┬──────────┘
                       ▼                  ▼
┌─────────────────────────────────────────────┐
│ NarrativeDirector                           │
│ 选择框架、检索旧事、确定推进目标与呈现渠道   │
└──────────────────────┬──────────────────────┘
                       ▼
┌─────────────────────────────────────────────┐
│ LLM StoryBeatGenerator                      │
│ 框架 + 玩家记忆 + 当前场景 → 独立剧情提案    │
└──────────────────────┬──────────────────────┘
                       ▼
┌─────────────────────────────────────────────┐
│ StoryValidator + StoryIntentRouter           │
│ 校验事实与规则，持久化后选择投递渠道          │
└──────────────────────┬──────────────────────┘
                       ▼
┌─────────────────────────────────────────────┐
│ 信件 / 云游事件 / NPC / 任务 / 地图 / 秘境   │
└──────────────────────┬──────────────────────┘
                       ▼
                  玩家行动或选择
                       └────────→ 新的权威事件
```

### 4.1 四层生成模型

| 层级 | 是否共享 | 职责 |
| --- | --- | --- |
| 世界规则 | 全服共享 | 境界、势力基础设定、地理、玩法规则和不可违反的世界事实 |
| 剧情框架 Base | 全服共享、带版本 | 主题、阶段类型、进入条件、合法冲突、必需信息和禁止事项 |
| 玩家剧情实例 | 角色私有 | 已发生事实、关系、伏笔、选择、剧情线阶段和待处理节点 |
| 剧情节点 Beat | 角色私有 | LLM 为当前玩家生成的具体人物、对话、事件、分支和衔接 |

一份 Base 可以服务大量玩家，但每次生成必须组合当前角色的私有状态。Base 更新后，已进入旧版本剧情线的玩家继续使用原版本或经过显式迁移，不能无提示改写已经发生的剧情。

### 4.2 剧情框架示例

```json
{
  "id": "base_sect_crisis",
  "version": 1,
  "theme": "宗门内部危机与立场选择",
  "entryConditions": ["已加入宗门", "存在至少一名相关 NPC"],
  "stages": [
    { "type": "omen", "purpose": "出现与玩家旧经历有关的异常" },
    { "type": "investigation", "purpose": "提供两种以上可验证线索" },
    { "type": "commitment", "purpose": "要求玩家选择信任对象或行动方向" },
    { "type": "confrontation", "purpose": "通过战斗、交涉或秘境解决核心冲突" },
    { "type": "aftermath", "purpose": "把选择结果写回人物、势力或地图" }
  ],
  "allowedChannels": ["mail", "travel_event", "npc_dialogue", "task", "dungeon", "map_change"],
  "forbiddenClaims": ["替玩家决定重大选择", "直接发放资源", "推翻永久事实"]
}
```

框架不应写死“某长老必定是内鬼”或“玩家必定帮助某人”。具体涉事人物、动机、线索和结局由玩家已有关系和后续选择决定。

### 4.3 单次生成输入与输出

生成输入只包含当前任务需要的最小上下文：

```text
共享世界规则与选中的 Base
+ 当前触发事件
+ 玩家剧情摘要
+ 一条待推进剧情线
+ 三至六条相关记忆
+ 必要 NPC、地点和势力状态
+ 当前可用的呈现渠道
+ 服务端允许的玩法动作
```

LLM 返回结构化提案，而不是直接执行游戏逻辑：

```json
{
  "frameworkId": "base_sect_crisis",
  "threadId": "thread_private_1024",
  "beatPurpose": "investigation",
  "memoryRefs": ["memory_1032"],
  "entityRefs": ["npc_private_88"],
  "summary": "曾受玩家帮助的弟子送来一封带血的账册残页",
  "recommendedChannel": "mail",
  "requiresPlayerChoice": true,
  "choices": [
    { "key": "meet_sender", "intent": "立即赴约" },
    { "key": "verify_first", "intent": "先查验账册" },
    { "key": "postpone", "intent": "暂不介入" }
  ],
  "continuityClaims": [
    { "memoryId": "memory_1032", "usage": "弟子因旧恩选择向玩家求助" }
  ]
}
```

服务端验证引用、阶段和渠道后，先保存为该玩家的正式剧情节点，再投递到前端。生成失败或玩家离线不会丢失关键剧情。

### 4.4 独立剧情的分化来源

玩家剧情由以下信息共同决定：

- 初始剧情种子，用于需要可重现的随机选择，不作为唯一差异来源。
- 角色宗门、境界、功法、常去地点和已解锁玩法。
- 玩家亲自做出的选择及其不可逆结果。
- 战斗胜负、放过或击杀对象等服务端权威事实。
- NPC 好感、恩怨、承诺、势力关系和未偿还的人情。
- 已持有的信物、线索和已经解决或放弃的剧情线。
- 近期重复惩罚，避免不同剧情线反复使用同一种冲突。

NPC 名称和措辞不同但因果完全相同，只算表现差异，不算独立剧情。验收时应检查剧情线、关系、选择条件和世界后果是否真正发生分化。

### 4.5 实时生成与算力控制

不在每次普通云游结算时生成长篇正文，也不一次生成完整个人剧本：

- 后台生成：记忆提取、章节摘要、下一剧情目标、秘境蓝图和可能的普通事件。
- 实时生成：玩家正在等待的关键对话、当前选择后的下一节点和强关联场景。
- 确定性执行：战斗、奖励、消耗、境界、掉落和任务条件。
- 队列拥堵：暂停未必使用的分支预生成，优先处理玩家已点击的节点。
- 模型不可用：保留待处理剧情，使用短模板或延后正文生成，不丢失权威进度。

这样计算量随实际触发的剧情节点增长，而不是随所有玩家所有潜在分支指数增长。

### 4.6 一个玩家故事的跨玩法示例

```text
云游救下受伤弟子
  → 写入“旧恩”记忆
  → 挂机期间收到求援信
  → 回宗门与弟子对话并选择调查
  → 地图出现新的可疑据点
  → 据点生成关联秘境和冲突
  → 结算后改变 NPC、势力和地图状态
  → 后续突破或云游再次引用这次结果
```

这里推进的是同一条玩家私有剧情线，并非六个玩法各自维护一段互不相干的剧情。

## 5. 记忆模型

### 5.1 工作记忆

工作记忆只服务于当前秘境，继续保存在现有 `DungeonState` 中：

- 当前轮数和阶段。
- 最近场景、选择和行动结果。
- 当前分支和未探索路线。
- 已击败敌人。
- 已获得奖励。
- 当前气血、法力和危险分。

工作记忆随秘境结束而冻结，不直接承担跨秘境剧情。

### 5.2 情节记忆

记录玩家经历过的具体事件：

```json
{
  "id": "memory_1032",
  "summary": "陈安在青石谷放走了一只受伤狐妖",
  "entityIds": ["cultivator_chen_an", "npc_fox_01"],
  "locationIds": ["map_qingshigu"],
  "tags": ["狐族", "恩情", "放生"],
  "importance": 82,
  "permanent": true,
  "sourceType": "dungeon_run",
  "sourceId": "run_xxx",
  "evidence": {
    "round": 4,
    "choice": "放走受伤狐妖"
  }
}
```

情节记忆回答的是“发生过什么”。

### 5.3 世界事实与实体状态

记录不能被后续生成随意推翻的状态：

```json
{
  "entityId": "npc_fox_01",
  "name": "白璃",
  "type": "npc",
  "lifeState": "alive",
  "factionId": "faction_qingqiu",
  "lastLocationId": "map_qingshigu_north",
  "relationship": {
    "targetId": "cultivator_chen_an",
    "kind": "owes_favor",
    "strength": 70
  },
  "facts": [
    "曾被陈安放走",
    "正在被玄阴教追捕"
  ],
  "version": 3
}
```

世界事实回答的是“现在是什么状态”。

只有真正参与互动或进入重要剧情的 NPC 才晋升为持久实体。普通路人和一次性怪物不需要永久保存。

### 5.4 剧情线

剧情线负责把零散记忆连接为持续发展的故事：

```json
{
  "id": "thread_fox_debt",
  "title": "狐族旧恩",
  "status": "active",
  "stage": "developing",
  "premise": "被陈安放走的狐妖正在寻找他",
  "unresolvedQuestion": "狐族为何被玄阴教追杀",
  "nextBeat": "陈安在其他秘境发现青丘信物",
  "entityIds": ["npc_fox_01", "faction_qingqiu"],
  "priority": 75,
  "cooldownUntil": null,
  "version": 2
}
```

允许的阶段变化：

```text
introduced → developing → confrontation → resolved
```

服务端只允许一次前进一步，不允许模型从伏笔直接跳到结局，也不允许已解决剧情线回退。

## 6. 数据模型

### 6.1 `story_frameworks`

共享且版本化的剧情框架。框架应由策划维护或经过审核后发布，不能让运行时模型直接改写线上 Base。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | varchar | 稳定框架 ID |
| `version` | integer | 框架版本，与 ID 组成唯一键 |
| `title` | varchar | 框架名称 |
| `entry_conditions` | jsonb | 服务端可验证的进入条件 |
| `stage_schema` | jsonb | 允许的阶段和推进规则 |
| `prompt_spec` | jsonb | 主题、必需内容、禁止事项和可用渠道 |
| `status` | varchar | `draft`、`active`、`retired` |
| `created_at` | timestamp | 创建时间 |

### 6.2 `story_states`

每个角色一行，保存剧情总状态。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `cultivator_id` | uuid | 角色，唯一键 |
| `version` | integer | 每次权威剧情变化后递增 |
| `story_seed` | varchar | 角色私有、可重现的生成种子 |
| `canon_summary` | text | 长期剧情压缩摘要 |
| `active_thread_ids` | jsonb | 当前活跃剧情线 |
| `active_framework_refs` | jsonb | 正在使用的框架 ID 与版本 |
| `schema_version` | integer | 数据结构版本 |
| `updated_at` | timestamp | 更新时间 |

### 6.3 `story_memories`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 记忆 ID |
| `cultivator_id` | uuid | 所属角色 |
| `source_type` | varchar | `dungeon_run`、`battle`、`realm_change` 等 |
| `source_id` | varchar | 来源记录 ID |
| `fact_fingerprint` | varchar | 幂等指纹 |
| `summary` | text | 简短事件摘要 |
| `tags` | jsonb | 检索标签 |
| `entity_ids` | jsonb | 相关实体 |
| `location_ids` | jsonb | 相关地点 |
| `importance` | integer | 0～100 |
| `permanent` | boolean | 是否永久保留 |
| `status` | varchar | `active`、`compacted`、`invalidated` |
| `evidence` | jsonb | 权威证据引用 |
| `occurred_at` | timestamp | 发生时间 |

建议唯一约束：

```text
(cultivator_id, fact_fingerprint)
```

### 6.4 `story_entities`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 服务端分配的稳定 ID |
| `cultivator_id` | uuid | 第一版为玩家私有世界 |
| `entity_type` | varchar | NPC、势力、地点、物件 |
| `name` | varchar | 展示名称 |
| `state` | jsonb | 生死、位置、阵营等状态 |
| `relationship` | jsonb | 与玩家及其他实体的关系 |
| `tags` | jsonb | 检索标签 |
| `version` | integer | 实体状态版本 |
| `last_seen_at` | timestamp | 最近出现时间 |

### 6.5 `story_threads`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 剧情线 ID |
| `cultivator_id` | uuid | 所属角色 |
| `framework_id` | varchar | 使用的共享框架 ID |
| `framework_version` | integer | 创建该实例时锁定的框架版本 |
| `title` | varchar | 标题 |
| `status` | varchar | `active`、`paused`、`resolved`、`abandoned` |
| `stage` | varchar | 当前阶段 |
| `premise` | text | 剧情前提 |
| `unresolved_question` | text | 尚未回答的问题 |
| `next_beat` | text | 推荐的下一剧情节点 |
| `entity_ids` | jsonb | 涉及实体 |
| `priority` | integer | 调度权重 |
| `cooldown_until` | timestamp | 防止连续重复出现 |
| `version` | integer | 乐观并发版本 |

### 6.6 `story_intents`

保存已经通过校验、等待投递或等待玩家处理的剧情节点，使剧情进度不依附于某个 UI 模块。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 剧情节点 ID |
| `cultivator_id` | uuid | 所属角色 |
| `thread_id` | uuid | 对应玩家私有剧情线 |
| `story_version` | integer | 生成时的玩家剧情版本 |
| `beat_type` | varchar | 伏笔、调查、选择、冲突、余波等 |
| `payload` | jsonb | 已校验的正文、引用和合法选项 |
| `preferred_channels` | jsonb | 可用呈现渠道及优先级 |
| `requires_choice` | boolean | 是否必须等待玩家决定 |
| `status` | varchar | `pending`、`delivered`、`resolved`、`expired`、`invalidated` |
| `delivered_via` | varchar | 实际使用的信件、NPC、秘境等渠道 |
| `created_at` | timestamp | 创建时间 |

重大剧情 `requires_choice=true` 时只能投递，不能在离线结算中自动变为 `resolved`。

### 6.7 `dungeon_drafts`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 草稿 ID |
| `cultivator_id` | uuid | 所属角色 |
| `map_node_id` | varchar | 对应地图节点 |
| `story_version` | integer | 生成时的剧情版本 |
| `dependency_versions` | jsonb | 依赖的实体、剧情线版本 |
| `status` | varchar | `queued`、`generating`、`ready`、`claimed`、`invalidated`、`failed` |
| `blueprint` | jsonb | 秘境蓝图 |
| `model_info` | jsonb | 模型和提示词版本 |
| `expires_at` | timestamp | 普通过期时间 |
| `claimed_at` | timestamp | 被使用时间 |
| `created_at` | timestamp | 创建时间 |

建议唯一约束：

```text
(cultivator_id, map_node_id, story_version, status=ready)
```

### 6.8 `dungeon_branch_drafts`

保存当前轮各选项对应的一层预测结果：

```text
run_id
run_version
choice_fingerprint
story_version
status
generated_round
expires_at
```

运行状态或选择内容发生变化时，草稿自动失效。

## 7. 权威记忆提取流程

### 7.1 触发来源

第一版优先消费现有 `dungeon.run.settled`。后续可逐步接入：

- `cultivator.realm.changed`
- `craft.item.created`
- `ranking.challenge.completed`
- 宗门任务完成事件
- 重要市场或黑市交涉事件

### 7.2 提取输入

输入必须由服务端整理，不把整个数据库开放给模型：

```json
{
  "runId": "run_xxx",
  "mapNodeId": "qingshigu",
  "outcome": "completed",
  "choices": [],
  "confirmedBattles": [],
  "defeatedEnemyIds": [],
  "actualGains": [],
  "actualCosts": [],
  "knownEntities": [],
  "activeThreads": []
}
```

### 7.3 模型输出

```json
{
  "episodeSummary": "陈安击退玄阴教追兵，并留下狐族信物",
  "memoryCandidates": [
    {
      "summary": "陈安放走受伤狐妖白璃",
      "entityRefs": ["npc_fox_01"],
      "tags": ["狐族", "恩情"],
      "importance": 82,
      "permanent": true,
      "evidenceRefs": ["round:4:choice"]
    }
  ],
  "threadProposals": [
    {
      "threadId": "thread_fox_debt",
      "action": "advance",
      "proposedStage": "developing",
      "nextBeat": "在北方秘境发现青丘接引人"
    }
  ]
}
```

### 7.4 服务端校验

- `evidenceRefs` 必须能够指向真实记录。
- 引用实体必须存在，或满足新实体晋升条件。
- 死亡、胜利、取得物品等事实必须有服务端证据。
- 剧情线只能按合法状态机推进。
- 关系变化必须限制在允许范围内。
- 模型不得创建真实资源变化。
- 相同 `fact_fingerprint` 不得重复写入。

提取失败时，不影响原秘境结算。任务进入重试队列；多次失败后使用确定性摘要。

## 8. 叙事检索与导演决策

### 8.1 第一版检索

第一版不依赖向量数据库，按结构化字段评分：

```text
活跃剧情线匹配        40
实体或势力重合        25
地图、元素标签匹配    15
记忆重要性            10
时间接近程度          10
近期重复出现惩罚     -20
```

每次秘境建议选取：

- 一条活跃剧情线。
- 三至六条相关情节记忆。
- 三至八个相关实体状态。
- 一份长期剧情摘要。

当结构化检索效果不足时，再增加 pgvector 和本地嵌入模型。向量相似度只用于召回，不可替代实体状态和剧情线状态机。

### 8.2 导演规则

每次秘境只能选择一种主要作用：

1. 引入新伏笔。
2. 推进一条活跃剧情线。
3. 让旧选择产生后果。
4. 将剧情推入核心冲突。
5. 解决一条剧情线并留下余波。

约束：

- 存在相关记忆时，蓝图必须引用至少一条记忆 ID。
- 每次最多推进一条主要剧情线。
- 同一 NPC 或剧情线可设置一至两次秘境冷却。
- 同时活跃的主要剧情线建议不超过三条。
- 已解决剧情线只能作为回忆或余波，不能重新回到未解决状态。
- 新剧情不能推翻永久事实。

## 9. 秘境蓝图

蓝图定义本次故事方向，不直接决定真实奖励和战斗胜负。

```json

  "theme": "被追杀的狐族旧部藏身于荒废陵冢",
  "memoryRefs": ["memory_1032", "memory_1088"],
  "threadId": "thread_fox_debt",
  "threadAction": "advance",

  "continuityClaims": [
    {
      "memoryId": "memory_1032",
      "usage": "当年的放生使狐族愿意向玩家求援"
    }
  ],
  "acts": [
    {
      "index": 1,
      "purpose": "发现狐族痕迹",
      "requiredFacts": [],
      "forbiddenClaims": ["断言白璃已经死亡"]
    },
    {
      "index": 2,
      "purpose": "识破追兵伪装"
    },
    {
      "index": 3,
      "purpose": "选择是否援助狐族"
    },
    {
      "index": 4,

    },
```

服务端校验：

- 五幕目的不能提前声明玩家战斗胜利。
- `rewardThemes` 只是语义方向，实际奖励仍由现有奖励工厂生成和限制。

## 10. 实时生成与预生成时序

### 10.1 上一场结束后

```text
秘境结算事务完成
  → 发布 dungeon.run.settled
  → StoryMemoryProjector 提取并提交记忆
  → story_states.version + 1
  → NarrativeDirector 生成地点无关的 nextBeat
```

此时不直接为所有地图节点生成完整秘境，避免玩家不进入造成浪费。

### 10.2 玩家选中地图节点时

新增接口：

```http
POST /api/dungeon/prepare
{
  "mapNodeId": "qingshigu"
}
```

返回：

```json
{
  "draftId": "draft_xxx",
  "status": "queued"
}
```

后台生成绑定当前 `storyVersion` 的秘境蓝图。前端可轮询：

```http
GET /api/dungeon/prepare/:draftId
```

也可以后续改为 SSE 推送状态。

### 10.3 玩家开始秘境时

扩展现有开始接口：

```http
POST /api/dungeon/start
{
  "mapNodeId": "qingshigu",
  "draftId": "draft_xxx"
}
```

服务端在同一流程中：

1. 校验地图、境界和灵气消耗。
2. 校验草稿属于当前角色和地图。
3. 校验剧情版本和实体依赖版本。
4. 原子地将草稿从 `ready` 更新为 `claimed`。
5. 将蓝图写入新的 `DungeonState`。
6. 使用蓝图生成或读取第一幕。

草稿不存在或失效时，可以回退为当前同步生成流程。

### 10.4 当前场景展示后

玩家阅读剧情期间，对本轮最多三个选项分别生成一层下一幕草稿：

```text
场景与三个选项返回前端
  → 后台生成 choice-1 下一幕
  → 后台生成 choice-2 下一幕
  → 后台生成 choice-3 下一幕
```

玩家提交选项时：

- 草稿命中且版本一致：直接验证和使用。
- 草稿尚未完成：等待当前高优先级任务完成。
- 草稿失效：同步生成。
- 未选择的另外两个草稿标记过期。

战斗选项不能提前编造战斗结局。可以预生成敌人身份、环境和胜负两种叙事约束，真实结果返回后再生成最终正文。

## 11. 草稿版本与失效规则

每份草稿必须绑定：

```text
storyVersion
threadVersion
entityVersions
runVersion（分支草稿）
mapConfigVersion
promptVersion
```

进入或领取草稿时重新检查。

### 11.1 可以继续使用

- 气血或法力自然恢复。
- 普通库存数量变化。
- 与草稿无关的日常任务变化。
- 显示文案变化。

### 11.2 必须失效

- 蓝图引用的 NPC 死亡、失踪或阵营改变。
- 对应剧情线被其他事件推进或解决。
- 玩家跨越大境界导致秘境难度层级改变。
- 地图配置或秘境规则版本变化。
- 草稿属于其他角色或地图节点。
- 同一草稿已经被领取。

普通时间过期仍建议保留，例如三十分钟至数小时；但剧情依赖版本比固定过期时间更重要。

在现有 `DungeonRoundLlmContext` 中增加：

```ts
interface DungeonStoryContext {
  storyVersion: number;
  canonSummary: string;
  blueprint: DungeonBlueprint;
  activeThread?: {
    id: string;
    stage: StoryThreadStage;
    premise: string;
    currentGoal: string;
  };
  relevantMemories: Array<{
    id: string;
    summary: string;
    importance: number;
  }>;
  entities: Array<{
    id: string;
    name: string;
    type: string;
    stateSummary: string;
  }>;
  forbiddenClaims: string[];

```

最终单轮模型上下文只包含：

```text
固定系统规则
当前秘境蓝图
一条活跃剧情线
三至六条相关记忆
必要实体状态

```

不传全部历史日志。

固定世界规则、输出 Schema 和通用文风应放在提示词最前面，便于推理服务复用前缀缓存。

## 13. 生成任务与消息架构

现有 `backgroundCommands` 面向固定定时任务，Envelope 没有玩家、地图和剧情版本等业务载荷，不适合直接承载每个玩家的预生成任务。

建议二选一：

### 方案 A：独立叙事命令流

新增：

```text
daoyou.command.narrative.memory-extract.v1
daoyou.command.narrative.dungeon-prepare.v1
daoyou.command.narrative.branch-prepare.v1
```

使用 JetStream 持久化、重试和死信，并在数据库通过唯一键保证幂等。

### 方案 B：数据库任务表

新增 `narrative_generation_jobs`，由工作进程领取：

```text
queued → running → succeeded
                 ↘ retry_wait → running
                 ↘ failed
```

第一版建议使用方案 B，状态更容易展示给前端和管理员；后续仍可用 NATS 作为唤醒机制。

## 14. 模型部署建议

在 GB10 上可以采用两级任务：

| 任务 | 建议模型 | 调度方式 |
| --- | --- | --- |
| 记忆提取和分类 | 7B～14B | 后台低优先级 |
| 剧情线规划和秘境蓝图 | 20B～30B MoE | 后台 |
| 当前一幕、选项和 NPC 对话 | 7B～14B | 实时高优先级 |
| 嵌入向量 | 小型嵌入模型 | 后台批处理 |

第一版可以只部署一个 14B 左右模型，先验证剧情连续性。剧情规划质量不足时，再单独升级蓝图模型。

任务优先级：

```text
P0 玩家已经点击、正在等待的生成
P1 当前秘境下一层分支预生成
P2 地图节点秘境蓝图生成
P3 记忆提取、压缩和嵌入更新
```

预生成隐藏了延迟，但不会减少总算力消耗。必须限制每个角色同时存在的草稿数量，避免玩家快速切换地图节点制造大量无用任务。

建议限制：

- 每个角色最多一个正在生成的地图秘境草稿。
- 每个地图节点最多一个可领取草稿。
- 每个当前回合最多三个分支草稿。
- 新选择提交后立即取消或过期未选草稿。
- 队列过长时停止分支预测，只保留玩家已点击任务。

## 15. 长期记忆压缩

长期记忆不能无限增长。

建议策略：

- 永久事实一直保留。
- 活跃剧情线一直保留。
- 每个角色保留最近约一百条未压缩普通情节。
- 旧的低重要性记忆按地点、人物或剧情线压缩为章节摘要。
- 已解决剧情线只保留起因、关键选择、结局和余波。
- 原始秘境日志继续按现有保留策略清理。
- 角色删除时相关个人记忆级联删除。

示例：

```text
十七条青石谷零散记忆
  → 压缩为章节记忆
  → “陈安在青石谷卷入狐族与玄阴教之争，
     放走狐妖白璃，击退两名追兵，并得到狐族信物。”
```

压缩只删除冗余叙述，不得删除永久事实和未解决剧情线所需证据。

## 16. 故障与降级

| 故障 | 处理方式 |
| --- | --- |
| 记忆提取失败 | 不影响结算，后台重试；最终使用确定性摘要 |
| 蓝图生成失败 | 使用当前同步秘境生成或确定性模板 |
| 分支草稿未完成 | 将任务提升到 P0 或同步生成 |
| 模型输出冲突 | 拒绝结果并携带冲突原因修正一次 |
| 多次修正失败 | 使用服务端模板并记录告警 |
| NATS 暂时不可用 | 数据库任务保留，恢复后继续消费 |
| Redis 丢失 | PostgreSQL 中的运行状态、记忆和草稿仍可恢复 |

任何降级都不能跳过资源、奖励和战斗规则。

## 17. 可观测性

至少记录以下指标：

- 蓝图生成耗时和失败率。
- 单轮生成 prefill token、输出 token 和总耗时。
- 草稿命中率。
- 草稿失效率及失效原因。
- 玩家点击后的 P50、P95 等待时间。
- 前缀缓存命中率。
- 每次秘境引用的记忆数量。
- 无记忆引用却通过校验的异常次数。
- 事实冲突拒绝次数。
- 剧情线推进、解决和重复出现次数。
- 每个角色长期记忆数量与压缩次数。
- 各框架被实例化的次数、分支分布和结局分布。
- 不同玩家在相同框架下的实体、关系、关键选择和世界后果重复率。
- 私有实体或记忆被其他角色检索到的次数；该值必须为零。

建议目标：

```text
存在有效历史时，秘境记忆引用率 = 100%
可用草稿的原子领取成功率 > 99%
蓝图事实冲突通过率 = 0%
草稿命中时，进入秘境不等待完整蓝图生成
跨角色私有剧情数据泄漏次数 = 0
```

具体延迟目标需要选定模型后通过实际压测确定。

## 18. 安全边界

- 所有 LLM 输出使用严格 Zod Schema。
- 模型只引用服务端分配的记忆、实体和剧情线 ID。
- 模型生成的未知 ID 一律拒绝。
- 奖励、代价、伤害、境界和资源仍由现有服务计算。
- 模型不能直接执行数据库写入。
- 记忆提取和剧情更新必须幂等。
- 所有私有剧情查询必须显式包含 `cultivator_id`，不能只依赖前端传入的实体或剧情线 ID。
- 剧情框架可以共享，框架实例、生成节点和未公开事实不能跨角色复用。
- 多租户前缀缓存应按角色或用户隔离，避免记忆串号。
- 管理端需要能够查看、失效和重新提炼异常记忆。

## 19. 分阶段实施

### 第一阶段：共享框架与玩家私有记忆闭环

1. 新增版本化 `story_frameworks`，先提供两至三种经过人工审核的 Base。
2. 新增 `story_states`、`story_memories`、`story_entities`、`story_threads`。
3. 所有私有表、仓储查询和缓存键以 `cultivator_id` 隔离。
4. 新增 `StoryMemoryProjector` 消费 `dungeon.run.settled`。
5. 从权威秘境状态提取并验证结构化记忆。
6. 新秘境上下文加入当前框架和相关私有记忆。
7. 要求生成结果引用框架、记忆和实体 ID。
8. 增加死亡实体、地点状态和剧情阶段冲突校验。

完成标准：两个角色使用同一 Base 连续完成两次秘境，后续内容分别引用各自的选择，且任何角色都不能检索到另一角色的私有记忆、NPC 和剧情线。

### 第二阶段：全游戏剧情中枢与投递路由

1. 增加 `NarrativeDirector` 和结构化 `StoryBeatSchema`。
2. 新增 `story_intents`，使待处理剧情不依附于云游或秘境页面。
3. 接入云游、战斗、宗门任务和突破等权威事件来源。
4. 第一版实现信件、云游事件、NPC 对话、任务和秘境五种投递适配器。
5. 挂机时只自动结算普通事件，重大选择保存为待处理剧情并通过信件通知。
6. 玩家处理剧情后，将选择和结果重新投影为记忆、关系与剧情线状态。

完成标准：同一条剧情线能够从云游事件开始，经信件或 NPC 对话推进，并在任务或秘境中继续；切换呈现渠道不会创建重复剧情线或丢失选择。

### 第三阶段：剧情线和秘境蓝图

1. 完善剧情线状态机。
2. 增加 `DungeonBlueprintSchema` 和校验器。
3. 将蓝图加入 `DungeonState` 和单轮上下文。
4. 每次秘境最多推进一条主剧情线。
5. 将实际结局写回玩家私有实体、关系和世界后果。

完成标准：一条玩家私有剧情线可以跨至少四个节点经历伏笔、发展、冲突和解决；使用同一 Base 的其他玩家不会被同步推进。

### 第四阶段：后台预生成

1. 新增 `dungeon_drafts` 和生成任务。
2. 新增地图节点 `prepare` 接口。
3. 扩展 `start` 接口支持领取草稿。
4. 增加剧情版本和实体依赖版本校验。
5. 增加同步生成和确定性模板回退。

完成标准：草稿有效时，点击开始不再等待完整秘境蓝图生成。

### 第五阶段：单层分支预测

1. 新增 `dungeon_branch_drafts`。
2. 当前场景返回后，后台预测各选项下一幕。
3. 玩家选择时按版本原子领取。
4. 战斗选项采用战后生成规则。
5. 增加队列限流和草稿取消。

完成标准：大部分非战斗选项点击后能够直接进入下一幕，同时未选择分支不会造成状态写入。

### 第六阶段：检索与运维增强

1. 根据真实记忆规模决定是否引入 pgvector。
2. 增加管理员剧情框架、玩家记忆与异常节点查看工具。
3. 增加旧记忆章节压缩。
4. 增加剧情质量、重复率、矛盾率和跨角色隔离监控。
5. 根据分支分布调整 Base，避免某个选项或结局长期占据绝大多数实例。

## 20. 第一版推荐范围

第一版建议只实现：

```text
两至三种版本化共享剧情 Base
+ 玩家私有剧情状态和生成种子
+ 永久剧情记忆
+ NPC / 地点权威状态
+ 最多三条活跃剧情线
+ 结构化相关记忆检索
+ StoryIntent 与信件、NPC、云游、任务、秘境投递
+ 挂机重大选择等待玩家处理
+ 秘境蓝图
+ 地图选中后的后台预生成
+ 无草稿时同步回退
```

暂时不实现：

```text
向量数据库
完整分支树
多玩家共享并共同修改同一个剧情世界
无限制的运行时 Base 自动创作
复杂多模型路由
跨机器分布式 KV Cache
```

这套最小范围已经能够做到：全服共享规则和可维护的剧情骨架，但每个角色拥有独立的人物、关系、伏笔、选择、后果和结局；同一条个人剧情可以跨玩法持续发展，而不是被限制在云游或秘境模块中。
