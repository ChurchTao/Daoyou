# 结伴讨伐（首版）

## 玩法规则

- 地图出现限时讨伐目标，覆盖金丹、元婴、化神、炼虚、合体、大乘、渡劫。系统频道发布传闻，点击「前往查看」进入对应地图与组队抽屉；地图头像也可打开组队。
- 创建队伍时指定最低与最高境界，范围必须包含队长。支持队伍列表加入、快速匹配已有队伍；快速匹配优先补齐人数较多的合适队伍。
- 每队 2～4 名不同账号的玩家，不要求满员。全员准备后队长开战；成员变化会清除准备，队长离开后自动由剩余成员接任。
- 出现期间各队分别挑战，战斗实例、血量互相独立。失败可重试，队伍在结算后保留并清除准备。
- 每个角色每次出现仅首次胜利发奖。已领奖角色可作为队长或队员助战、计入开战人数，不重复获得奖励，也不影响其他角色的领奖资格。
- 到期停止招募和新开战，旧链接展示「此处异动已平息」。到期前已开始的战斗继续完成并正常结算。

## 首版默认值

这些是本次实现的初始配置，尚未经过正式数值平衡验收。

- 每两小时一轮，各境界同时出现一个目标，共七个；八个 BOSS 类型随轮次轮换，每个境界八轮内遍历全部类型，地点目前固定。
- 每个目标采用对应境界中期等级。首次胜利的修为、灵石、感悟复用 BOSS 境界中期挂机历练 6 小时的计算器，保留随机浮动，每位角色独立抽取；不消费实际挂机时长。
- 通用掉落配置在 `src/shared/rewards/data/hunt.json`：保底 2 件 `material.v1`，品质按 BOSS 境界沿用副本分布；独立 20% 概率掉落 1 枚传承灵印、20% 概率掉落 1 瓶归元灵露。灵印池 version 2 显式配置当前开放的 67 种技能（普通 34 种、上品 33 种），每种普通权重 4、上品权重 1；有奖励资格的单次胜利掉落上品灵印的概率约 3.91%。灵露池普通／上品权重为 3:1。这些数量和概率为本次初始默认值。
- 基础资源直接入账，遵循现有上限，结算页显示实际增量；道具通过奖励邮件送达，领取进入统一库存，背包满不阻塞战斗结算。
- 使用满气血、满法力的隔离战斗快照，不扣持久气血、法力或灵兽寿命。
- 每场敌方固定 8 个单位：1 个 BOSS、1 个精英、6 个小怪（4 个近战、2 个术士）。双生冥虎的另一只虎占精英位；噬灵邪修的护法占精英位。小怪气血、攻击与防御低于精英。
- 敌方气血按人数增长，但小于等比例增长，增加队友仍有战力收益。
- 复用已注册头像，尚未新增专属 BOSS 立绘。
- 地图每 15 秒更新事件、组队页每 5 秒更新队伍；服务端严格检查到期时间，客户端显示可能有轮询延迟。

## 八类目标

| 目标     | 机制                               | 合作应对                     |
| -------- | ---------------------------------- | ---------------------------- |
| 噬灵邪修 | 护法为受伤的邪修恢复气血           | 封印或优先击杀护法           |
| 六目古魔 | 魔眼标记玩家，下一回合发动物理重击 | 被标记者防御，队友保护或救援 |
| 双生冥虎 | 交替给同伴施加物理、法术减伤护体   | 驱散或转火                   |
| 血河妖蟒 | 气血极高，防御普通                 | 先清随从，集中输出，兼顾续航 |
| 铁背玄鼋 | 物防极高，法防较低                 | 法术主攻，物理清理随从       |
| 吞霞灵蟾 | 法防极高，物防较低，擅用妖焰       | 物理主攻                    |
| 金身尸王 | 双防极高，气血较少                 | 固定伤害、破防              |
| 掠影妖貂 | 闪避极高，速度较快                 | 法术或必中攻击              |

数值仍为待平衡的初值：BOSS／精英／小怪分别按预设遭遇预算的 1/2、1/4、1/12 取气血与攻击，全部气血乘以 `1.8 + (人数 - 2) × 0.65`；小怪双防为普通预设的 65%。血河妖蟒气血为常规 BOSS 的 3.5 倍；铁背玄鼋物防 6 倍、法防 0.6 倍，吞霞灵蟾相反；金身尸王双防 6 倍、气血 25%；掠影妖貂闪避为预设命中加等级 × 6，速度 1.3 倍。

这些特性遵循现有 V6 公式：高防不等于免伤，物理命中下限为 45%，法术和必中招式不受该闪避影响，固定伤害不受双防影响。小怪轮流选择玩家为目标；双虎护体只给另一只虎施加，同伴阵亡后不会转给小怪。

内容位于 `src/shared/engine/combat-v6/hunts/content.ts`，不修改 V6 核心。出现与招募规则位于 `src/shared/hunts`。

## 状态与结算边界

- 出现 ID 由版本、轮次与境界确定，所有实例生成相同 ID。新增八类目标使用 `hunt-v2`；`hunt-v1` 仍按原三类映射解析，避免旧传闻和已建队伍的目标被重新解释。切换版本的当轮，新旧出现各自保持独立领奖资格；已经创建的战局沿用冻结阵容，新开战使用八人敌阵。传闻使用确定性消息 ID 与 Redis 去重标记。
- Redis 保存队伍、账号归属、事件索引，短期互斥锁配合 Lua revision 检查原子更新。当前实现的队伍互斥锁是全局锁，尚未做高并发容量验收。
- 开战重新读取成员归属、活跃状态和境界，在现有角色变更锁内构建快照，复用 V6 Redis 战斗占用。Lua 创建战局时再次使用 Redis 时间检查到期边界。
- 开战请求使用冻结阵容和 `startRequestId` 恢复，响应丢失不会重复创建战局；旧结算事件不会清除新一场战斗的队伍状态。
- 开战时冻结每人资源与完整物品事实快照，随机流由出现 ID、角色 ID、池版本和组名隔离。材料库读取沿用同一数据库事务；缺少本境界品质范围内的材料时拒绝开战，不用越界品质填充保底。
- 终局沿现有 NATS 消息设施投递，先归档可回放的 `hunt` 战绩，再由 `HuntRewardProjector` 结算。数据库消费回执、修仙日志领奖凭据、三项资源变更和道具邮件在同一事务内提交。结算重试不重抽、不多发邮件。
- 修仙日志以 `(cultivator_id, hunt_reward:{event_id})` 唯一键承接首次胜利领奖资格，不能使用战斗 ID 作为去重键。助战资格、队伍列表和战果查询统一读取该凭据；私有 `result` 保存首次获奖战斗 ID、实际奖励快照和邮件 ID，不通过日志列表返回。即使资源受上限裁剪为零，也保留凭据；助战和失败不新增收入日志。重复消息和重复胜利均不能重复加款或寄信；事务完成后清理队伍战斗状态、释放占用并确认终局。
- 日志记录直接到账的灵石、修为、感悟，地点和目标作为简短上下文；邮件里的物品实际领取时再计入道具收入。消息消费回执继续负责战局缓存过期后的重投识别。
- 新接口统一位于 `/api/hunts`，沿用登录和活跃角色中间件，参数在服务端校验；奖励金额与目标由服务端生成。
