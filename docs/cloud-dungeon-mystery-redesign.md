# 云游探秘重构：剧本杀式解谜副本设计

状态：设计已确认（2026-11-02），第 15 节各项按“建议默认”拍板；实施进度见第 17 节。后续开发路线见 [cloud-dungeon-roadmap.md](cloud-dungeon-roadmap.md)，上线前事项见 [cloud-dungeon-launch-checklist.md](cloud-dungeon-launch-checklist.md)。

## 1. 一句话

开局为玩家生成一份**有确定真相的案卷**，玩家以剧中角色身份进入地图节点场景，通过移动、搜查、对话、出示证据、使用物品和战斗逼近真相，最后结案推理；**评分由规则计算**，按评分发放奖励。LLM 负责“把案卷写活”和“演 NPC”，不负责“决定发生了什么”或“决定给多少”。

## 2. 现状梳理

### 2.1 当前流程

| 环节 | 实现 | 入口 |
| --- | --- | --- |
| 入口 | 31 个带 `dungeon_config` 的卫星节点；节点只有名称、标签、一句描述和难度档 | `packages/game-content/src/world/data/map.json` |
| 入场 | 预扣气（`dungeon_start`），同一角色仅一个活动副本，副本期间占用构筑 | `DungeonFlowService.startDungeonUnlocked`、`dungeon/occupancy.ts` |

| 前端 | 场景状态包括 `map_selection / exploring / battle_preparation / in_battle / looting / settlement` | `apps/web/src/routes/game/dungeon/**` |

### 2.2 问题与根因

| 玩家感受 | 根因 |
| --- | --- |
| 慢 | 每一步都要等一次完整的长文本加结构化 JSON 生成，不存在不经过 LLM 就能完成的操作 |
| 读了没用，不看字直接选 | 没有隐藏真相，也没有需要解答的问题；LLM 每轮凭最近 4 轮历史即兴编写，文本里的信息不影响结果 |
| 选项可预测 | 风险顺序固定，选项本质是代价菜单，最优解很快被摸透 |
| 没有空间感 | 5 轮线性推进，不能回头，也不能自选去哪里、查什么 |
| 不知道怎么拿高分 | 评级由 LLM 凭印象给出，和玩家行为之间没有可解释的关系 |

结论：问题出在结构上，不在文笔。只优化 prompt 无法解决。

## 3. 目标与非目标

**目标**

1. 阅读文本能带来收益：信息直接决定结案正确率和评分。
2. 玩家能主动做选择：自选地点、对象、提问内容和出示的证据，不再是三选一。
3. 大部分操作即时响应；只有 NPC 对话和自由行动需要 LLM，并且流式输出、篇幅短。
4. 评分可解释、可复现，奖励完全由服务端规则决定。
5. 地图节点通过配置扩展剧本，内容生产可持续。

**非目标（首版）**

- 多人同局、玩家之间互相扮演角色。
- 完全由 LLM 自由生成谜题结构（见 5.1）。
- 新增战斗机制；战斗沿用 V6。
- 改动气的经济体系、背包或掉落底座。

## 4. 核心概念

| 概念 | 说明 | 谁可见 |
| --- | --- | --- |
| 剧本模板 Scenario Template | 人工编写的谜题骨架：类型、规模、结案问题、评分细则、可插入的槽位 | 仅服务端 |
| 案卷 Case File | 开局由 LLM 按模板填充、经规则校验后的完整隐藏真相 | 仅服务端 |
| 角色本 Role Brief | 从案卷中投影出的玩家身份、目的、已知关系和开场背景 | 玩家 |
| 运行态 Run State | 位置、已获线索、局内物品、NPC 态度、剧情标记、行动力、对话记录 | 服务端权威，玩家只看到投影 |
| 笔记本 Notebook | 已获线索、证词、人物关系的自动归档，是运行态的玩家投影 | 玩家 |
| 结案 Deduction | 回答模板定义的结案问题 | 玩家提交，规则评分 |

真相与叙事分离：**案卷在开局时一次性确定**，运行时的一切反馈都只是“揭示案卷的一部分”，或者“按白名单改变运行态”。

## 5. 内容配置

### 5.1 为什么要人工编写骨架

纯 LLM 生成的谜题常见问题：关键线索放不下来、获取条件形成循环、真相与线索矛盾、难度失控。所以骨架（谜题结构、结案问题、评分细则）由人工编写，LLM 只填充人物、地点、物件和文字。这样既有可玩性的下限，又保留了每局的新鲜感。

### 5.2 剧本模板（`game-content`，新增）

建议位置：`packages/game-content/src/dungeon/scenarios/*.json`，配套 Zod 校验，并通过 `game-content/authoring` 的内容校验测试。

```jsonc
{
  "id": "inheritance_murder",
  "name": "遗府疑案",
  "archetype": "whodunit", // whodunit | unlock | retrieval | allegiance
  "fits_tags": ["坐化遗骸", "古修士洞府", "宗门"],
  "scale": {
    "rooms": [4, 6],
    "npcs": [2, 4],
    "key_clues": [4, 6], // 结案所需的关键线索
    "red_herrings": [1, 3], // 误导线索
    "action_budget": 24, // 行动力，见 7.2
  },
  "roles": [
    // 角色槽位，LLM 负责命名和赋予性格
    { "slot": "culprit", "count": 1, "lies": true },
    { "slot": "witness", "count": [1, 2] },
    { "slot": "heir", "count": [0, 1] },
  ],
  "questions": [
    // 结案问题，答案类型决定判分方式
    { "id": "who", "prompt": "谁是凶手", "answer_kind": "npc" },
    { "id": "how", "prompt": "用了什么手段", "answer_kind": "clue" },
    { "id": "seal", "prompt": "禁制应交给谁开启", "answer_kind": "npc" },
  ],
  "combat_slots": [
    // 可插入的战斗位置，敌人等级由节点难度决定
    { "id": "guardian", "trigger": "enter_room", "optional": true },
    { "id": "culprit_exposed", "trigger": "accuse_correct", "boss": true },
  ],
  "endings": ["truth_revealed", "culprit_escaped", "wrong_accusation"],
  "scoring": {
    "truth": 50,
    "coverage": 15,
    "efficiency": 15,
    "branch": 10,
    "combat": 10,
  },
}
```

首版建议写 3–5 个模板，覆盖四种原型：

- **whodunit**：找出真凶及作案手段。
- **unlock**：凑齐条件，开启封印或机关。
- **retrieval**：推断遗宝或失物的下落。
- **allegiance**：在两派之间看清真相，选择立场。

### 5.3 地图节点配置增强

在现有 `dungeon_config` 上扩展，原字段保持不变：

```jsonc
"dungeon_config": {
  "difficulty": "normal",
  "scenario": {
    "templates": ["inheritance_murder", "sealed_formation"],  // 可抽取的模板
    "setting": "瀑布后的古修士洞府，禁制残破",                    // 场景基调，喂给生成
    "factions": ["散修", "古修士后人"],
    "fixed_npcs": [],                   // 可选：节点固定出场的人物，用于跨局世界观
    "forbidden": ["现代器物"]           // 生成禁忌
  }
}
```

没有配置 `scenario` 的节点，按 `tags` 匹配模板的 `fits_tags` 兜底，保证 31 个节点首版都能开局。

## 6. 案卷生成与校验

### 6.1 案卷结构（`game-domain/dungeon`，新增）

```ts
interface CaseFile {
  templateId: string;
  truth: string; // 真相全文，仅用于生成 NPC 回复和结局叙事
  brief: RoleBrief; // 玩家角色本
  rooms: Room[]; // id、名称、描写、相邻房间、物件、进入条件
  objects: CaseObject[]; // id、所在房间、简述、细看描写、可交互动作
  clues: Clue[]; // id、名称、正文、是否关键、能证明什么、获取方式
  npcs: NpcCard[]; // 见 8.1
  items: RunItem[]; // 局内物品（钥匙、残页、符箓），不进背包
  interactions: Interaction[]; // (动作, 物品?, 目标) → 效果[]，效果来自白名单
  encounters: Encounter[]; // 对应模板 combat_slots，敌人参数由规则校准
  answers: Record<string, string>; // 结案问题标准答案（npc id / clue id / 选项 id）
  endings: Ending[]; // 结局条件与结局基调
}

type ClueSource =
  | { kind: 'search'; objectId: string; requires?: Condition }
  | { kind: 'dialogue'; npcId: string; requires: Condition }
  | { kind: 'interaction'; interactionId: string };

type Effect =
  // 白名单，运行时唯一能改变状态的方式
  | { kind: 'reveal_clue'; clueId: string }
  | { kind: 'grant_item'; itemId: string }
  | { kind: 'consume_item'; itemId: string }
  | { kind: 'unlock_room'; roomId: string }
  | { kind: 'set_flag'; flag: string }
  | { kind: 'npc_attitude'; npcId: string; delta: number }
  | { kind: 'start_encounter'; encounterId: string }
  | { kind: 'spend_action'; amount: number };
```

`Condition` 由 `has_clue / has_item / flag / attitude_gte / room_visited` 组合而成，只允许 `all / any` 两层嵌套。

### 6.2 生成流程

结构由程序决定，LLM 只写文字（2026-11-02 由“一次性整份生成”改为三段式，原因见第 17 节）：

1. **选择模板**：从节点的 `scenario.templates` 中按种子抽取，种子写入运行态。
2. **程序生成骨架**（`buildMysterySkeleton`，纯函数）：按模板原型与种子确定房间连通、物件位置、线索获取链、锁与钥匙、谎言与戳穿证据、结案答案，并为每个元素附上“作用”说明。每份骨架在生成时即可解。当前只实现了 whodunit 原型，该原型约定身份槽位 `culprit/heir/witness` 与问题 `who/how/heir`。
3. **LLM 起名与真相**（一次调用，约 10 秒）：结构化输出的键就是骨架里的 id，模型只能逐一填写名称，无法增删元素或写错引用。
4. **LLM 填写正文**（三次并行调用：场所、物证、人物）：同样以骨架 id 为固定键，参考上一步的名称与真相。
5. **组装与清理**：去掉偶尔带出的内部 id、英文单词与 Markdown 标记，超长截断。凶手的谎言原话由程序统一渲染到线索与台词中。敌人相关的规则校准留到战斗槽位接入时再做。
6. **一致性审校**（最多两轮）：模型对照事实设定（canon）找出正文之间的矛盾，先写理由、再给 `confirmed` 判断，只改写确认有问题的字段；有修正时再审一轮。
7. **可解性校验**（`game-rules`，纯函数，带单元测试）：
   - 结构：房间连通，物件、线索、NPC 的引用全部存在，数量在模板范围内。
   - 可达性：从初始状态出发，按条件图做不动点推演，所有关键线索都能获得，所有结案标准答案都有至少一条关键线索支撑。
   - 无循环：线索获取条件之间不存在互相依赖。
   - 预算：估算的最短通关行动数 ≤ 预算 × 0.75，确保有容错空间（估算会把每个相关物件、人物和交互各计一次，偏保守）。
   - 安全：文本通过现有文本过滤，不得出现节点的 `forbidden` 内容。
8. 任一段调用失败先重试该段一次；仍失败或校验不通过时回退到该模板的手写保底案卷（案卷池完成后先取池中的备用案卷）。

## 7. 运行时模型

### 7.1 运行态

```ts
interface MysteryRunState {
  runId: string;
  caseRef: { poolId?: string; seed: number };
  location: string; // 当前房间
  visitedRooms: string[];
  searchedObjects: string[];
  clues: string[]; // 已获线索 id
  items: string[]; // 持有的局内物品
  flags: string[];
  npcAttitude: Record<string, number>; // -100..100
  dialogue: Record<string, DialogueTurn[]>; // 每个 NPC 保留最近 K 轮，更早的压缩为摘要
  actionsLeft: number;
  encounterResults: Record<string, 'won' | 'lost' | 'fled' | 'avoided'>;
  phase:
    | 'briefing'
    | 'investigating'
    | 'in_battle'
    | 'deducing'
    | 'settling'
    | 'finished';
}
```

案卷与运行态一起存入 `dungeon_runs.run_state`（沿用权威表）；案卷体积较大时拆到 `case_snapshot` 列。Redis 仍然只做缓存。

### 7.2 行动力

- 移动 1、搜查物件 1、对话每轮 1、使用物品 1、细看已搜过的物件 0、翻阅笔记本 0。
- 行动力耗尽后强制进入结案，没收集到的线索就此作罢。
- 作用：让盲点乱试变得有代价，同时给评分提供“效率”维度。
- 行动力不消耗气血、灵石等真实资源；真实资源只在入场（气）和战斗中消耗。这是对旧版“选项扣资源”的有意删除，目的是让玩家敢于探索。

### 7.3 交互动作

| 动作 | 请求 | 处理 | LLM |
| --- | --- | --- | --- |
| `move` | 目标房间 id | 检查相邻关系和进入条件，返回房间描写和物件列表 | 否 |
| `search` | 物件 id | 返回细看描写；满足条件时获得线索或物品 | 否 |
| `use` | 物品 id + 目标（物件或 NPC） | 查交互表，命中则执行效果；未命中返回模板化的“无事发生”文案 | 否 |
| `talk` | NPC id + 自由文本（限 80 字） | 见 8.1 | 是，流式 |
| `present` | NPC id + 线索或物品 id | 先查 NPC 卡上的 `reactions`，命中则执行确定性效果，再由 LLM 写台词 | 是，流式 |
| `attempt` | 自由文本（限 60 字） | 见 8.2，首版可不开放 | 是 |
| `fight` | 遭遇 id | 进入 V6 战斗，结果写回 `encounterResults` 和标记 | 否 |
| `deduce` | 结案问题的答案 | 规则判分，见 9 | 否 |

所有动作带 `actionId` 做幂等处理（沿用现有 `pendingAction` 和账本思路），并带 `version` 做乐观锁。

## 8. LLM 在运行时的职责

### 8.1 NPC 对话

**NPC 卡**（案卷的一部分）：

```ts
interface NpcCard {
  id: string;
  name: string;
  role: string; // 角色槽位
  persona: string; // 性格、口吻、说话习惯
  publicStance: string; // 对外说法
  knows: string[]; // 知道的事实（自然语言）
  secrets: { clueId: string; revealWhen: Condition }[];
  lies: { topic: string; claim: string; contradictedBy: string[] }[];
  reactions: {
    trigger: { present: string };
    effects: Effect[];
    hint: string;
  }[];
}
```

**每轮流程**：

1. 服务端算出这一轮**允许透露的线索集合** = 该 NPC 的 `secrets` 中 `revealWhen` 已满足的部分。
2. LLM 输入：NPC 卡（去掉 `revealWhen` 的具体条件）、允许透露的线索、玩家已出示的证据、最近 K 轮对话、玩家本轮发言。
3. LLM 输出：`{ reply: string(≤180 字), reveal: clueId[], attitudeDelta: -10..10 }`。回复文本流式下发。
4. 服务端裁剪：`reveal` 只保留允许集合内的 id，`attitudeDelta` 截断到范围内。

所以玩家无法靠话术诱导 LLM 泄露未解锁的线索，最多只能让 NPC 态度略有变化。

**说谎与戳穿**：NPC 会按 `lies` 坚持错误的说法；玩家 `present` 了 `contradictedBy` 中的线索时，`reactions` 确定性地触发“破绽”效果（设置标记、可能解锁新的秘密），LLM 只负责把 NPC 的慌乱写出来。这是本玩法的高光时刻，UI 上需要强化表现。

### 8.2 自由尝试（可选）

玩家写“用火符烧掉藤蔓”。LLM 作为裁判，从**当前房间可用的交互**中选择一个匹配项或判定无效，输出 `{ interactionId | null, narration }`，服务端只执行被选中交互的白名单效果。首版建议不开放，先观察 `use` 能否覆盖大部分需求。

### 8.3 叙事润色

房间和物件的描写在生成案卷时已经写好，运行时不再调用 LLM。结局叙事在结算时调用一次，输入是真相、玩家答案和关键事件，只写文字，不给评级。

### 8.4 Prompt 与调用

- 新增 prompt：`dungeon-case.md`（生成案卷）、`dungeon-npc.md`（对话）、`dungeon-epilogue.md`（结局）；可选 `dungeon-attempt.md`。
- 统一走 `apps/api/src/utils/aiClient.ts`；流式对话使用 `streamAiText`，结构化部分（`reveal`、`attitudeDelta`）放在流结束后的尾部 JSON 中，或改为“先结构化、后流式”两段输出，实施时二选一，以首字延迟为准。
- 记录 `sceneId` 指标，接入现有 LLM 指标后台。

## 9. 结案与评分

### 9.1 结案

- 玩家随时可以主动结案；行动力耗尽时强制结案。
- 每个结案问题按 `answer_kind` 作答：选择 NPC、选择已获得的线索、选择预设选项。**只能从已经获得的线索中选择**，所以没找到线索就答不出“手段”。
- 正确指认真凶且模板有战斗权重时，真凶负隅顽抗，进入对决；见第 17 节“结案对决”。

### 9.2 评分（`game-rules`，纯函数）

```
truth      = Σ 答对的结案问题权重              （模板 scoring.truth 分配）
coverage   = 已获关键线索数 / 关键线索总数      × scoring.coverage
efficiency = clamp(剩余行动力 / 预算 × 2, 0, 1) × scoring.efficiency
branch     = 达成的结局分支加分（救下 NPC、识破全部谎言等，模板定义）
combat     = 对决结果：擒下 1 / 落败、逃跑或任其遁走 0 / 未指认真凶 0   × scoring.combat
总分 0–100 → S ≥ 90，A ≥ 75，B ≥ 60，C ≥ 40，其余为 D
```

- 评分明细完整展示给玩家（“真相 40/50，漏了 1 条关键线索……”），让玩家知道下次怎么改进。
- 中途放弃：按已获线索计算 coverage，truth 记 0，最高 D。

### 9.3 奖励

- **沿用现有底座**：`resolveDungeonReward` 的种子掉落、`RewardFactory.generateBaseRewards`、难度系数、背包发放、账本防重全部保留。
- **唯一的改变**：`RewardFactory` 的评级输入从“LLM 评级”换成“规则评分”。
- 探索掉落的时机从“每轮”改为“获得关键线索 / 开启特定物件时”，掉落键形如 `clue:<id>`，仍由种子和配置确定。
- 战斗掉落沿用 `battle:<id>`。

## 16. 示例：太岳山·无名古修士洞府

- **角色本**：你受散修韩老三之托，前来替他取回亡兄的遗物。同行的少女苏晚自称洞府主人的后人。
- **真相**（隐藏）：古修士死于弟子之手，那名弟子化名韩老三，想借你之手破开最后一道禁制；苏晚才是真正的后人。
- **房间**：瀑布洞口 → 石室（遗骸）→ 丹房（弟子名册）→ 静室（禁制）→ 暗道（需要钥匙）。
- **关键线索**：遗骸指骨上刻着半个“韩”字；名册被撕掉的一页（藏在丹炉灰中，需要先“使用”拨火钳）；苏晚的家族口传（向她出示指骨刻痕后解锁）；韩老三对“亡兄死于何年”的说法与名册矛盾（出示名册残页即可戳穿）。
- **误导线索**：洞口新鲜的妖兽爪痕（指向守洞妖兽，与命案无关）。
- **结案**：谁杀了古修士 → 韩老三；手段 → 丹房毒烟（线索：炉灰中的残毒）；禁制交给谁 → 苏晚。
- **分支**：指认正确时韩老三暴起，触发 BOSS 战；指认错误时禁制被他夺走，只能拿到基础分。

## 18. 剧本库与惰性生成

状态：已实现（2026-11-02），按 18.10 默认值；重温不限制收益（见 18.8）。

### 18.1 目标

- **开局零等待**：开局只从全服剧本库选本，不在请求链路上调用 LLM。
- **按需生成、全服共享**：只有玩家真的在玩、且某节点的剧本快被玩完时才生成；生成一次，全服所有玩家都能用。
- **成本有上限**：待生成队列全服最多 5 个，超出的请求直接忽略；另有每个节点的库存上限与失败退避。
- **玩完不断档**：玩家把某节点的本都玩过后先玩旧本，同时触发补货。

### 18.2 概念

| 概念 | 说明 |
| --- | --- |
| 剧本（scenario） | 一份已校验的案卷，绑定一个地图节点与一个剧本模板，全服通用 |
| 剧本槽（slot） | “节点 × 模板”，例如“太岳山洞府 × 遗府疑案”；库存与生成都按槽计算 |
| 游玩记录（play） | 某角色玩过某剧本，开局即记录 |
| 生成任务（job） | 为某个槽生成一份新剧本的请求；数据库表即队列 |

一个节点在 `dungeon_config.scenario.templates` 中可以配置多种剧情模板，每个模板就是一个槽。

### 18.3 数据表

**`wanjiedaoyou_dungeon_scenarios`（剧本库）**

| 字段 | 说明 |
| --- | --- |
| `id` | uuid |
| `map_node_id`、`template_id` | 所属槽，联合索引 `(map_node_id, template_id, status)` |
| `case_file` | jsonb，完整案卷（含真相），只在服务端读取 |
| `title` | 冗余标题，便于后台查看 |
| `source` | `generated`（生成）或 `seed`（手写保底案卷入库） |
| `generator_version` | 骨架与生成流水线版本；不兼容时可整批停用 |
| `status` | `active` / `retired` |
| `review_issue_count` | 生成时审校修正的问题数，留作质量参考 |
| `generation` | jsonb：耗时、用到的模型路由、种子 |
| `play_count`、`completion_count`、`score_sum` | 游玩统计，结算时累加 |
| `created_at` | 时间 |

**`wanjiedaoyou_dungeon_scenario_plays`（游玩记录）**

| 字段 | 说明 |
| --- | --- |
| `cultivator_id`、`scenario_id` | 联合唯一 |
| `map_node_id`、`template_id` | 冗余，便于按槽查询“玩过哪些” |
| `first_played_at`、`last_played_at`、`play_count` | 开局时写入或累加 |
| `best_total`、`completed` | 结案时更新 |

**`wanjiedaoyou_dungeon_scenario_jobs`（生成任务，即队列）**

| 字段 | 说明 |
| --- | --- |
| `id` | uuid |
| `map_node_id`、`template_id` | 目标槽 |
| `status` | `queued` / `running` / `succeeded` / `failed` |
| `reason` | `exhausted`（有人玩完了）/ `low_stock`（快玩完）/ `cold_start` / `warmup` / `admin` |
| `requested_by` | 触发的角色，可空 |
| `attempts`、`error` | 重试次数与最后一次错误 |
| `scenario_id` | 成功后生成的剧本 |
| `created_at`、`started_at`、`finished_at` | 时间 |

部分唯一索引 `(map_node_id, template_id) WHERE status IN ('queued','running')`：同一个槽同时只能有一个待生成任务，重复投递在数据库层面就被挡掉。

### 18.4 开局选本

```
开局（只读库，不调用 LLM）
  1. 读取节点配置的模板列表 → 得到该节点的所有槽
  2. 读取各槽的 active 剧本，以及该角色在这些剧本上的游玩记录
  3. 选槽：优先选“该角色还有未玩剧本”的槽；多个时选该角色玩得最少的模板，保证玩法轮换
  4. 选本：
     - 有未玩剧本 → 选其中全服游玩次数最少的（让新本尽快被验证），同分随机
     - 都玩过 → 选该角色最久没玩的那本，标记为“重温”
     - 槽内一本都没有 → 见 18.7 冷启动
  5. 写入游玩记录；运行态记录 scenarioId 与是否重温
  6. 判断是否需要补货（18.5），需要则投递生成任务；投递失败或被忽略都不影响本次开局
```

### 18.5 补货触发与队列限流

**触发条件**（对本次选中的槽判断，开局后执行）：

- 该角色在此槽的剩余未玩剧本 ≤ 1（`LOW_STOCK_THRESHOLD`）：快玩完了，提前补一本；
- 或本次已是“重温”：已经玩完，必须补。

**投递规则**（单个事务，用 `pg_advisory_xact_lock` 串行化投递，避免并发计数不准）：

1. 该槽 active 剧本数已达库存上限（建议 30 本）→ 不投递，该槽之后只轮换旧本；
2. 该槽最近一次失败距今不足退避时间（建议 30 分钟）→ 不投递；
3. 该槽已有 `queued`/`running` 任务 → 不投递（部分唯一索引兜底）；
4. 全服 `queued`+`running` 任务数 ≥ 5（`MAX_PENDING_JOBS`）→ **忽略本次投递**；
5. 否则插入一条 `queued` 任务，并发出一次唤醒（18.6）。

全服上限 5 正好对应“生成一本后大家都能用”：被忽略的请求不需要排队，后来的玩家再触发时自然会重新投递。

### 18.6 异步生成

沿用现有后台命令设施，**数据库表是队列，NATS 只负责敲门**：

- 新增后台命令 `dungeon-scenario.generate`。现有后台命令不带参数、按时间桶去重，正好用作“去处理队列”的唤醒信号；去重桶设为 30 秒，短时间内多次投递只唤醒一次。
- 定时任务每 5 分钟也发一次同样的唤醒，兜底处理漏掉的唤醒与卡住的任务。
- 处理器循环认领任务：`UPDATE … SET status='running' WHERE id = (SELECT id … WHERE status='queued' ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1)`，多实例部署时也不会重复认领。
- 每个实例同时只跑 1 个生成（每本约 45 秒、5–8 次 LLM 调用），控制瞬时并发与费用。
- 生成：调用现有三段式流水线，**去掉玩家个人信息**（剧本全服共享，角色本只用第二人称“你”），种子随机。只有 `source = generated` 且通过结构与可解性校验的案卷才入库；退回保底案卷视为失败。
- 成功：插入剧本，任务标记 `succeeded` 并记录 `scenario_id`。失败：`attempts + 1`，未满 3 次回到 `queued`，否则标记 `failed` 并开始该槽的退避计时。
- 兜底清扫：`running` 超过 10 分钟（实例崩溃等）视为中断，按失败处理一次。

### 18.7 冷启动与保底

- **上线预热**：发布时投递 `warmup` 任务，为每个已配置剧本的槽各生成 2 本（受全服队列上限约束，分批完成）。
- **手写保底案卷入库**：模板自带的保底案卷以 `source = seed` 写入对应节点的槽（只限案卷场景与节点匹配的槽，例如太岳山洞府），作为最后一道底。
- **槽内一本都没有时**：投递 `cold_start` 任务；本次开局退回实时生成（即当前行为，约 45 秒），生成成功的案卷同时入库，下一个玩家即可直接用。预热完成后这条路径基本不会走到。

### 18.8 重温

2026-11-02 拍板：重温与首次游玩**走同一结算路径，不限制收益**。重温标记只用于两处：

- 开局在调查界面提示“此案你已经历过”；
- 剧本统计只累计非重温的结案，避免重温的高分拉高平均分、影响自动停用判断。

### 18.9 质量与运营

- 结算时累加剧本的游玩、完成次数与得分，用于发现问题本：例如游玩 20 次以上、完成率低于 20% 或平均分过低的剧本自动 `retired`。
- `generator_version` 变化（骨架或引擎不兼容）时可整批停用旧本；读取剧本时再走一遍 `MysteryCaseFileSchema` 与 `validateMysteryCase`，不通过就停用并跳过。
- 后台后续可提供剧本列表、预览、停用与手动补货（`admin` 任务）。
- 观测指标：各槽库存、队列长度、被忽略的投递次数、生成成功率与耗时、LLM 用量（已有 `LLM_METRICS`）。

## 19. 第二种案型：遗珍寻踪（retrieval）

### 19.1 为什么是它

- 现有唯一案型“遗产谋杀案”的核心是**指认人**；第二种案型换成**找东西、开禁制**，玩家的注意力从“谁在说谎”转到“哪条线索是真的路”，与前者拉开差异。
- 天南多数解谜候选节点的设定是遗迹、禁制、宝库，天然适合寻宝：
  - `SAT_TN_02` 云梦山·崩塌的上古宗门（金丹）：残魂、多重禁制；
  - `SAT_YW_01` 元武国·天星宗旧阵库（筑基）：阵旗残卷、傀儡守卫；
  - `SAT_LX_02` 深海·沉船遗迹（筑基）：禁制宝箱、海兽袭击。
- 同时引入**调查中途的守卫战**：战斗不只在结尾出现，线索可以帮玩家绕开或削弱守卫。

### 19.2 故事骨架

一位前辈把一件遗珍封存在遗迹深处。此刻遗迹中有几拨人：

| 身份槽 | 说明 | 说谎 |
| --- | --- | --- |
| `rival` 夺宝者 | 也在找遗珍，暗中布下假线索把旁人引向错误地点，想独吞 | 是 |
| `owner` 应得之人 | 遗珍真正该交付的人（前辈的后人、弟子或遗愿所指） | 否，但不轻易交底 |
| `decoy` 被误导者 | 被夺宝者的假线索骗了，真诚地相信错误的地点，替假线索作证 | 否 |
| `keeper` 守遗者（0–1） | 残魂、器灵或老仆，知道开禁的法门，需要满足条件才会告知 | 否 |

结案（即“开启秘藏”）三问：

| 问题 | 形式 | 答案来源 |
| --- | --- | --- |
| `where` 遗珍藏在何处 | 四选一：真藏处、夺宝者的假藏处、传闻所指、另一处看似合理的地方 | 前辈留下的遗迹线索相互印证，并识破夺宝者的假线索 |
| `how` 如何破开禁制 | 四选一：真法门、照搬假线索的法门、蛮力破禁、另一种误判 | 禁制铭文 + 守遗者或应得之人提供的关键一环 |
| `owner` 遗珍当归何人 | 选人物 | 信物、遗书或守遗者的证言 |

谜题设计要点（与谋杀案的嫌疑人机制对称）：

- **假线索与反证**：夺宝者伪造的线索（如改刻过的地图、调包的阵旗）确实存在于场景里，看起来指向假藏处；被误导者真心为它作证。玩家要找到能证伪它的痕迹（新刻痕、材质对不上、时间矛盾），向被误导者或夺宝者出示后才会翻转。
- **夺宝者的谎言**：在“来意”或“行踪”上说谎（与谋杀案的变体同理），被物证戳穿时计入“识破全部谎言”分支。
- **开禁关键一环**：由守遗者或应得之人掌握，前提条件随种子变化（出示信物、解开某个房间、取得信任）。

### 19.3 守卫：调查中途的战斗

案卷新增 `guards`（每局 0–2 个，种子决定），守住某个房间的入口：

- 玩家移动到被守住的房间时，不直接进入，而是看到守卫的描述和两个选项：
  - **强闯**：消耗 1 点行动力，进入 V6 遭遇战（精英强度，敌人名即守卫名）。胜则守卫退散、进入房间；败或逃跑则退回原房间，守卫仍在，气血损耗保留。
  - **化解**：满足守卫的 `bypass` 条件（持有某件物品、知道口令或某个标记）时可用，消耗 1 点行动力，不战而过。化解所需的线索放在不经过该房间也能拿到的地方，由校验保证。
- 守卫不挡死唯一的必经路线：校验要求即使每个守卫都打不过，也能通过化解进入；即“打得过可以省事，打不过可以动脑”。
- 守卫房间里放的是加分线索或物品，而不是结案必需的唯一线索，避免打不过就必然答错。

### 19.4 结尾对决

沿用谋杀案的对决机制，改为可配置的“谁会翻脸”：

- 模板新增 `finale: { role, when }`。谋杀案为 `{ role: 'culprit', when: ['who'] }`（指认真凶时）；遗珍寻踪为 `{ role: 'rival', when: ['where', 'how'] }`（藏处与法门都答对、秘藏开启时，夺宝者现身抢夺）。
- 答错时秘藏没开，夺宝者不会现身，照常结算。

### 19.5 评分

| 项 | 权重 | 规则 |
| --- | --- | --- |
| 真相 | 45 | 三问答对比例 |
| 线索 | 15 | 关键线索覆盖率 |
| 效率 | 10 | 同谋杀案 |
| 分支 | 10 | 识破全部谎言（5）、翻转被误导者（5） |
| 战斗 | 20 | 结尾对决胜 10；每个守卫以任一方式通过各计一份、合计 10（没有守卫的局这 10 分按满额计） |

“化解”与“强闯获胜”同分：避战靠的是线索，本身就是解谜的回报。

### 19.6 实现落点

1. **通用化骨架框架（重构，不改玩法）**
   - `game-rules/dungeon/mystery/skeleton/`：拆为通用部分（房间图、站位、锁钥、谎言与戳穿、反证、四选一题目、`purposes`）与按案型注册的构造器 `whodunit.ts`、`retrieval.ts`；`buildMysterySkeleton` 按 `template.archetype` 分派。
   - 生成器的大纲字段（canon）、锁定字段、程序渲染的谎言、真相中必须出现的人名，改由案型描述提供；谋杀案的行为保持不变，用现有测试兜底。
   - 剧本库按“模板”分槽，本来就支持多模板，无需改动。
2. **守卫**
   - 领域：`MysteryCaseFile.guards`、动作 `force_guard` / `bypass_guard`、运行态记录已通过的守卫。
   - 规则：移动被守卫拦下的判定、化解条件、可达性校验（化解路线必须存在）、评分。
   - 服务端：强闯复用对决的遭遇战链路，战斗结束后回到探索而不是结算；为此把“对决待定”和“守卫待定”统一为解谜的“待战事件”。
   - 前端：被拦下时的守卫面板（强闯 / 化解 / 回头），迎战页文案区分守卫与真凶。
3. **遗珍寻踪模板与内容**：模板 JSON、一份手写保底案卷、三个节点的场景配置、案型专属的大纲与审校提示词片段。
4. **验证**：300 个种子的结构与可解性校验（含“不打守卫也能解”）；实际生成若干份检查一致性；页面实测守卫的强闯（胜 / 败）与化解、结尾对决。

### 19.7 待拍板（默认值）

- 守卫强度：精英（默认）。
- 守卫战失败：退回原房间、守卫仍在，可再战或去找化解办法（默认）；不因此结束探索。
- 谋杀案是否也加守卫：本轮不加（默认），待遗珍寻踪验证手感后再说。
- 结尾对决强度：与谋杀案一致，首领（默认）。

## 20. 解谜界面方案（路线图阶段 2，2026-11-03 按默认值确认）

目标：玩家不靠记忆管理线索、人物与地形；第一屏只回答“我在哪、出了什么事、这里能做什么”。

### 20.1 分层

- **身份层**：沿用副本壳的场景头（节点名 + 返回洞府），案卷标题降为任务层第一行的上下文，不做第二个标题。
- **任务层（调查主屏）**，自上而下：
  1. 状态行：案卷标题 · 当前地点，右侧行动力（剩余/预算）。
  2. 异动横幅：有预兆未解时常驻，事件发生或被阻止后消失。
  3. 小地图：已知房间连线示意，标出你所在、到访过、上锁、守卫、有人在场；点相邻房间即前往。
  4. 本回合叙事：只显示最近一回合，旧内容移入案情板“经过”页。
  5. 此处：物件（已看过打勾，再看不耗行动力）与在场人物卡（印章头像、称谓、状态标记）。
- **底部操作栏**（拇指区，固定）：地图（窄屏展开大图）、案情板（未读角标）、静思、结案。原来散落的“案卷笔记”“离开”收进案情板菜单与场景头。

### 20.2 案情板

窄屏为底部弹层，宽屏（≥1024px）为常驻右栏。四页：

- **线索**：按来源分组（得自某地点、得自某人），新获得的标“新”；每条可“钉到”某个结案问题。随身物品也在此页，带“使用”。不展示线索与问题的真实对应，钉选完全由玩家判断。
- **人物**：印章头像、称谓、所在地点、状态标记（尚未交谈、已交底、谎言被戳穿、已离场）、最近一句话；交谈与出示从卡片发起。出示时证据按与此人相关程度排序（得自此人或其所在地点的在前）。
- **地点**：大图小地图与各房间已知情况（物件看过几件、在场人物）。
- **经过**：完整日志。

### 20.3 结案

按问题列出玩家钉下的依据，再在下方作答。没有钉选也能直接作答。

### 20.4 数据与实现要点

- 投影补充：线索来源（地点或人物）、人物状态与所在、当前未解的异动预兆、已知房间的连线与标记。全部由服务端投影计算，不下发隐藏真相。
- 钉选：默认存在浏览器本地（按局区分），属于玩家笔记，不影响评分。
- 人物头像：先用姓氏印章（水墨圆章），通用身份立绘作为后续美术任务。
- 移动：小地图只允许点相邻房间；不做多步自动寻路，避免一次点击扣掉多点行动力。
- 等待：开局生成时分阶段提示并显示已用时间；结案后先展示评分，再等结局叙事。
- 规范：按 `daoyou-game-ui` 审查；正文标题只做信息分组，不用特殊字体。

## 21. 第三种案型：破禁试炼（unlock，2026-11-03 按默认值确认）

适配节点 17 个（见路线图矩阵），以试炼、禁地、古塔、碑林、阵库、遗殿为主。

### 21.1 故事骨架

前辈在此设下试炼与禁制，闯过者可得其所留之物。玩家与另一名闯关者同场，还有守着试炼的守试者。

| 身份槽 | 说明 | 说谎 |
| --- | --- | --- |
| `warden` 守试者 | 器灵、残魂或守塔人，知道试炼的规矩，只用谜语回答；结尾亲自出手考校 | 否 |
| `rival` 同场闯关者 | 声称从前人那里得了解法，实为误导或故意引人触发反噬；在来历或所得上说谎 | 是 |
| `fallen` 前人（0–1） | 曾失败的闯关者（残念或重伤未走的人），记得自己哪一步出了错，但记忆有偏差 | 否 |

### 21.2 新机制：机关

- 每局 2 个小机关，各由一个物件承载。每个机关有 4 个部件（符号，如“坎、离、震、兑”或“青龙、白虎……”，名称由模型按场景起），解法是从中按次序选 3 个（共 24 种组合）。
- 操作：新动作 `operate`，提交一个次序。对了：机关开启，揭示一条线索或打开一个房间。错了：反噬，多扣 1 点行动力（共 2 点），记一条反噬描写。错满 3 次，机关锁死，其后的内容拿不到。
- 解法提示：每个机关配 2 条提示线索（如“坎在离之前”“居中者为震”），合起来恰好唯一确定解法。**提示文字由程序按解法渲染，审校不得改写**，避免模型写出自相矛盾的提示；模型只负责符号命名与外围描写。
- 可解性：机关后只放加分线索，或另有来源的关键线索；校验按“机关全部锁死”的最坏情况检查每道结案问题仍有支撑。

### 21.3 结案（开启主禁制）

| 问题 | 形式 | 答案来源 |
| --- | --- | --- |
| `order` 主禁制的开启次序 | 四选一：真次序、闯关者给的次序、照前人记忆字面得出的次序、另一种 | 主禁制铭文 + 两个小机关开启后得到的残句 |
| `catalyst` 以何为引 | 四选一 | 守试者的谜语（玩家读过铭文后才肯说）+ 前人遗物 |
| `cause` 前人为何失败 | 四选一：真相（如被闯关者误导、记错一步）、前人自述、传闻、另一种 | 前人的说法 + 记载戳穿闯关者的谎言 |

- 结尾对决：次序与引子都答对时，守试者亲自出手考校（首领强度）。
- 守卫与事件沿用：守卫守加分房间；事件如“闯关者抢先乱试，一处机关锁死”“禁制收缩，封住一处房间”。

### 21.4 评分

真相 45 / 线索 15 / 效率 15 / 分支 10（戳穿谎言 5、两个小机关都未触发反噬 5）/ 战斗 15（结尾对决 10、守卫 5）。

### 21.5 界面

- 机关物件在“此处”显示为可操作，点开机关面板：4 个部件按钮，依次点选 3 个，显示已选次序与“撤销”，提交前确认；面板显示已失败次数与“再错 N 次将锁死”。
- 已开启的机关打勾，锁死的显示锁。
- 提示线索在案情板中照常归组，可钉到“主禁制次序”。

### 21.6 交付

骨架构造器与 300 种子校验（含机关全锁死的最坏情况）、机关的规则与单元测试、模板、生成器案型描述与提示词、程序渲染的提示文字、保底案卷（绑定一个节点）、机关面板、实际生成与浏览器实测。完成后把 17 个适配节点加上此案型（暂不撤旧配对，撤配对在 3.5 统一做）。

## 22. 第四种案型：异变溯源（anomaly，2026-11-03 按默认值确认）

适配节点 16 个（见路线图矩阵），以资源点、裂缝、祭坛、暗河、荒岛、贝场等“此地出了异常”的地方为主。原型 `anomaly` 为新增。

### 22.1 故事骨架

此地近来出了异常（灵脉枯竭、妖兽暴动、封印松动、阵法失控、药草成片枯萎），玩家受托或路过，要查明根源、找出引发者，并平息它。

| 身份槽 | 说明 | 说谎 |
| --- | --- | --- |
| `culprit` 祸首 | 引发异变的人：有意（截脉、偷走阵眼、私设邪阵）或无心（贪采、误触）；在行踪或所为上说谎 | 是 |
| `local` 当地人 | 受异变所害的人（守园人、采贝人、矿工），描述症状最清楚，指认的“罪魁”却是错的 | 否 |
| `scapegoat` 背锅者 | 被当地人怪罪的对象（外来散修、山中妖兽化形者），有可疑之处但与异变无关；被出示可疑物证后给出反证 | 否 |
| `sage` 知情者（0–1） | 懂得古法的老人、残魂或典籍守护者，知道平息之法的关键一环 | 否 |

结案三问：

| 问题 | 形式 | 答案来源 |
| --- | --- | --- |
| `source` 异变之源 | 四选一：真源头、当地人以为的源头、背锅者身上的表象、另一处 | 现场症状的分布（越近源头越重）+ 源头处的痕迹 |
| `culprit` 是谁引起 | 选人物 | 记载戳穿祸首的谎言 + 源头处的物证 + 背锅者的反证 |
| `remedy` 如何平息 | 四选一：真法、蛮力镇压、当地土法、另一种 | 知情者或典籍给出的关键一环 + 源头处的铭刻 |

### 22.2 新机制：异变加剧

- 异变分三重，在行动力用到约 30%、55%、80% 时依次加剧（沿用事件系统：先有预兆，到点发生）。每重加剧会封住一处房间（新事件效果 `seal_room`：此后不能进入，已在其中可以离开）或毁去一处物件。
- 暂时镇住：玩家找到“镇物”（某件物品）并用在源头处，可设置 `anomaly_contained`，此后不再加剧，并计入分支分。
- 加剧只封加分内容所在的房间或物件；校验按“三重加剧全部发生、不进守卫房间、机关全锁”的最坏情况检查每道结案问题仍有支撑。
- 地图上被封的房间显示“封”，异动横幅显示当前是第几重。

### 22.3 结尾对决

源头与平息之法都答对时，异变之源化形扑出（首领强度）。对手不是人物，而是案卷中的“异变化形”（名字与样子由模型按设定写，如枯藤妖、地脉煞灵）。模板的 `finale.role` 用保留值 `manifest` 表示它。

### 22.4 评分

真相 45 / 线索 15 / 效率 10 / 分支 10（戳穿谎言 5、暂时镇住异变 5）/ 战斗 20（结尾对决 10、守卫 10）。

### 22.5 交付

骨架构造器与 300 种子校验（含三重加剧的最坏情况）、`seal_room` 效果与地图标记、异变化形作为对决对手、模板、生成器案型描述、保底案卷（绑定一个节点）、实际生成与浏览器实测。完成后把 16 个适配节点加上此案型。

## 23. 第五种案型：立场抉择（allegiance，2026-11-03 按默认值确认）

适配节点 8 个（见路线图矩阵）：黄枫谷后山禁地、古魔祭坛群、圣山地脉秘窟、虚天殿星辰阶、法士秘密祭坛、圣禽祭天台、碎空战场、黑潮贝场。都是有两方势力对峙的地方，节点设定的 `factions` 已写明对立的两方。

### 23.1 故事骨架

两方在此对峙，各执一词，都想拉玩家入伙；暗中还有一个两头挑拨的中间人。玩家要查清双方真正图谋什么，然后自己决定站在哪一边。

| 身份槽 | 说明 | 说谎 |
| --- | --- | --- |
| `envoy_a` 甲方代表 | 甲方的出面人，公开说法与真实图谋不同；在一件事上说谎 | 是 |
| `envoy_b` 乙方代表 | 乙方的出面人，同上 | 是 |
| `broker` 中间人 | 两头传话、暗中挑拨的人，想坐收渔利；可被物证揭穿 | 是 |
| `bystander` 旁人（0–1） | 被卷进来的人，知道双方各一部分实情 | 否 |

两方的真实图谋由骨架决定：一方“另有私心但不害无辜”，另一方“所图会祸及无辜”，哪一方是哪种随种子决定，模型按此写故事。

### 23.2 结案

| 问题 | 形式 | 计分 |
| --- | --- | --- |
| `intent_a` 甲方真正图谋什么 | 四选一 | 计入真相分 |
| `intent_b` 乙方真正图谋什么 | 四选一 | 计入真相分 |
| `side` 你站哪一边 | 支持甲方 / 支持乙方 / 两不相帮、出面调停 | **不分对错**，决定结局走向 |

- 模板的结案问题新增标记 `judgement: true`：该题没有标准答案，不计入真相分，结算页显示“你的抉择”而不是对错。
- 抉择影响：结局叙事按抉择分支（叙事输入带上抉择与双方真实图谋）；结算标签记下抉择（如“助甲方”“居中调停”）。
- 调停只有在揭穿中间人后才真正成功；未揭穿时选择调停，结局写成调停未果、双方不欢而散（仍正常结算）。

### 23.3 结尾对决

两道图谋题都答对时触发，对手随抉择而定：支持甲方则与乙方代表交手，支持乙方则与甲方代表交手，调停且已揭穿中间人则与中间人交手；调停但未揭穿中间人则不发生对决。模板的 `finale.role` 用保留值 `opposed` 表示“按抉择决定对手”。

### 23.4 评分

真相 40（两道图谋题）/ 线索 15 / 效率 10 / 分支 15（戳穿甲方谎言 5、戳穿乙方谎言 5、揭穿中间人 5）/ 战斗 20（结尾对决 10、守卫 10）。抉择本身不加减分。

### 23.5 暂不做

按抉择改变奖励倾向（如助某方多得灵石、助另一方多得材料）涉及经济数值，先不做，记为后续。

### 23.6 交付

骨架构造器与 300 种子校验、`judgement` 题的评分与投影、按抉择决定对手、结局叙事的抉择分支、模板、生成器案型描述、保底案卷（绑定一个节点）、实际生成与浏览器实测。完成后给 8 个适配节点加上此案型，然后进入 3.5 节点切换。

**与设计的差异**

**已验证（本地真实接口与页面，账号 local2）**

- 完整流程：开局 → 移动、搜查、使用物品（选择目标）、交谈、出示证据、带条件的锁门 → 结案 → 94 分 S 档，评级取规则评分，资源与 6 件探索物品实际发放，结局叙事依据推断结果写成。
- 调查动作响应约 30–60 ms；重放同一 `actionId` 不重复扣行动力；过期回合返回 409；不在场的目标、非法 id、未掌握的线索作答返回 400。
- `GET /api/dungeon/state` 与命令响应中不含案卷、真相或答案；中途离开结算为 C 档，不揭示真相。
- 未配置剧本的旧秘境会话仍按旧流程展示与结算。

**发现的问题**

- 当前 `LLM_PROVIDER`（qwen3.7-flash）一次生成整份案卷的可靠性不足：三次开局共五次生成均未通过校验（关键线索数不符、引用不存在的 id、问题缺少支撑线索），全部回退到保底案卷，单次开局耗时约 70 秒。已加入自动修复（秘密缺条件时视为到场可得、丢弃无效果的交互），首轮问题从 6 条降到 1 条，但仍未通过。P2 的案卷池应离线批量生成、多次重试，并考虑改用更强的模型；在此之前，玩家实际玩到的都是保底案卷。

**改造：三段式生成（2026-11-02）**

- 原因：上面的失败全部是结构自洽问题（JSON 解析从未失败），JSON Schema 无法约束跨字段引用，而 flash 模型一次写出约 5k token、互相引用的案卷时难以保持一致；按问题清单重试等于重写，反而引入新错误。
- 做法：见 6.2。骨架生成器有 5 个单元测试，其中 300 个种子全部通过结构与可解性校验，房间数覆盖 4–6，旁人有无与连通方式随种子变化。
- 结果（同一模型 qwen3.7-flash）：本地 8 次生成全部成功（1 次走真实开局，7 次直接调用生成函数，其中 4 次并发），每次 24–34 秒，此前为 0/5、约 70 秒。生成的案卷在页面中可以正常开局、调查、结案并结算（实测一局因漏掉作案手段得 59 分、C 档）。
- 已处理的质量问题：真相里带出内部 id 与 Markdown、混入英文单词、房间描写提前透露密物。
- 仍需关注：内容偶有小的前后不一（如线索转述的凶手说法与其台词措辞不同）；一次开局并发 3 个请求，高峰期需留意 `AI_MAX_CONCURRENT_REQUESTS`。

**改造：内容一致性（2026-11-02）**

前后不一的来源与对策：

| 来源 | 对策 |
| --- | --- |
| 真相先于名字生成，人物换名、身份前后两样 | 大纲字段按“人物名字与 `nature` → 线索 `fact` → `canon` → 真相”的顺序生成；真相必须提到凶手与传人的名字，否则重写一次大纲 |
| 并行撰写的各段对同一事实各自发挥 | 大纲产出事实设定 `canon`（死者、凶手真实身份、手段、谎言、矛盾点、信物）与每条线索的核心事实 `fact`，所有正文以此为准 |
| 同一物证在房间、物件、线索、交互、解析里各写一遍 | 单一出处：物证细节只写在线索正文；房间只写空间与人物；藏有线索的物件只写一句异样（40 字）；交互只写动作与感官；解析只用线索名称引用 |
| 凶手的说法在开场、关系、台词、线索里措辞不同 | 谎言原话由程序渲染到 `clue_claim` 与对应秘密；对外身份一律使用其称谓 `title` |
| 骨架语义含糊（密室门纹样像机关，模型写成“凶手进不去密室”） | 修正骨架的作用说明：开门靠钥匙，门上纹样只是血脉印记 |
| 仍有遗漏 | 一致性审校两轮，只改确认有问题的字段 |

评估方法：用比生成模型更强的 qwen-plus 做独立审校（只计数、不改写），对比改造前后各 5–6 份案卷。该审校过于苛刻，会把措辞不统一、遗漏也报成严重问题，自动计数噪声大；因此再按“两处对同一事物陈述了不同事实”人工逐条复核：

- 改造前：约 12 处 / 5 份，**约 2.4 处每份**（身份“高足”与“结义兄弟”混用、手的位置四处不一、信物名称两样、门上凹槽数量不一等）。
- 改造后：约 6 处 / 6 份，**约 1.0 处每份**（凶手辈分“师叔祖/师叔”、解析引用了错误的线索名、开场提到不存在的令牌等）。
- 代价：生成耗时从约 30 秒升到 37–53 秒（一次 77 秒），每局多 1–2 次审校调用。

剩余问题与后续方向：生成与审校都用 flash 模型、不开思考，审校本身漏检与误报都有。案卷池离线生成后可以改用更强的审校模型，并按“严重问题为零才入池”做生成—校验—择优，耗时不再影响开局。

**谜题可推理性与入库把关（2026-11-02）**

- 问题：每局只有凶手、传人和可能的旁人，凶手几乎一眼可辨；骨架固定，“手段”一问的答案永远是用工具探查到的那条线索，玩过几局即可套路作答。
- 嫌疑人：模板新增身份“嫌疑人”。每局都有一名被冤枉的嫌疑人，留有确实存在、但另有清白缘由的可疑物证；遗骸上的残缺痕迹凶手与嫌疑人都对得上；向嫌疑人出示可疑物证后，他会给出可核实的反证（关键线索），才能排除他。
- 骨架变体（随种子）：有无封闭密室；作案手段由工具探查、旁人目击或取得信任后的传人道出；凶手在身份还是行踪上说谎；房间、物证与人物站位。
- “手段”改为选择题：真相一项，另有顺着嫌疑人物证、传闻表象与另一种说得通的误判共三个干扰项，顺序随种子打乱（Fisher–Yates，修正了小种子下真相总排第一的问题）。

**与人物自由对话（2026-11-02）**

- 交谈改为打开对话面板：玩家直接输入问题（80 字以内，经文本过滤），每问一句消耗 1 点行动力；原有的固定台词保留为“寒暄”。接口 `POST /api/dungeon/mystery/talk`，场景 `dungeon-npc` 走基础模型组，不流式。
- 防泄露分两层：模型只拿到此人此刻**可以说**的内情（解锁条件已满足的秘密），拿不到真相与未解锁的秘密；它声称透露的线索再由规则层 `applyMysteryDialogue` 过滤。凶手的对外说法作为 `publicClaim` 提供，对话中必须与之一致。
- 先校验在场与行动力再调用模型；模型失败不扣行动力。每人保留最近 4 轮对话作为上下文。
- 验证（直接调用生成函数，测试账号的气已用尽，未经页面走接口）：每次回复 0.8–1.5 秒；越狱式指令与诈问均被角色口吻挡回、不透露任何线索；传人未取得信任时拒答；相关提问正常解锁线索。规则层新增 3 个单元测试。
- 已知不足：问无关问题时，模型有时仍会顺口说出已解锁的内情（不构成泄露，“寒暄”同样会给出，但削弱了“问对问题”的成就感）。

**结案对决（2026-11-02）**

- 模板有战斗权重（`scoring.combat > 0`）且玩家正确指认真凶时，结案不立即结算：真凶负隅顽抗，进入现有的遭遇战流程（迎战预览 → V6 战斗 → 返回）。真凶为整场唯一敌人，按首领强度生成，敌人名即真凶姓名。指错人则真凶不暴露，照常直接结算。
- 对决结果计入评分：擒下（战胜）得满额战斗分；交手落败（含战斗中逃跑）或在迎战前“任其遁走”记 0。三种结局都按完成通关结算，推理所得照常发放；战胜另有沿用 `battle:<id>` 的战斗掉落。
- 遗产谋杀案模板权重调整为 真相 50 / 线索 15 / 效率 15 / 分支 10 / 战斗 10（原 55 / 20 / 15 / 10 / 0）。
- 状态：结案答案暂存在 `MysteryRecord.verdict`，对决结束后连同结果一起评分；评分结果带 `confrontation`（won / lost / spared / none）。结局叙事输入同时给出对决结果，提示词要求未对决时不得描写交手。结算标签追加“擒下真凶”或“真凶遁走”。
- 前端：结案面板提示“指认真凶后对方可能负隅顽抗”；迎战页改用“负隅顽抗”“任其遁走”文案与对应确认框；结算页的评分明细显示战斗一项及对决结果。修正了战斗结束回调不带最终状态、结算页缺少评分明细的问题。

**案情随回合推进（2026-11-03）**

- 案卷新增可选字段 `events`：每个事件有预兆回合 `warnAt`、发生回合 `at`、阻止条件 `unless` 与后果（毁去物件、人物离场或设置标记）。每次调查动作后由规则层推进：到预兆回合在日志里记一条“异动”，到发生回合执行后果；阻止条件先满足则不再推进。回合数随每个成功的动作递增（重看已搜过的物件不扣行动力，但时间照样流逝）。

- 校验按最坏情况推演：不进任何守卫房间、所有事件都已发生，每个结案问题仍须有关键线索支撑。错过事件只损失线索分与分支分，不会让案子无解。
