# 游戏文案共同口径

供后续按玩法审查玩家可见文案时使用。包括页面、按钮、提示、通知、战斗记录和生成内容的展示文本。具体规则、数值、物品事实以当前实现为准；本文件不替代主流程 UI 与物品预览的现有规范。

## 写给谁

写给正在做决定的玩家。先让他看懂当前状态、可做的事和操作结果，再考虑场景气氛。洞府、宗门等地点可以有自己的语气，但界面提示应像同一个游戏在说话。

- 界面用自然、简短的现代汉语。需要直接称呼玩家时用“你”；没有必要时省去称呼。不在系统提示里反复叫“道友”，也不用“您”。NPC 对话、书信和剧情按角色身份写。
- 修仙词汇用于地点、身份、物品和真实玩法。若一个说法会遮住操作含义，就用玩家熟悉的词说明动作。例如按钮写“存入”，实际入库后反馈“已存入洞府储藏室”。
- 不靠排比、套话、无依据的赞美或玄虚结语制造气氛。场景描述可以有画面，但每句话都应帮助玩家感知场所或理解眼前的事。
- 不把内部实现写给玩家，例如接口、状态码、字段名、任务 ID 和“请求失败”。确实需要说明连接问题时，说清受影响的功能和下一步。

## 按位置写

| 位置 | 应回答的问题 | 写法 |
| --- | --- | --- |
| 场景名与入口 | 我到了哪里？ | 沿用同一个地点的正式名称。入口只承担导航，不附一段玩法说明。 |
| 场景简介 | 这里能做什么？ | 一两句建立场所感和主要用途。主流程首屏不堆条件、概率和完整规则。 |
| 按钮 | 点下去会怎样？ | 文案与实际效果一致。跳转写去向，如“前往静室”；即时操作写动作，如“领取”“存入”。不要把打开准备页面写成已经冲关。 |
| 状态与限制 | 现在为什么不能做？ | 说出当前条件，必要时指出下一步。条件、数量和剩余时间必须与实时数据一致。 |
| 空状态 | 为什么这里是空的？ | 只解释当前为空的原因或可做的下一步；未知原因不猜测。筛选无结果与确实没有物品分开写。 |
| 加载与失败 | 正在等什么，失败后怎么办？ | 加载文字点明对象。失败反馈优先给出可恢复动作；不要把原始异常直接当玩家文案。 |
| 成功反馈 | 刚才完成了什么？ | 写明动作和对象。若结果已在当前画面明显呈现，可以不再弹一条重复提示。 |
| 确认层 | 我将付出什么，得到什么？ | 在确认前说明真实消耗、风险和不可逆结果。精确数值放在玩家做决定的位置。 |
| 剧情、NPC 与生成内容 | 这个世界发生了什么？ | 可以更有性格和留白，但不能捏造奖励、成本、规则或已发生的状态变化。 |

同一信息只在最能帮助决策的位置说一次。状态、标题和按钮已经说明结果时，删掉复述它们的正文。物品预览保留现有的字段顺序与完整描述，不为凑气氛补造背景或无效限制。

## 称呼与术语

名称先核对当前路由、场景导航和共享定义。同一对象在标题、入口、操作结果中保持一致；“储物袋”作为场景名、“随身物品”作为其中的标签，可以并存。旧入口保留其迁移含义，不能当成新玩法的命名依据。

| 所指 | 当前可用称呼 | 审查时注意 |
| --- | --- | --- |
| 玩家角色页 | 道身；导航中的“角色” | 分清场景名与通用称谓，不在同一界面无故轮换。 |
| 随身与存放处 | 储物袋、随身物品、洞府储藏室 | 写清物品究竟进了哪一处。 |
| 破境流程 | 任务中心、破境卷宗、静室冲关 | 状态和按钮跟随当前阶段，不把“准备”写成已经冲关。 |
| 数值与条件 | 当前配置中的境界、属性、资源名 | 数字用阿拉伯数字；加成、概率、消耗与门槛按真实规则写，不凭语感改含义。 |

各玩法的专有名词在审查该模块时补齐，不提前建立一份脱离代码的总词典。道具名称与效果以共享物品定义为准，物品预览的格式与数值写法沿用 `daoyou-item-preview`。

## 从现有页面校准

这些是审查方向，不表示页面文案已经修改。

| 当前样本 | 处理方向 |
| --- | --- |
| 储物袋操作成功后，部分动作统一提示“已完成” | 按动作写结果，例如整理后提示“已整理随身物品”；转存时说清件数和去向。 |
| 破境卡同时出现“前置已成”“可回静室冲关”和复述这件事的整段正文 | 保留足以说明状态与下一步的内容，删掉重复说明。 |
| 洞府加载时写“正在推演天机……” | 加载提示应让玩家知道正在等待洞府内容，例如“正在进入洞府……”。 |
| 储物袋区分“暂无物品”与“暂无符合筛选条件的物品” | 保留这种区分，避免让玩家误以为物品丢失。 |

## 每轮审查的记录与验收

按“位置、触发状态、原文、事实来源、建议文案、修改理由”记录。先核对规则与实际动作，再改措辞；同一文案如果由前端、服务端或生成模板共同决定，要查到最终玩家看到的文本。

主流程场景的顶部简介以 `apps/web/src/router.tsx` 的 `scene().summary` 为准；页面传入的 `GameSceneFrame.description` 可能被覆盖。修改后要在实际页面核对显示结果。

每条修改最后检查：玩家能否看懂下一步；是否增加或丢失事实；是否重复相邻文字；成功、失败、空状态是否各说各的事；术语是否与其他入口一致；剧情味道是否妨碍理解。生成文本还要检查提示词与展示层的约束，不能只改一份示例输出。
