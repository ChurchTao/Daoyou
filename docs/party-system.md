# 通用组队与玩法接入

队伍是账号之间的长期集结。同一账号同时只占一个队伍席位，席位记录当前参队角色。队伍管理容量（四人）、入队、退出、解散、队长变更和名单版本。结伴讨伐、古魔入侵和擂台分别管理自己的招募目标、准备、准入和开战。队伍可以从一个玩法带到另一个玩法。

| 层 | 数据 |
| --- | --- |
| 通用队伍 | 队伍 ID、队长、成员账号和角色、入队顺序、名单版本 |
| 玩法候场 | 队伍 ID 和当前玩法内的准备、招募或擂台阵营 |
| 已开战 | 玩法冻结参战成员、实际战斗席位、用时、进度和奖励 |

古魔入侵按账号保存个人周进度。组队层允许成员离开或解散，已经开战的波次按冻结名单结算，完成后可换队继续。新的场次由队长的个人进度决定起始波，按实际参战成员的最高境界设定难度。

结伴讨伐读取通用队伍，目标、境界范围和助战资格由讨伐校验。擂台使用两边参战名单和观战席，纯观战不改变队伍。队长可将当前队伍作为完整小队入场，擂台负责安排同侧席位、准备与开战。名单更改时，玩法只能通过新快照重新确认开战名单。

通用队伍写入在同一 PostgreSQL 事务内串行校验队长、角色归属、人数和账号唯一席位。人员或队长变动会递增名单版本。玩法在开战时核对名单版本并冻结当场参战名单。

## 入口与入队申请

- 展开菜单的「组队」是固定入口。在队角色可以从吸边按钮打开同一工作台，战斗中默认打开传音。队伍资料、管理和审批集中在「队伍」页签。聊天未读和待审申请分别提示。
- 未组队时可以创建队伍、按玩法找队和查看已发申请。分享链接和世界频道招募都打开组队内的申请预览。申请有十分钟有效期，同一队伍只保留一条待审申请，每人同时最多申请三支队伍。
- 申请与审批结果存入 Redis。待审有效期最长十分钟，结果保留至发起申请后 24 小时。正式入队由 PostgreSQL 提交，成功回执随后写入 Redis。回执写入失败时，队伍界面以正式名单确认入队。审批开始写入名单前会先消费申请，若名单写入失败，玩家可重新申请。
- 队长可以同意、拒绝或展开申请者的公开构筑。只有批准入队才占用一个席位并更新名单版本，提交或撤回申请不改变候场准备。成功入队后其余待审申请失效。
- 招募来源在申请和批准时由玩法复核。讨伐校验目标、候场和招募境界，古魔校验期次、招募状态和挑战占用。普通分享链接用于自由结伴，最终的参战资格由玩法开战时校验。
- `party.changed` 只通知客户端重新读取队伍数据，申请资料和审批权限由 HTTP 接口校验。讨伐的进场联动由游戏布局独立维护。

| 玩法 | 候场与已有数据 |
| --- | --- |
| 古魔入侵 | 按期和队伍 ID 保存招募及准备。已有队伍可在营地直接准备，需要补人时由队长开启营地招募。开战时绑定个人周进度与独立场次，并冻结当轮名单。 |
| 结伴讨伐 | Redis 保存目标、境界范围、准备和战局记录。旧 Redis 候场队伍在讨伐入口读取时尝试迁入通用队伍，已有通用归属优先。旧战斗按原快照结算。 |
| 擂台切磋 | 队长可选带队入场，并占用同侧席位。通用队伍变更后，需退出该次擂台候场并用新名单入场。个人切磋和观战沿用原房间入口。 |

## 通用组队上线前的本地验收

- 三个独立浏览器会话验证了邀请入队、队长移交、队长解散和旧邀请失效。通用队伍页面检查了桌面及 360px 宽度。
- 同一支队伍先在擂台同侧完成切磋，再选定讨伐目标、准备并进入共用战局。验证了讨伐招募范围、非队员传音权限及擂台拒绝使用旧名单开战。
- 古魔首波开战后退出通用队伍的成员仍可回原局，尝试再次报名被拒绝。通用队伍补入新成员后，原局仍显示开战名单。另验证准备时队伍仍保持私密，队长可主动公开或停止营地招募。
- `lint`、`typecheck`、`build`、全量 3648 个单元测试和本地数据库迁移均通过。未验收存量 Redis 队伍迁入、跨实例压力和预发布环境。
