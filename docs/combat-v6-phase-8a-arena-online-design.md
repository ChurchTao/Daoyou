# combat-v6 Phase 8A：擂台接入 v6 与服务端权威回合

> 日期：2026-09-06  
> 状态：实现已接入；纯本地八账号 4v4 主链路通过，完整故障与响应式验收仍有未验证项。  
> 方向基线：[总路线图](./combat-v6-mhxy-redesign-roadmap.md)  
> 展示基础：[v6 战斗 UI 与差量播放](./combat-v6-battle-ui.md)

## 1. 目标与确定边界

复用现有擂台房间，在最终开战时桥接到 v6 权威战斗与新版 React 页面。保留房间既有人数、邀请码、换队、准备、冻结阵容及房主开战规则，每方最多四名人物；不新增邀请或组队系统。

- 参与人物使用自己的现有 v6 构筑，以 `full` 策略入场；无持久资源回写、消耗品、奖励、排名或任务结算。
- 下令窗口 30 秒；所有仍在场的人物，包括倒地者，都提交本回合指令。提交即锁定，全部提交后立即结算，否则截止后补普攻。
- 离线默认普攻，不增加认输、连续超时弃权或托管 AI。玩家离场使用引擎逃跑规则；一人逃跑不直接终止仍有队友在场的战斗。
- 100 回合结束仍未产生正常结果则平局；创建后两小时绝对期限不续期，届时超时终止，不按剩余血量判胜。
- 正常播放约每行动一秒，无整回合跳过；刷新或重连恢复最新权威状态，补齐战报而不强制重播离线行动。
- 同账号可多端查看，首份成功指令生效；不新增踢设备机制。
- 停机维护后直接硬切，不提供旧擂台战斗恢复、双引擎选择、v5 回退或功能开关。
- 不包含持久召唤兽、捕捉、回放播放器、观战、分享、匹配、跨服、道装经济或完整养成入口。真实人物多人控制在本阶段完成，不留到 8C。

## 3. 房间到战斗的桥接

保持房间流程：组局 → 准备 → 冻结阵容 → 创建战斗 → 关联 battle ID → 广播并进入新版页面。房间内无需再次确认或选择引擎。

创建阶段由服务端执行：

1. 复用房间开战权限和 `startRequestId`，以房间 ID 与该请求构成稳定幂等身份。
2. 按稳定顺序校验冻结席位的账号/角色归属、当前 v6 构筑及活动战斗/结算互斥；客户端不得提供面板、seed 或技能定义。
3. 编译并冻结所有人物完整入场快照，创建 `participant → controlledUnitIds` 映射。房间席位是阵容来源，最终编译结果必须与冻结席位一致。
4. 原子提交 v6 运行态、参与者占用索引、房间来源索引与截止调度信息。重试复用同一个 battle ID，不重复创建或只锁住部分参与者。
5. 关联房间 battle ID；若在创建后、关联前崩溃，通过来源幂等索引恢复关联。明确校验失败时恢复房间可处理状态，不遗留 `starting` 或占用锁。

不通过持有长时间数据库事务等待网络/结算。复用现有角色互斥边界，并核查擂台、野怪、训练房与构筑变更之间的互斥覆盖。房间本身 TTL 与战斗两小时 TTL 不混为一谈：战斗创建后依赖已持久的来源和参与者事实清理，即使房间过期也不得遗留角色占用。

## 4. 倒地人物的指令与执行

将“本回合可提交意图”与“此刻能执行行动”分开。对仍在场的人物，倒地不阻止提交；已逃离、永久死亡、未入场的单位不收令。正常胜负判断优先，战斗已经结束时不再等待倒地者。

- 指令阶段仍校验归属、指令结构、技能持有与目标类别；当前倒地、控制状态或资源不足是执行条件提示，不能以此一概拒绝可在行动前恢复的人物意图。
- 执行时再次权威裁定存活、控制、资源、目标和技能要求；不为允许预提交而放宽实际扣费或技能规则。
- 锁令与速度队列包含在场倒地人物，沿用既有速度及同速规则。轮到时已复活则执行；轮到时仍倒地则跳过；在其顺序之后复活不补行动。
- 防御/保护仍须遵循现有锁令和实际拦截资格规则，倒地者不能在未复活时提供有效保护。倒地、复活、再次倒地不得产生重复出手。
- 超时/离线补入明确的本回合普攻，不使用可能复用上次技能的自动模式。默认目标采用稳定合法目标顺序，目标失效沿用已有执行期重选规则；不得在重复调度中额外消费 RNG。

这是 core 可观察语义变化，需提升相关战斗版本，并更新受影响的版本戳、内容/投影组合检查与共享黄金测试；不得静默改写旧回放解释语义。是否仍能执行旧版本快照必须显式校验，8A 不承担跨版本续跑，历史记录读取仍保留。

## 5. 服务端回合生命周期与恢复

在线 Host 在 core 阶段之外管理 `collecting → resolving → playback → collecting`，终局进入 `finished`。计划中的运行态记录至少包括：版本、来源房间、参与者与控制权、冻结入场数据、core checkpoint/RNG、回合 ID、已接受指令、revision、事件游标、各阶段截止时间、锁令事实和最近已提交回合结果。

- 收令以战斗、回合、单位与请求 ID 校验；相同请求重试返回原提交结果，同单位不同请求在已锁定后返回稳定冲突。其他玩家提交导致的全局 revision 增长不使本人的合法请求失败。
- 全部收齐和截止调度竞争同一个原子阶段转换；锁定缺省指令与输入 checkpoint 后再计算。resolver 输出经 CAS 提交成功后才能推送，CAS 失败的计算结果不得发布。
- Redis 保存阶段截止索引，后台协调器扫描并补偿；进程定时器仅是及时唤醒手段，不是权威计时来源。服务重启或所有客户端离线后仍会推进。
- resolver 崩溃后用已锁定输入重算；提交成功而推送失败时，以已提交结果重发或 HTTP 补齐，不重复结算。阶段租约须带 fencing/CAS 约束，不能只靠进程内标记。
- 公共播报窗口按已提交结果帧数及现有间隔计算，之后开启 30 秒下令。结果提交时提供 `serverNow`、`playbackEndsAt`、`commandOpensAt` 和 `commandDeadlineAt`，客户端不得自行延长。
- 服务端不等待播放 ACK；慢设备或重连者通过恢复追到当前权威状态。终局结果在连续观看客户端播完后展示，服务端终局清理不依赖此时机。

存在任一有效战斗订阅连接即视为该参与者在线，关闭一个标签页不等于离线。复用实时连接心跳/失效机制，以参与者所有连接汇总判定；新断线者保留本轮截止机会，确认离线后从后续收令阶段补普攻。补令和重连提交原子竞争，已经接受的普攻不撤回，下一尚未锁定的操作机会恢复手动。离线不改变 100 回合及两小时上限。

## 6. HTTP、WebSocket 与权限

| 职责 | 方式 |
| --- | --- |
| 开战 | 现有擂台 start HTTP，桥接创建 v6 |
| 提交本回合指令 | v6 HTTP，明确返回 accepted/locked/stale 等结构化结果 |
| 下令状态、锁令、回合结果、截止时间、终局 | WebSocket 推送，按回合发送结果及差量帧 |
| 首次进入、重连、缺口 | HTTP 读取完整基准或匹配游标后的增量 |
| 逐行动文字与血条 | React/播放控制器，不按画面帧率发送网络消息 |

新增擂台 v6 HTTP 契约放在 `src/shared/contracts`，接入现有认证中间件。建议独立战斗路由 `/game/combat-v6/arena/:battleId` 与 `/api/combat-v6/arena/...`，最终名称在实现时与路由注册统一；不复用 v5 live 路由组件。玩家没有直接触发权威 resolve 的在线接口。

推送信封至少包含协议版本、battle ID、round ID、revision、可见事件游标及消息种类。业务事件区分指令已接受/提交状态、阶段变化、回合结果与终局；消息中携带服务端时间。NATS Core 复用跨实例分发，WebSocket 订阅必须经认证和参与者归属校验。Redis 为权威，消息丢失不等于战斗丢失；不新增外部状态库或消息中间件。

### 可见性必须由服务端裁剪

- 所有人可见各单位 HP/MP 比例、公开护盾和状态、是否已提交及已发生的行动。
- 精确属性、角色私有资源、可用技能选项与未结算指令仅本人可见；不因同队关系扩大到其他角色。
- 现有单位 DTO 含精确数值，不能只在 React 隐藏。先生成权限范围内的单位视图，再计算该视图的差量；对手精确数值不得藏在顶层 units、差量、详情、调试字段或 WebSocket 中。
- 原始 `CommandAccepted` 等事件包含技能/目标，不直接作为公共战报推送。公共提交状态只显示是否提交，本人通过私有指令视图获得确认。可见事件流有自己的连续游标，不因过滤私有事件制造假缺口。
- v6 调试 trace 不为生产擂台暴露他人信息；回放也不能绕过权限，完整权威归档保留在服务端。双方可读取本场授权回放视图，不开放其他人的历史记录或分享。

### 基准与推送衔接

先建立订阅并确认就绪，再通过 HTTP 获取基准；基准返回前短暂缓存推送，收到基准后丢弃已包含的消息，只应用连续新消息。基准后到达的旧消息同样去重。跨连接的缓存有界，发现缺口、版本不匹配或缓存溢出则重新获取基准，不能猜测状态。

HTTP 补增量必须校验基准和可见游标；服务端不再保留所需区间时返回必须重建基准的明确响应。刷新/重连直接以最新单位状态初始化显示游标，不展开离线期间所有完整快照。播放队列仍只保存差量，并及时释放。正常推送按回合携带结果；载荷保护超限时通知客户端通过 HTTP 读取已提交结果，不改为逐画面帧推送。

## 7. 终局、回放和房间释放

正常胜负、逃跑导致的终局、100 回合平局均发布 v6 终局事实，记录回合数和结束原因；技术中止或绝对期限终止明确区分，不伪造正常胜负。没有认输接口或认输终局类型。

扩展 v6 元信息支持擂台来源与冻结参与者；终局事实及归档授权不能继续只依赖单一 `cultivatorId`。回放 payload 保存参与者事实，PG 归属关系使用可索引的参与者映射或等价现有结构；执行前审查 schema 后生成最小业务迁移，不改 Better Auth，也不将派生战斗属性写入角色表。

终局消费者按 battle ID 幂等释放全部角色占用、更新/释放房间并通知参与者。归档失败不阻塞房间和角色解锁；解锁失败由持久终局事实和协调器重试。擂台终局不进入野怪 Condition 写回，不触发奖励或任务消费者。

本阶段保证授权回放可读取，播放器和历史逐行动表现格式归 8B。v6 尚未上线，练功房、野怪和擂台统一采用 `CombatV6ReplayV1`，不保留旧 v6 测试归档格式兼容。v5 历史记录不在本轮处理范围。

## 9. 验收矩阵

纯单元测试仅位于 `src/shared`，不新增前端、服务端或基础设施 mock 测试。

- 倒地人物成功提交；快治疗拉起慢人物后本轮执行；慢治疗拉起已错过顺序的人物不补行动；二次倒地、保护、状态解除和资源恢复后的执行裁定。
- 1v1、现有规则允许的不等人数及 4v4；全部参与者的指令归属、同速顺序、超时与离线普攻、逃跑后剩余队友继续战斗。
- 100 回合平局、正常胜负优先、两小时到期、双方离线推进；恢复前后 checkpoint、RNG、锁定指令与结果一致。
- 服务端可见性纯投影测试：不同参与者仅收到本人私有字段，差量重建不产生精确对手数值或未结算指令泄露。

使用实际本地 Redis、认证 HTTP、WebSocket 和数据库做定向运行验证，记录使用的测试角色及资源影响，不把运行验证写成第三方依赖单元测试：

- 并发提交、同账号多端、请求成功但 HTTP 响应丢失、截止与最后指令竞争、同房间重复开战。
- 创建成功后关联前中断、锁令后计算前中断、CAS 成功推送前中断、归档/解锁失败重试；没有重复战斗、回合或永久占用。
- 订阅就绪与 HTTP 基准间的结果竞态、重复/乱序消息、历史游标缺口、权限拒绝、跨实例推送与连接失效。
- 桌面与 360px：4v4 血条对齐、抽屉/Tooltip、倒地下令、连续点击、公共播报时间、慢客户端/后台标签页恢复、逃跑与终局展示。
- 检查实际 HTTP/WS payload，不只检查 UI；擂台战后 condition、奖励与任务数据不发生写回。

执行相关 v6 共享测试、`bun run lint`、`bun run build`、触及文件 Prettier 和 `git diff --check`；core 语义变化还需扩展共享引擎回归。无法获得八名测试参与者时必须记录真实 4v4 联调未完成，不能以 16 单位布局或模拟角色替代认证多人验收。

## 10. 停机维护与硬切

上线由用户停机维护，不实现运行中的旧战斗迁移：停止接收请求并停掉旧擂台调度/消费者的相关执行，按旧擂台来源清理其活动房间、战斗运行态及关联占用索引；不得执行全 Redis 清空或删除历史归档。清理范围和可重入脚本在实施时依据真实键前缀与反向索引列清，不在本次设计阶段执行。

维护期应用所需业务迁移、部署前后端一致协议并完成最小开战/终局检查后恢复服务。不保留用户可选旧引擎、旧战斗重连或 v5 开战回退；故障处理通过继续维护和修复发布，不借功能开关切回旧战局。

## 11. 本轮实现与验证记录（2026-09-06）

- 擂台开始已硬切 `createArenaV6` 和 `/game/combat-v6/arena/:battleId`；独立 runtime、HTTP、WebSocket 和 React 在线 Hook 已接入，不导入 v5 战斗页面。
- 收令、锁令与结算提交采用 Redis revision CAS；协调器按持久截止索引推进。终局运行态在归档和消息投递完成前不设置 TTL，作为可重试的终局任务；先释放角色／房间，再写统一归档及角色关联表并投递 `combat.v6.battle.finished`。无需增加第二套终局消费者；条件回写消费者显式跳过 `sourceType=arena-sparring`。
- 练功房、野怪、擂台统一使用 `wanjiedaoyou_combat_v6_replay_archives`：战斗 ID 为主键，保存来源、玩法、版本、开始／结束时间、结果和带版本的回放 payload。`wanjiedaoyou_combat_v6_replay_participants` 使用 `(battle_id, cultivator_id)` 联合主键及角色查询索引；读取先通过关联表鉴权，擂台继续校验 payload 中的账号归属并生成私有视图。两表在同一事务中幂等写入，删除归档级联删除关联；删除角色不删除历史归档。
- 归档 payload 统一为 `CombatV6ReplayV1`：参与角色、初始阵容、技能／状态定义、种子、版本、每回合指令、事件和最终状态。来源差异只在 metadata 中表达；结果统一为 `side-0 | side-1 | draw | aborted`，按查看者阵营生成胜负显示。`ArenaRuntime` 仅用于 Redis 活动战斗，不再入归档；收令、回执、截止时间和推送缓存不属于回放。所有来源使用同一个构造、归档、授权读取和公开展示函数。
- 尚未提交的两份归档迁移已合并为 `0036_unified_v6_replay`，直接清空旧 v6 开发回放并建立角色关联表，没有历史 payload 转换。维护时先停止旧进程，再迁移、启动新版；本地原测试归档已清理并重新迁移。未向预发布执行迁移，v5 历史战报保持原状。
- 统一契约验证：26 个共享测试文件／207 项测试通过，覆盖三种来源使用同一结构、拒绝旧运行态字段、重复参与者和查看者授权；野怪共享测试验证新归档序列化。真实本地 4v4 和练功房终局分别生成 8 人／1 人归档，两份 payload 顶层字段一致、均通过统一解析；通用与擂台读取入口输出一致且只暴露查看者的私有属性。Lint、本地构建通过；本轮未重复完整野怪 HTTP 结算链路。
- 开战冻结在统一角色行锁下读取构筑并原子登记 Redis 占用，避免与使用数据库协调的角色修改交错；事务不等待收令、演算或结算。构筑初始化同样经过占用检查。
