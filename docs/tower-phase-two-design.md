# 蜃楼幻境第二阶段：配置驱动与玩法收口

日期：2026-09-19。状态：配置与编排已实施，验证记录见第 8 节。玩法未发布，直接硬切，不保护旧内容版本；敌人根据配置编译，尽量减少代码中的内容分支。

现状参考：[逐层策略存储](tower-strategy-storage.md)。当前已保存显式 20 层策略，开战按境界编译敌人，预览由策略生成。本文替代此前的旧版本保护、转换兼容和版本化祝福安排。

## 1. 本阶段只做三件事

1. **补齐配置驱动。** 将属性修正、行动周期、机制参数、适配限制及说明来源从内容分支收敛到配置，复用现有策略编译链路。
2. **编排完整 20 层。** 四个普通铺垫层关联当周强敌；15/20 层使用配置定义的行动变体，不统一强加调息。
3. **验证玩法与节奏。** 比较不同打法的收益，完成金丹代表构筑的完整流程和末段校准；祝福采用已确认的九次选择。

保持正常角色构筑、每场满状态、公共战斗组件、简单祝福、20 层和四档奖励。每角色一条本周领奖记录、每周一条配置不变。

不新增商店、事件、分支路线、战斗专属面板、后台编辑器、通用规则语言或复杂 AI。不重写已有周抽取算法，不扩展封印多敌、复活、召唤、双首领。全开放境界校准及跨周、并发、故障验收继续归第三阶段，仍是正式开放前的必要检查。

## 2. 已有能力与剩余缺口

直接复用已有逐层策略、独立词条、预算份额、明确护卫目标、最多三敌、校验、预览、策略签名及近三周软避重。模板外的合法策略可以编译；生成池只负责选择经过验证的内容，不是编译器白名单。

实施前编译器通过原型/词条分支选择行动周期，直接写入厚血、防御、速度、法力、首领/封印输出修正等常量；预览与校验也存在内容判断。本轮已将这些事实提取至内容配置。

本阶段直接整理当前实现，不再建立 v5/v6 并行解释器。只移除本次替换导致失去用途的塔内旧实现及兼容测试，不清理无关模块。

## 3. 配置与代码的分工

### 两层数据

**仓库内容配置**保存可复用的境界基准、预算、原型、词条、行动方案、技能/状态、候选遭遇、铺垫映射与祝福节点。优先沿用已有 JSON、Schema 和 V6 技能定义格式，不为每个概念新建一套系统。

**每周 SQL 配置**只保存本周选中的 20 层策略。沿用 floors/enemies，每敌人增加明确的 `behaviorId` 引用；发布时填全，编译时不根据楼层或词条名猜行动周期。完整技能和周期定义不重复写入周记录。当前结构为 schema 3 / content v6。

若结构变化需要升级 schema，只保留当前结构并硬切，不编写旧结构转换。Redis 单场战斗快照仍保存真实单位、技能、状态与行动计划，刷新恢复不重新编译。

### 配置负责内容事实

| 内容 | 配置职责 |
| --- | --- |
| 原型 | 属性档、资源与外观；角色定位不隐含技能 |
| 属性词条 | 固定属性修正，必要的原型差异显式配置 |
| 行动方案 | 技能周期、目标选择方式、资源不足时备用动作 |
| 机制 | 引用已有 V6 技能/状态，配置护卫减伤、治疗量、低血阈值等；关系通过敌人 ID 绑定 |
| 遭遇编排 | 适用层段、组合、份额、关键层候选、铺垫方案引用 |
| 合法性 | 互斥组、适用原型、行为兼容、封印单敌和双护卫限制 |
| 展示 | 名称、图标、短说明；周期和百分比来自同一配置 |
| 祝福 | 五项效果、上限、候选数量、选择节点 |

例如治疗者耗尽法力后弱攻击，应由行动方案配置，替代 Host 对治疗技能 ID 和法力 12 的专用判断。技能资源与控制是否合法仍交给公共 V6 引擎。

只支持实际需要的有限能力：固定周期、指定关系目标、最低血量比例目标、属性乘加和被动绑定。不要引入任意脚本、第二套表达式解释器或无界条件树。

### 代码负责通用规则

代码保留 Schema 解析、引用检查、人数与份额校验、防循环、声明式兼容检查、固定预算计算顺序及取整、目标绑定、技能实例化、周期执行、预览组装和确定性抽取。

伤害结算、控制、行动时序继续属于公共引擎。新增一组由现有能力组成的敌人应只需修改配置及验证；只有现有能力无法表达的新机制才需要扩展代码。不新增另一份楼层描述模型，不恢复完整 NPC 存储。

## 4. 玩法进一步收敛

### 四个铺垫层

仅调整 4/9/14/19 层，分别关联 5/10/15/20 层，其余普通层先保留。每个候选遭遇在内容配置中引用可复用的铺垫方案，不在生成器中增加“有治疗就生成某两只敌人”的专用分支。

治疗铺垫练习拆辅助，双护卫可用单护卫铺垫，单敌展示主周期；14 层优先练习 15 层行动变体。使用普通预算，不复制精英属性，不强制锁血或敌人出手。

先抽关键层，再展开铺垫引用，最终保存完整策略。编译当前层时不读取下一层动态改变敌人。人数变化后需有正确份额与目标引用，不能直接截断数组。

### 15/20 层变体

保留后半程行为差异目标，撤回“全部追加调息”和专用 recovery_cycle 词条的默认方案。

本阶段先用已有技能配置不同周期及辅助配合，例如蓄势间隔、群法后的进攻空档、治疗与强技的回合关系。变化写入行动方案，由生成配置选择；编译器不因楼层达到 15 而暗中增加技能。

四回合周期可通过已有技能编排验证；本阶段不新增独立调息技能。每种变体须证明产生决策差异，而非拖时长或无代价削弱敌人。不新增多阶段状态机。封印单敌、精英及铁甲受保护者双护卫限制继续保留；辅助只获得显式配置的自身词条。

### 祝福（已确认）

五种祝福、上限三次不变，总选择由十次减至九次：入场及通关 2/4/6/8/10/12/14/16 层。取消第 18 层后的选择，避免无宠单修三类主要有效祝福容量只有九层却必须选十次。

节点写入当前配置，不增加版本分派、刷新或放弃补偿。减少一次成长后重新校准 19/20 层，不能宣称与原难度等价。

## 5. 硬切边界

- 不保护旧解释器，不做旧周转换、多版本祝福或跨版本历史评分。内容/schema 标识仅用于识别当前配置、排查和拒绝过期输入。
- 旧塔挑战不续接，旧周配置及塔榜单不作为新玩法数据继续使用。仅针对蜃楼数据，不清空公共 Redis、不影响其他玩法战斗。
- 经核实，塔战斗和占用均读取模式自身 run key；本次切换塔 run 命名空间直接失效旧挑战，没有独立公共占用需要迁移。不恢复旧战。
- 奖励领取记录和已发放资产默认保留；硬切不等于重发奖励。每角色一条记录及事务幂等不变。
- 未上线，本周首次访问可对不同内容版本的周记录重新发布，无需等待下周；不做批量清库。
- 正式开放后再按需要决定内容发布方式，本阶段不预建兼容系统。正式运行的一周内不做无标识的配置热更。

## 6. 开发顺序与验收

1. **内容配置化。** 以当前代表样本作基线，搬出常量与周期，接通配置校验、编译、Host 行动和预览。迁移时可临时对比原输出，最终只保留当前机制测试，不为测试继续保留旧解释器。
2. **配置编排。** 配置候选、铺垫及后半程变体；复用周算法。完整签名包含行动方案的语义身份，不能通过重命名局部敌人 ID 绕过避重；阵容签名仍关注关系与份额。
3. **策略校准。** 金丹物理、法术、控制/辅助路线，有宠/无宠，多固定种子，对比先辅助/先主怪、控制/输出、防御重击/抢攻、空档输出等策略，记录回合、承伤、控制空档及失败点。
4. **流程收口。** 按九次选择调整祝福和末段难度，落实硬切，浏览器完成一趟 20 层，检查刷新恢复、预览、重复领奖、祝福节点和移动端层级。

验收要求：

- 现有能力范围内的周期、参数、属性修正、组合调整只需改配置；不存在新增敌人专用代码分支。
- 引用完整，行为冲突拒绝加载，不以静默优先级吞掉某个行为；预算折扣不重复计算。
- 配置仍紧凑，复用连续周确定性和 16 KiB 体积检查，不保存完整 NPC、技能和预览副本。
- 现有五类机制和后半程变体有可解释的策略价值；不要求手动永远胜过 AUTO，不强制所有构筑同一种打法。
- 不引入跨层血蓝压力，不出现正常满状态基准构筑没有应对窗口却稳定被一轮击杀的组合，不强制稀有解控或灵兽。
- 相关纯共享测试、lint/build、本地完整流程通过。仅在 src/shared 添加符合项目要求的测试，不添加服务端单测或一次性跑分脚本。

普通 2–3、精英 4–5、首领 6–8 回合仅作诊断起点。记录实际完整流程用时，不凭回合推算时长。既有小样本不代表新增验收已完成或统计胜率结论。
