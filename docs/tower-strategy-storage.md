# 蜃楼幻境逐层策略存储

2026-09-19。schema 2 / combat-v6-tower-v5。本文取代第一阶段中“周记录保存完整战斗发布包”的存储描述；第二阶段玩法提案不在此次实施范围。

## 权威与边界

- PostgreSQL `tower_weeks` 每周一行，JSON 仅含 `schemaVersion`、`contentVersion`、`generatorVersion`、`season`、完整有序的 20 个 `floors`。
- 每层保存 `floor`、`kind`、`budget.hpScale` 和 1–3 个 `enemies`。每敌人保存层内唯一 `id`、`archetype`、`role`、独立 `traits`、`budgetShare.hp/output`。
- 原型 warrior / mage / binder / attendant 决定基础行动。leader / striker / support 仅标识定位；治疗、护卫、蓄势、碎梦均需显式词条。
- 护卫配置为 `{ id: "guard", targetEnemyId: "enemy.0" }`；目标可以不是首位敌人。其他词条为 `{ id: "magic_ward" }` 等无自由数值参数的引用。
- 不保存各境界单位、技能、状态、预览或历史周副本；开战只编译当层、当境界。Redis 战斗快照仍保存真实单位、技能、状态与行动计划，恢复不重编译。
- 奖励表不变：每角色一条本周领取记录，转换周配置不更新奖励、榜单和战斗快照。

## 生成、校验、编译

`strategy-templates.ts` 将现有普通层规则和关键层组合展开成 20 层。`weekly.ts` 继续有限枚举、同周组合不重复、至少一个多敌遭遇、近三周软避重及确定性排序。新发布的历史评分使用策略签名，忽略实例 ID 与词条顺序，保留目标关联和预算；不会从签名反查白名单。

`strategy.ts` 校验连续楼层、类型、单个主敌、人数、ID、预算合计、词条重复与冲突、护卫目标及循环引用。生存槽 armor / magic_ward / vital 和节奏槽 swift / seal_resist / charge 各最多一个；charge 与 limited_healing 不可同时替换周期。封印仍限单敌；精英与铁甲受保护者暂不允许双护卫。编译器不依赖组合或阵型 ID。

`strategy-compiler.ts` 使用 v5 固定基准与每敌人的显式词条。阵型生命折扣仅由 `hpScale` 应用一次。厚血对自身生效；为保持旧周完全等价，旧版整组生命池上的厚血会在转换时显式赋给每位同伴。各成员按自身生命池取整，最后位置承担对应池的尾差，避免一个敌人的词条变化影响另一个敌人的气血。

预览由同一策略定义生成，沿用现有 UI 契约；`formationId` 变为可选，当前策略预览不返回该字段。公共战斗界面没有增加塔专属逻辑。

## 版本与转换

v5 的策略语义、文案、技能/状态和数值/等级分别固定在 `strategy.ts`、`strategy-compiler.ts`、`strategy-content-v5.ts`、`strategy-scaling-v5.json`。不得通过修改既有版本来改变已发布周；下次内容变更需增加新版本及对应分派，继续保留旧版本解释器。未知版本拒绝读取，不使用当前默认值。

当前 schema 1 / v4 记录在读取时原位升级：展开原周选择，逐一比较七境界 × 20 层的 units、plans、skills、statusDefs，全部相同才执行 `WHERE schema_version = 1` 的条件更新并重读最终记录。失败包含境界、层数和字段名，不重新抽取。并发升级者共享同一最终行。旧版本实现只供转换与回归；没有新增表或修改现有迁移。

发布部署应切换全部 API 实例到新代码；旧服务不认识 schema 2，不应与新服务混跑。历史重型记录在被访问时转换，不执行全库重写。
