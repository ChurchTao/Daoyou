# 蜃楼幻境重构规格：节奏、敌人与精简交互

状态：设计稿，未实施。用户已认可精简交互方向；本文中的敌人、祝福数值和回合目标是首轮验证提案，不代表已完成平衡或正式上线配置。

## 1. 已确认边界

- 使用正常角色数据与本次爬塔祝福，不维护独立幻境人物、跨层血蓝账本或整局冻结构筑。
- 每层满状态迎战。难度来自敌人、阵容和机制，不来自跨层血蓝消耗。
- 祝福保持简单，以直接数值增益为主。
- 20 层；5、15 层精英，10、20 层首领。先验证前 10 层闭环，再制作后半程。
- 敌人机制只在战前说明。战斗沿用公共 V6 系统与组件，不新增意图栏、倒计时、阶段面板或蜃楼专属战斗播放器。
- 页面做减法：先看到楼层、对手和主操作；详情按需展开。图标能表达的内容不再重复铺文字，但不让玩家猜测关键操作。
- 精简原型只确认信息结构、交互与阅读顺序。正式颜色、字体、按钮、图标、弹层和场景壳遵循游戏现有规范。
- 本轮不加入商店、事件节点、休整经营、复杂分支地图、套装机缘、局外天赋或无尽模式。

保留现有金丹准入、上海时区周一换周、境界榜、四档里程碑及奖励防重规则。奖励内容与经济平衡不在首个实现阶段另起一套。

## 3. 每层角色与资源规则

### 3.1 每场读取正常构筑

- 开战服务端重新读取当前角色、装备、功法、宗门构筑和灵兽阵容，经现有投影装配，再叠加本次祝福。
- 祝福不写入永久六维、物品实例、灵兽资质或正常角色面板。
- 单场开始后继续使用权威战斗快照。刷新恢复同一场战斗，不重新装配、不再次恢复、不重新抽选。
- 层间可调整装备、功法和灵兽；本场未结束或待结算时继续禁止冲突写入。
- 入场境界用于本次难度与榜单归属。为避免突破后使用高境界构筑冲低境界榜，开下一场时境界已变则结束本次挑战，并提示按新境界重新入场。

### 3.2 满状态的实施口径

以下是据已确认方向提出的执行口径，需要在资源接入阶段用现有权威模型逐项验算，不以新建幻境资源表解决：

| 对象 | 入场规则 | 战后及下一层 |
| --- | --- | --- |
| 人物气血、法力 | 正常恢复路径补至当前正常上限，单场以满值装配 | 本场消耗走正常资源写回；下次开战再次补满 |
| 灵兽 | 当前合法阵容按现有投影满状态进入 | 不沿用上一场的局内倒地、死亡标志或血蓝；不新增永久死亡、寿命扣减规则 |
| 单场状态、护盾、特殊战斗资源、战斗伤势 | 按技能与 V6 的开战初始规则生成 | 不跨场携带；“满状态”不等于所有特殊资源都灌满 |
| 永久养成、丹毒、寿元、境界、已有 `condition.statuses` | 不清空、不重置，遵循正常模型 | 本次不添加解除全部现实负面状态的额外功能 |

“满状态”在首版产品文案中特指气血、法力与可出战状态，不承诺清除一切角色长期状态。若长期状态实际影响入场战力，应在既有角色详情中保持真实展示。

- 当前 `full` 投影只能证明战斗单位按满值装配，不能冒充已对正常 `condition` 完成恢复。
- 每层开战恢复作用于正常资源；进入蜃楼可用于恢复是该规则的明确结果，不额外引入收费或反复进出的惩罚来抵消它。
- 恢复仅由有效开战操作触发，不由 GET、战前详情、选祝福、刷新或失败重试触发。
- 入场恢复、战斗创建、终局资源写回分别建立明确幂等边界；事务与 Redis 之间重试不得重复恢复并覆盖已发生的战斗消耗。
- 不在离场时用入境旧值覆盖当前资源。恢复、结算均复用 `ConditionService`、资源事件及现有事务/锁边界。
- 当前 `CombatV6ConditionProjector` 只处理 `wild-encounter`；不能假设蜃楼已自动接入。保留蜃楼已有终局凭据与奖励事务，明确唯一的资源结算拥有者，不增加两个并行写回者。

首版祝福暂不增加最大气血、法力，避免同时引入临时上限解除后的资源折算问题。

## 4. 简单祝福清单

首轮建议五项；所有数值待普通构筑实测，原型中的 `8%` 不是已批准的最终平衡值。

| 图标示例 | 名称 | 每次选择的效果 | 叠加上限建议 |
| --- | --- | --- | --- |
| 💪 | 强攻 | 人物物理攻击 +8% | 3 次 |
| 🔮 | 灵威 | 人物法术攻击 +8% | 3 次 |
| 🛡️ | 坚守 | 人物物理、法术防御各 +8% | 3 次 |
| 👣 | 疾行 | 人物速度 +5% | 3 次 |
| 🐾 | 兽威 | 当前阵容灵兽物理、法术攻击各 +8% | 3 次 |

- 在正常构筑投影后，对明确的目标属性统一加成；同项相加，从未加祝福的基准计算，最后取整，不逐层复利。
- 不做品质、负面代价、组合套装、触发连锁或推荐流派。
- 入场选一次，此后第 2、4、6、8、10、12、14、16、18 层胜利后各选一次。第 20 层直接结算。此频率为减少中断的执行建议。
- 候选由服务端生成并保存，刷新不重抽；剔除已满层项。未满层项不足三个时展示实际数量，不补假选项；全部满层则直接继续。
- 无合法灵兽阵容时不出现兽威；已经获得的兽威在之后换上合法灵兽时仍生效。
- 默认显示图标与总增益，点击显示准确属性和作用对象。选择时保留短属性名，不能只靠 emoji 区分物理、法术与双防。
- 不保留吐纳回元、周天流转等跨层恢复祝福，不把它们变成无效选项。

## 5. 前 10 层遭遇设计

第一章围绕“蓄势、破绽、拆除辅助”展开。每层仍然是一场战斗，不加入层间事件。

| 层 | 阵容提案 | 首次出现的决策 / 本层重点 | 战前短提示 |
| --- | --- | --- | --- |
| 1 | 蜃影剑卫 ×1 | 熟悉敌人的单体攻击 | 单体攻击 |
| 2 | 蜃影剑卫 ×2 | 集火，尽快减少敌方行动次数 | 双卫夹击 |
| 3 | 碎镜术士 ×1 | 群体法术后有弱点窗口 | 群法 · 施法后破绽 |
| 4 | 蜃影剑卫＋执灯幻侍 | 先压输出还是先拆治疗 | 幻侍疗伤 |
| 5 | 精英：负碑蜃卫 ×1 | 防御危险回合，在破绽期爆发 | 蓄势重击 · 出手后破绽 |
| 6 | 高阶蜃影剑卫 ×2 | 提高基础压力，战斗保持短促 | 双卫夹击 |
| 7 | 碎镜术士＋执灯幻侍 | 群攻压力与治疗配合，决定击杀顺序 | 群法 · 幻侍疗伤 |
| 8 | 护镜傀＋镜侍 ×1 | 第一次拆除减伤来源 | 镜侍护主 |
| 9 | 护镜傀＋镜侍 ×2 | 分配输出，理解两名镜侍的贡献 | 双侍护主 |
| 10 | 首领：照影镜主＋镜侍 ×2 | 拆除保护、处理群法、安排末段爆发 | 镜侍护主 · 群体法术 |

### 5.1 普通敌人原型

- **蜃影剑卫**：普通攻击为主，保留一招较强的单体攻击；不叠加额外控制、吸蓝、反伤等特征。
- **碎镜术士**：群法后获得短暂防御降低；普通层只介绍“高威胁出手带来反击窗口”。技能耗蓝必须覆盖目标战斗时长。
- **执灯幻侍**：治疗受伤同伴，其余时间进行弱攻击；治疗量与资源限制不能把普通层拖成无限续航战。
- **护镜傀**：基础单体攻击，承接镜侍保护；不另外附加精英级机制。
- **镜侍**：弱攻击并维持对指定守护对象的减伤；易被集火击破。角色和灵兽均可以有效攻击它，不要求特定宗门或驱散技能。

镜侍与其保护对象使用明确的战斗单位关联。每名存活镜侍提供 15% 减伤、总计最多 30% 为首轮提案；按回合开始时存活关系刷新，击杀镜侍后下一回合减伤降低。详情必须说清这一时点，不能宣称即时解除。原语是否支持这种关联须先验证，不依赖客户端补算。

### 5.2 第 5 层：负碑蜃卫

核心是一道可重复学习的题：蓄势 → 重击 → 破绽。

| 回合节拍 | 行为 | 可用应对 |
| --- | --- | --- |
| 1、4、7…… | 蓄势，不造成重击伤害 | 输出、调整目标、准备防御 |
| 2、5、8…… | 单体物理重击 | 防御、保护、合法控制或提前击杀 |
| 3、6、9…… | 弱攻击，降低自身防御 | 集中输出 |

- 节拍按回合确定，受控制时跳过当回合受限行动，不把被跳过的重击偷偷延后到破绽回合。
- 蓄势、重击和破绽通过现有技能、状态、日志表达，不额外绘制战斗提示。
- 重击不得在匹配难度的正常满血构筑上无解秒杀；防守选择应明显改善结果。
- 不赋予全面控制免疫。控制构筑能够推迟伤害，防御/保护也必须是可行解法。
- 重击系数、破绽幅度和速度先做小范围验证后定稿，避免假设所有玩家都能先手。

### 5.3 第 10 层：照影镜主

固定开场：本体＋两名镜侍，不做动态召怪和无限补员。

- 镜侍提供本体减伤，规则与第 8、9 层一致；击杀镜侍减少敌方行动与后续减伤。
- 本体以普通单体攻击为基础，每第三回合尝试施放群体法术；战前详情说明固定周期。
- 本体在回合开始时气血首次不高于 40% 后，进入本场持续的进攻状态，攻击提升 15% 为首轮提案。
- 转阶段不清空伤害、不复活镜侍、不突然插入额外行动，也不改变已说明的群法周期。
- 机制允许先拆镜侍，也允许足够强的爆发构筑带着减伤攻击本体；不设置硬性职业钥匙。
- 现有公共防御/保护对物理和法术的作用需分别核对；详情不能笼统保证“防御能化解所有群法”。

所有百分比和周期均需在内容实现后实测。首领的目标是更丰富的决策，而不是用高血量延长普通攻击循环。

### 5.4 机制可实现性门槛

先以现有 `SkillDef`、`StatusDef`、条件、回合钩子、资源和普通命令验证下列三件事：

1. 蓄势、重击、破绽能否遵守固定节拍，控制和目标失效时行为仍符合战前说明。
2. 镜侍保护能否正确绑定目标、随来源死亡解除且刷新恢复一致。
3. 低血量阶段能否在规定回合边界触发一次，避免同回合因出手顺序反复变化。

公共 AUTO 是效用选招，不能假设其一定选择蓄势或按预定回合使用技能。优先使用已有合法性条件和状态表达；若无法满足，单独给出最小 NPC 选招接入方案后再决定，不恢复历史 rotation 字段、不在 core 写楼层或 BOSS ID 分支，也不改公共战斗 UI。

若需要的运行能力超出当前引擎，明确缩小敌人机制或讨论那项扩展，不把未支持的机制当成已落地配置。

## 6. 难度与节奏验收

具体定标方法见 [数值缩放设计](tower-scaling-design.md)：固定大境界参考构筑，先确定整场生存/输出预算，再分配阵容；双防、速度、命中、修炼采用各自的规则。该文的参数均为首轮提案，不能视为已通过实战的正式数值。

- 普通层目标 2—3 回合，精英 4—5 回合，首领 6—8 回合，均为初始调试目标，不是强制回合限制。
- 同一难度档位随层数提高基础威胁预算，预算分配到人数、攻击、生存和辅助能力；不能把双人阵容简单理解为每人都用单体 BOSS 属性。
- 精英后可以有短促战斗，但正常层之间基础压力仍应上升；避免每层同时提高人数、速度、伤害与机制复杂度。
- 难度按本次入场境界固定，不根据局内祝福实时追涨敌人，让成长能带来优势。
- 扩展 11—20 层时检查现有阶段从圆满回到初期引起的数值落差，不能仅靠 `floorGrowth` 宣称单调变强。
- 使用正常可获得的物理、法术、控制/辅助构筑和不同灵兽验证；记录通关回合、失败点、关键技能使用、祝福选择。
- 强化测试角色只用于流程验收，不作为平衡证据。高养成允许碾压低层，不为强行展示机制而普遍加无敌或锁血。

## 7. 页面真实落地规范

### 7.1 原型保留什么

- 入口：一处场景意象、一个入境操作，最佳层数作为次要信息。
- 备战：楼层、对手形象/名称、精英或首领短标识、一行可展开机制、祝福图标、迎战操作。
- 祝福：三选一，图标＋短属性名＋增益；选中反馈与确认操作清楚，不增加长段教学。
- 结算：通过层数、结果与重新入境操作；已获奖励可按需查看。
- 奖励、榜单、规则、主动结束挑战放在辅助入口，不常驻展开。
- 战斗直接跳转公共页面；不把原型“查看战后祝福/查看结算”的演示按钮带入产品。

机制摘要一行默认可见，完整解释点击展开。关键含义不依赖悬停；图标入口具备可访问名称，触屏可点击查看。

### 7.2 美术与组件映射：强约束

依据 [游戏 UI 技能](../.agents/skills/daoyou-game-ui/SKILL.md)、[图标规范](game-icons.md)、[数字排版](numeric-typography.md) 和 [布局归属](game-layout-ownership.md)。

| 职责 | 正式实现 |
| --- | --- |
| 页面身份与骨架 | 保留 `GameViewportLayout` 下的 `GameSceneFrame` 与现有 scene metadata；正文不再画第二个“蜃楼幻境”标题，也不复制全局 dock |
| 背景与正文 | 复用现有宣纸背景，正文 `text-ink`，次级 `text-ink-secondary`；不照搬原型的独立纸色、青灰色与自定义主题变量 |
| 主操作 | `InkButton variant="primary"`；沿用朱砂色文字和方括号形态，不照搬原型深色实心按钮 |
| 次级操作 | 复用 `InkButton` 的 secondary / ghost / outline 等已有变体；不另造一套按钮状态 |
| 色彩语义 | 使用 `paper/bgpaper`、`ink`、`crimson`、`teal` 等现有 token；朱砂用于主操作/重点，绿色用于适当的正向反馈，避免所有标签都有颜色 |
| 字体 | 场景标题由壳层承担既有标题字体；正文继承游戏正文字体，不拷贝原型系统字体栈，不给敌人名另加书法大标题 |
| 数字 | 层数、祝福增益使用 Tailwind 默认 `font-mono`，权重与间距局部设置，不新增 `.num` 或覆盖 `--font-mono` |
| emoji / 图片 | 均经 `GameIcon`；emoji 直接传值，图片统一注册 `icon:名称`，不复制原型的大 emoji 尺寸作为固定像素规范 |
| 祝福说明 | 优先 `InkTooltip`，使用已有键盘、悬停及触屏行为；选择项保留简短文字标签 |
| 机制详情 | 简短原生展开交互或已有说明弹层；不重新制造嵌套卡片、提示区与多层外框 |
| 奖励与榜单 | 复用 `InkModal` 或现有 `useInkUI` 弹层能力；奖励涉及物品预览时继续遵循物品预览技能 |
| 确认、错误、加载 | 复用现有 dialog / pending / 加载能力；正常状态简洁，异常时必须保留清楚的恢复入口 |

`GameSceneFrame` 已拥有纸面、身份层和默认分隔；调用方不能为追求原型像素一致叠加另一层全页纸面、标题或边框。`GameSceneSection` 在确有分组时使用，不为每行信息各建 section。

组件没有所需能力时，先找同类页面的现有用法；确有必要才增加局部页面组件，不给全局壳透传蜃楼专用样式参数。

### 7.3 UI 验收

- 首屏无需阅读规则就能识别对手并点击迎战，只有一个主操作重心。
- 可展开机制与图标详情可被发现，触屏与键盘均能访问。
- 不出现常驻楼层轴、历史榜单大表、血蓝账本、角色面板或重复状态说明。
- 320/360px 窄屏与桌面均无溢出，祝福选项的作用对象和增益清楚；必要时换行，不无限缩小文字。
- 按钮、色彩、字体、图标、弹层与其他游戏场景一致；精简不通过绕开公共组件实现。
- 检查 [主流程审查表](../.agents/skills/daoyou-game-ui/references/viewport-checklist.md)，确认 HUD、聊天偏移和全局导航保持正常。

## 8. 状态、契约与恢复

- 保留 runId / revision / floor / highestFloor / blessings / choices / reason、赛季归属、内容版本和当前单场引用；不持久化第二份普通角色。
- `READY` 与 `CHOOSING_BLESSING` 可以访问正常角色调整；活动战斗和未完成结算仍占用角色。逐个审计 `hasActiveTower` 调用方，不直接把整局函数改成只查 battleId 影响全部业务。
- 不允许同时开启其他冲突战斗。需要区分“可调整构筑”和“可开始另一个活动”，不能一次放开所有占用。
- 战前敌人描述、图标、机制摘要与详情由权威内容生成，和本场敌人使用同一内容版本，前端不另写一份敌人规则。
- 刷新不得重抽祝福、重复开战或重复发奖；败北、逃跑、平局和主动结束继续区分。
- 结算失败保留同一终局，沿用重试入口；不能为了界面简洁隐藏“待结算”导致玩家误开新战。
- 沿用 Redis 权威活动状态和现有持久终局凭据，不在本阶段新增数据库周进度表。
- 内容改版必须绑定版本。发布前为旧活动局与旧祝福指定显式结束/兼容策略，不将旧 ID 静默解释为新效果；旧周领奖记录不能因换内容被无意清除。

## 9. 实施顺序与验收门槛

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| A：机制小样 | 精英节拍、镜侍关联、首领阶段的纯内容/规则验证 | 与战前说明一致；公共战斗可表达；列清真实能力缺口 |
| B：状态简化 | 当前构筑装配、满状态开战、资源写回与占用拆分 | 调整下一场生效；重试不重复恢复；单场快照与结算不受影响 |
| C：前 10 层闭环 | 敌人表、简单祝福、真实精简页面 | 入境至第 10 层及失败分支可实际操作，UI 使用项目 token 和公共组件 |
| D：节奏校准 | 正常构筑实战记录与调整 | 普通层短促，精英/BOSS 有决策，不依赖高血量拖时长 |
| E：扩展 20 层 | 第二章、15/20 层机制、完整回归 | 延续学习节奏，数值曲线、周奖励与排行榜完整 |

前 10 层小样通过前，不把新的 10 层临时验证终点改成正式 20 层通关规则，也不把缺乏设计的后 10 层宣称为新版完整体验。

实现阶段的检查：

- 纯共享逻辑：针对祝福叠加、满值装配、敌人机制、候选抽取和快照恢复添加有意义的确定性测试。
- 前后端：运行 `bun run lint`、`bun run build`；按波及范围运行聚焦共享测试，广泛改动再运行 `bun run test`。
- 按 `docs/testing.md` 使用本地测试账号进行浏览器验收：入口/备战/祝福/结算、图标详情、刷新、层间换装换宠、待结算重试、重复点击、满状态与现实资源一致性、320/360px 与桌面布局。
- 不新增 server / React 单元测试，也不新增一次性 E2E、seed 或故障脚本；不使用预发布/生产测试写入。
