# 蜃楼幻境完善清单

日期：2026-09-19。基于当前工作区 `combat-v6-tower-v3` 代码核对。本文是下一阶段建议，不代表下述新增能力已经实现，也不修改已确认玩法边界。

## 1. 判断与范围

当前已具备可玩的首轮闭环：正常构筑、每场满状态、五种简单祝福、20 层、固定周表、多敌阵容、战前预览和公共 V6 战斗。下一阶段应补齐内容的策略价值、整周编排、完整难度验证与发布可靠性。

继续保持：5/15 层精英、10/20 层首领；各境界共享周主题、独立固定数值基准；不按玩家动态缩放；机制只在战前解释；不添加复杂祝福、商店、事件、独立资源账本或专属战斗组件。

优先级：P0 为稳定开放前必须处理或验证；P1 为本轮玩法完整度需要；P2 为后续可选扩展。小池可以先上线，未经校准的内容不能因为配置可编译就视作已验收。

## 3. 词条与组合的最小完善方案

### 内容组织

保持四层结构：主套路、特性、阵容、已批准的完整遭遇。

- 主套路负责技能、目标选择、行动周期和玩家应对方式。
- 生存与节奏特性只提供固定模板，不独立随机强度，也不额外藏技能。
- 阵容负责人数、角色、生命/输出份额、配合关系和关联终止条件。
- 完整遭遇绑定前三者、适用楼层类型和已校准参数；只有批准的完整遭遇进入周池。

抽取单位建议统一为完整遭遇ID，避免先抽主怪后拼随从时绕过整体平衡。原有模块仍可复用，不需要通用规则语言、编辑器或自动组合所有排列。

每条新内容至少写明：稳定ID、短名、实际行为、作用对象、周期/持续时间、应对窗口、互斥条件、固定预算修正和战前说明。配置可以使用类型化TS；只有确实需要数据维护的部分再进入JSON与Schema。

### 扩池顺序

1. 先给现有六个主组合和合法阵容建立完整清单，保留现有禁配。
2. 验证同套路的不同阵容是否改变玩家决策，而非仅改变敌人数。
3. 优先补物理与术法的行为差异；数量由轮转约束决定，不预设必须填满多少词条。
4. 封印随从、双核心敌人等另行验证后扩展，不为表面丰富度放开封印加爆发/治疗。

新机制须能通过公共V6命令、状态与日志理解。无法在现有系统中表达应对窗口时，应缩小设计，不新增蜃楼专属战斗UI。

## 4. 组合设计必须验证玩家决策

机制测试证明规则正确，策略验证证明规则值得玩家关注，两者不同。

| 遭遇 | 需要比较的打法 | 验收关注点 |
| --- | --- | --- |
| 主攻＋治疗 | 先辅助、先主攻、控制辅助 | 治疗在正常战长内有机会发生；拆辅助或压制治疗在部分构筑上有实际收益 |
| 主攻＋镜侍 | 拆一只、拆两只、强攻主怪、群攻 | 减伤与辅助血量形成取舍；避免所有构筑都必定选择同一路线 |
| 蓄势重击 | 持续输出、重击前防御/保护、控制跳过重击 | 玩家能实际降低风险，且重击后破绽足以支持反击 |
| 法术波次 | 保护脆弱目标、压制施法者、破绽期输出 | 两目标法术对不同灵兽阵容的总压力合理 |
| 周期封印 | 抗封、普通攻击/保护、空档期输出 | 每周期有实际行动窗口；不强制稀有解控或特定宗门 |

不要求所有遭遇都必须先杀辅助，也不要求手动操作全部获胜。需要证明至少存在几类可解释的策略差异，不能只用公共AUTO通关作为玩法质量验收。

补查敌人选目标规则：当前Host使用可选目标列表，显式最低血量治疗除外；若未来主张“追击”“集火”等特色，必须有对应明确规则和战前说明。首版无需实现复杂智能AI。

## 5. 周次抽取与轮转

### 保留的硬约束

- 同周同层、所有玩家及境界共享同一完整遭遇主题。
- 5/15层主套路不同，10/20层主套路不同；四个关键层不重复完整遭遇。
- 同层相邻周主套路变化；每周至少一个多敌关键层。
- 只抽已批准、已覆盖开放境界的组合；不根据当前玩家构筑选敌人。
- 刷新、重开不改变周表；战斗RNG与周抽取独立。

### 建议新增的软目标

- 减少同一阵容连续出现及整周阵容同质化。
- 尽量避免完整遭遇在短期内重复；优先改变10/20层的策略体验。
- 在一个有限轮转周期内，让已批准内容有合理的出场机会。
- 多敌保底位置分散，不始终向最前方可用楼层倾斜。

软目标不能凌驾兼容性：当前封印只有单敌，不应要求每个位置阵容必定跨周不同。六套小池也不支持对所有遭遇任意设置长冷却。

### 推荐生成流程

批准遭遇池 → 保留三周主套路骨架 → 枚举满足硬约束的四层周表 → 根据近期完整遭遇/阵容重复情况排序 → 以周标识和生成器版本确定性选取 → 发布固定周表。

当前小池采用有界枚举即可，不需要无限重抽或复杂求解器。若未来池变大，再按实测规模调整。

首次发布前模拟跨年连续周，检查确定性、可解性、重复间隔、遭遇频率和阵容分布。静态小池已能满足现有规则，不必只为“完善”额外搭备用系统；新增冷却、权重或开关后，才需要为新增无解情况提供经过验证的备用表。

无需新增轮转后台或手工每周排表。可按固定发布周期预计算有限周表，或将所需近期周表作为生成输入；不要从当前周无界递归追溯历史。

## 6. 普通层与后十层

当前普通层按十层重复。建议保留大部分固定教学层，仅让少量关键层前的普通遭遇关联当周机制。

- 1–4：短战斗、认识目标选择，精英前出现一个低压力相关机制。
- 5：单一核心机制的精英检验。
- 6–9：引入拆辅助或保护关系，为首领做准备。
- 10：首次完整组合检验。
- 11–14：短战斗恢复节奏，练习本周后半段机制。
- 15：提高配合要求，不同时堆多个新概念。
- 16–19：已有机制的有限组合，为最终层做准备。
- 20：本周最完整的一场战斗，可用一种可控的节拍/配合变化形成结尾感。

具体15/20层变体须另列批准内容，不能宣称当前已存在第二章机制。也不必强迫每层严格高于上一层：精英/首领之后普通层应该回落，整体压力逐段提高。

验收需同时看每场回合、整趟操作次数与实际时长。先测完整20层，再确定目标区间；避免预设不符合公共战斗播放速度的分钟数。

## 7. 数值与祝福

- 整场预算不等于技能周期伤害已经等价。当前攻击按参照防御之上的差值分配；多段、群法、固定技能威力、辅助弱攻击、击杀后的行动数变化仍需真实引擎验算。
- 三次治疗和镜侍减伤已有限制，但0.9/0.8生命折价只是固定起点，不能替代有效生存验证。
- 验证生命/输出曲线、暴击峰值、先手关系、封印空档、单体与群攻对不同人数的收益。
- 参考矩阵覆盖开放境界、早中晚养成、物理/法术/控制辅助路线、有宠/无宠、1/5/10/15/20层及必要的普通过渡层。
- 每组使用多个固定种子，记录回合数、失败点、剩余资源和策略选择；正常配置不是必须全胜，但不得因合法组合产生无法行动或无实际应对的局面。
- 五种祝福继续保持简单。先处理十次选择与有效容量的关系，可选最小方案包括调整末段选择节奏、允许放弃，或调整少量上限；应结合平衡结果选一个方案，不同时增加多种补偿机制。
- 当前祝福候选绑定runId，重开会变，这是现状而非漏洞定论。建议首版保留局内变化；需评估是否出现反复重开刷开局祝福的明显收益，只有影响体验时再调整。

现有平衡证据是金丹三条参考路线、1/5/10层、合法组合阵容、固定种子42的69场样本。不能据此声称已完成所有境界、完整20层或统计胜率验证。

## 8. 发布、跨周、奖励与榜单

### 已发现的实现边界

1. `currentWeek` 的缓存key包含内容版本，榜单key不包含内容版本。版本更新后可以在同一赛季产生新周表。建议普通内容更新下周生效；当前周继续使用已发布内容与相应解释器。紧急改动单独处理，不能悄悄混排不同条件的成绩。
2. 当前 `getTowerView` 对结束挑战使用当前周预览，但 `publicView` 仍返回旧run的season。建议明确当前周入口信息与上次挑战结果的归属，复用现有详情/结果页，不增加常驻面板。
3. 周表只保存组合ID，不冻结所有将来用于新战斗的定义。需绑定遭遇包、数值包和生成器版本，或保存足够的发布快照；当前单场快照已冻结，继续沿用。
4. 周奖励已具备同一战斗的SQL归档防重，但跨挑战的周已领列表读取Redis。需要确认缓存丢失/恢复后如何从耐久记录还原周领奖事实，不能将同一战斗幂等等同于整个赛季领奖幂等。
5. 榜单更新失败目前只记录日志。需要可重复补写最高层记录的恢复路径，不必另建一套消息基础设施。
6. 当前挑战和榜单到周末后额外保留一天；跨周在途战斗、延迟结算及超过保留期的处置需要明确并实测。不能无条件承诺离线多久都能继续旧战。

### 保持简单的产品口径

- 普通内容更新下周生效；新周开始后不再开启旧周下一层。
- 旧周已开的战斗按原快照处理，收益和成绩归属旧周，遵循明确的结算有效期。
- 每角色每周每里程碑一次；突破换境界不重置本周已领资格。
- 现有榜单是最高层优先、同层先到优先，适合周常进度记录。暂不新增速度榜、回合榜、积分兑换或专属商店。
- 重试允许，奖励不重复；退出与失败保留已获奖励；页面仅在相关状态说明。

上述问题应优先复用现有归档、资源事务与恢复能力，实施前再判断是否确实需要新增持久化字段。

## 9. 验收与后续顺序

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| A：规则收口 | 完整遭遇清单、禁配矩阵、周轮转规则、发布/跨周口径 | 每套内容都能说明玩家决策；生成规则有解；明确上线数值覆盖范围 |
| B：实现补齐 | 批准池与周编排、版本冻结、周展示修正、结算与榜单恢复补缺 | 确定性与不变量测试通过；当前周内容稳定；恢复路径可检查 |
| C：完整玩法 | 普通层铺垫、15/20层有限变体、祝福选择收口 | 20层有节奏变化，策略选择确实产生收益 |
| D：上线验收 | 全开放境界参考样本、多种子结果、完整浏览器流程与简明观察指标 | 构筑/阵容/周边界验收有证据；未完成项不冒充已平衡 |

共享纯逻辑使用现有Vitest；页面、服务端、数据库与Redis使用代码检查和项目规范允许的浏览器/运行验收。不得新增一次性benchmark、seed、故障注入脚本或服务端单元测试。

运行验收应覆盖：完整20层、失败/平局/退出、战中刷新、重复请求、层间换装换宠、突破后入场规则、跨周/跨年、版本更新、结算重试、奖励防重、榜单补写、移动端各关键页态。故障场景应使用既有受支持手段验证，缺少可用手段时注明未验收。

本次仅代码与文档梳理，新增本文，未修改玩法代码；检查Markdown与 `git diff --check`，未重跑lint/build/测试。既有验证结果参考重构规格第11节。
