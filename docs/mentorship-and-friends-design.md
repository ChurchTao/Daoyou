# 师徒好友与私聊系统设计和实现计划

日期：2026-11-13。状态：已实现并完成重点本地验收，未部署生产。验收记录见文末。

将师徒和好友建设为两个独立系统。好友承载结缘、名录和一对一私聊；师徒承载拜师收徒、授业、个人成长和出师；系统传音继续负责信件与附件投递，作为好友列表的置顶会话。底栏「传音」统一进入好友和传音工作区，师徒保留展开导航入口，师徒交流复用好友私聊，不产生第二份聊天记录。

首版由化神及以上角色收徒，拜师时徒弟必须低于元婴。出师固定检查当前角色境界、功法、宗门心法和炼体，不选择任务。账号首次拜师后永久记录，不允许通过解除、删角、转世或师父离去重新拜师。师徒交流复用好友私聊，成功出师结算双向声望并公告，成就可选入名片展示。

## 1 交付范围和当前依据

| 系统 | 首版交付 | 后续扩展 |
| --- | --- | --- |
| 好友 | 独立页面、名录、搜索和邀请、双向申请、删除、账号屏蔽 | 分组备注、公开名片的更多社交能力 |
| 私聊 | 文字、持久历史、离线读取、未读、多端同步、失败重试、断线补拉 | 物品和战报分享、回复、举报处理工作流 |
| 师徒 | 独立页面、寻师收徒、双向确认、授业目标、成长记录、自主出师、解除、桃李簿 | 专属外观、称号权益、专题授业、师门谱系 |
| 传音 | 收发信件、系统信、领取附件、给好友投递物品 | 本次不扩展新的附件或交易能力 |

首版不引入师门群聊、多人云游秘境、直接传修为、师父收益抽成或额外战斗属性。现有组队讨伐可作为双方自愿参加的活动，不作为出师门槛。

以下是实施前核对的代码事实，决定本次复用和替换的范围：

| 当前实现 | 设计约束 |
| --- | --- |
| 好友按角色保存，成立时写双向关系；单方添加直接成立 | 新关系增加申请确认，保留既有好友；不能照搬原 POST 直接完成的语义 |
| 每角色最多 200 好友，完整道号搜索，搜索冷却 3 秒 | 首版保留限制，不混入模糊全服搜索与全新推荐基础设施 |
| 好友管理位于传音页 `tab=friends`，其他页面共用 `FriendTargetModal` | 页面、弹层、邀请链接和所有调用方要一起迁移 |
| 世界和宗门聊天已有 PostgreSQL 历史、提交顺序水位、幂等发送和事务 outbox | 借鉴机制；私聊另建表和鉴权，不进入公开频道查询 |
| 统一 `/api/realtime` 已支持跨实例通知；业务发送主要走 HTTP | 继续 HTTP 写入、现有 WS 接收通知，不新建聊天连接 |
| 存在物理删角、死亡、转世和跨服状态 | 历史归属与账号防重奖不能依赖角色级联存活 |
| 角色称号是可编辑字符串，现有声望是游戏资源 | 师徒荣誉单独展示，不冒充已有称号解锁或写入 `reputation` |

实现入口见文末。旧文档 `channel-chat-redesign.md` 将私聊排除在当时范围之外，本方案接续其范围；现状以代码为准。

## 2 入口和页面分工

### 2.1 导航与地址

核心底栏保持四项：角色、储物袋、洞府、传音。「传音」进入好友与私聊工作区；系统传音置顶，点击后在同一工作区阅读邮件。展开导航「交游」只保留带图标的师徒入口，好友和邮件不重复列出，世界传音由常驻聊天预览条进入。成就保留在修行分组并补齐图标；修仙日志与探险札记仍属于见闻。邮件未读、私聊未读和好友申请汇总在「传音」红点，师徒待办提示展开红点。

| 地址 | 场景 | 首屏任务 |
| --- | --- | --- |
| `/game/friends`、`/game/friends?chat=会话ID` | `friends` | 一体化道友列表与私聊，选定道友原地交流 |
| `/game/friends?chat=system-mail` | 同属 `friends` | 选中置顶系统传音，在右侧信件目录选信、原位阅读正文和领取附件 |
| `/game/friends?chat=会话ID&composeTo=道友ID` | 同属 `friends` | 保留当前私聊，打开固定收件人的赠物弹层 |
| `/game/friends/chat/:conversationId` | 保留 `friends-chat` 兼容入口 | replace 到统一工作区的 `?chat=会话ID` |
| `/game/mentorship` | `mentorship` | 当前师徒关系、正在进行的目标、下一步操作 |
| `/game/mail` | 兼容跳转，无独立场景 | replace 到统一工作区的 `?chat=system-mail`，迁移已识别参数 |
| `/game/world-chat` | 保留现有场景 | 世界、宗门与系统频道 |

全部沿用真实路由树中的 `GameViewportLayout`。在 `gameNavigation.ts` 声明私聊场景属于好友入口，详情页保持底栏激活状态；不另外按 pathname 维护一套注册表。

`viewport/social.tsx` 位于现有 viewport 路由数组末尾。旧 `mail` 路由保留在原数组位置，仅负责兼容跳转，以免改变已有隐式路由 ID；移除独立 `mail` 场景元数据。

### 2.2 好友与私聊页面

好友与最近会话合并为同一列表，已结缘但还没聊过的好友也直接可选；历史或非好友会话保留在“其他会话”。系统传音固定置顶并显示邮件未读数，好友行内只保留道号、真实最后一句、时间和未读数，不设列表搜索框。结缘申请、寻访、分享链接和屏蔽管理通过独立面板进入，移出、屏蔽和师徒操作收进选定道友资料。

桌面在同一个工作区左侧选道友或系统传音、右侧显示对应内容；360px窄屏原地切换列表与会话。消息使用与世界聊天共享的头像、姓名时间、连续发言、本人底纹、日期分隔和输入组件，桌面Enter发送、Shift+Enter换行，输入法组合时不发送；接近字数上限才提示计数。按会话保留草稿、待确认发送和阅读锚点，提供回到最新与返回刚才位置。赠物通过“传音赠物”进入原流程。

从私聊赠物使用 `/game/friends?chat=会话ID&composeTo=目标角色ID`，参数值通过 `encodeURIComponent` 编码。工作区父级打开固定收件人的赠物弹层，底层仍保留原私聊与草稿，不切到系统传音。正文和附件在同一发送区核对，发送前显示传音符费用、所选附件和数量；提交时重新校验好友、角色、屏蔽及物品 revision。目标失效时给出错误，绝不回落到默认第一位好友。

师徒页面的“私聊”进入同一会话地址，消息不带可由客户端任意填写的“师徒专用权限”。

### 2.3 传音会话和旧链接

系统传音作为工作区内的置顶会话，保留一封一封的邮件形式。首次进入显示精简信件目录，每行包含标题、时间、简短预览及有意义的未读、附件状态，目录只展示摘要。选定后在同一工作区原位读信，不打开独立邮件页；完整正文与附件属于当前信件，上一封、下一封和返回目录操作保持当前阅读上下文。返回目录、读取更多信件、刷新和切换会话保留已选信件及阅读位置，不把当前加载页当作全邮箱统计。

当前信件完整展示正文、附件网格和领取操作，附件继续使用共享物品预览。单封领取后原位显示已领取，保留信件正文与附件；失败原因紧邻原操作。「领取全部」和「全部已读」直接放在系统传音顶部，窄屏紧凑单行排列，沿用领取主操作与已读次操作的层级。只有当前打开的信件在文档可见、窗口聚焦且未被赠物或其他弹层遮挡时才自动标记已读；滚动信件目录、隐藏会话、仅收到推送和仅打开好友列表都不算读过。

系统传音不设发信入口。赠物在好友会话中处理，无目标的传音符入口先选择好友，再打开工作区父级的固定收件人弹层。收件人选择消费好友数据，不负责增删好友；传音符费用、附件扣除、物品 revision 和领取规则沿用原链路。

旧 `/game/mail?tab=friends` 使用 replace 跳到 `/game/friends`；旧地址包含 `addFriend` 时，转为 `/game/friends?addFriend=...`。普通 `/game/mail` replace 到 `/game/friends?chat=system-mail`；旧赠物地址中的 `composeTo` 配合 `conversation` 迁移为 `?chat=会话ID&composeTo=道友ID`，缺少会话 ID 时仍打开指定好友的赠物弹层，不将任意 `returnTo` 当可跳转地址。

新邀请链接只生成好友地址。打开链接展示目标身份和申请动作，GET 不自动加好友或拜师。讨伐领奖收件链接直接进入系统传音会话，普通 `/game/mail` 旧书签继续有效。新邮件和赠物链接统一复用 `lib/social/mailNavigation.ts` 的 `SYSTEM_MAIL_HREF` 与 `mailGiftHref`，保留值 `system-mail` 不作为私聊会话 ID 请求服务端。

## 3 好友关系和申请

### 3.1 建立关系

新增好友采用“发起申请、对方接受”的流程。角色名片、聊天头像、讨伐聊天和分享链接共用同一套关系状态与操作。

申请状态为 `pending → accepted / rejected / cancelled / expired`。同一规范化角色对最多一个未决申请；双方互发时，第二位玩家看到收到的申请，并明确选择接受，不暗中创建第二条关系。申请有效期七天，接受时才占用好友名额。

接受事务重新检查双方角色活跃、账号不同、未屏蔽、双方好友容量及申请 revision，再写原好友表的双向关系。双方都无需为接受申请消耗传音符。

保留现有好友名单，不要求所有老玩家重新确认。上线提示“好友现已支持私聊，可删除或屏蔽不希望联系的道友”；旧记录只代表既有关系，不宣称它们曾经过双向申请。

首版建议每账号每天最多主动申请 20 次，被拒绝后同一对象 24 小时内不能重发。接受、撤回和合法重试不重复扣申请额度。过期由服务端时间判定，清理作业迟到不使过期请求恢复可接受。

同对旧请求已到期但尚未清理时，新申请事务先终结旧请求再创建，不能被未决唯一索引一直挡住。角色对、账号归属、期限和配额均由服务端判断。

### 3.2 删除和屏蔽

删除好友仍双向移除关系。双方可阅读原私聊，停止新发送；重新成为好友后复用原会话。删除不撤回已投递邮件，也不重新转移其附件。

屏蔽采用账号范围，目标账号由服务端从目标角色解析，前端不需要获得或指定对方账号 ID。屏蔽后停止新私聊、好友或拜师申请、玩家传音及定向寄售等直接联系；同时取消双方未决请求、结束在授师徒并释放名额。既有邮件附件与已成立交易按原规则结算，屏蔽不引发退货、复制或资金回滚。

屏蔽事务删除双方账号之间各角色对的双向好友关系。解除屏蔽只移除屏蔽记录，重新联系仍需申请。私聊、玩家传音和定向寄售入口统一检查账号屏蔽，不仅依赖好友行是否存在；待发布的直接联系通知也重新核对，不能在屏蔽后继续提醒。

被屏蔽一方收到通用的“当前无法联系该道友”，不返回对方屏蔽设置。解除屏蔽不自动恢复好友或师徒。公开频道不因屏蔽删除公共消息，首版也不承诺跨所有公开频道的隐藏功能。

好友删除和屏蔽的确认区提前说明师徒后果。删除好友保留师徒，但暂停新的授业互动；师徒页提供“重新申请好友”和“解除师徒”，徒弟个人目标和出师继续进行。屏蔽会直接结束在授关系。

## 4 私聊规则和消息体验

### 4.1 身份和权限

会话按双方原角色 ID 规范化后唯一，一对角色只有一份会话。成员额外保存账号归属与道号快照，角色被删后仍能确定历史归属。

读取使用登录账号鉴权，必须确为会话成员。发送还要求当前活跃角色就是该会话成员，双方角色均可互动、好友成立且没有账号屏蔽。只有师徒身份不能绕过好友私聊权限。

死亡或删角使旧角色会话只读，原账号可在“历史会话”查看。转世后的角色不会自动成为前世好友，也不能继续用前世身份发送。跨服不建立远端私聊；转出准备期停发，回退后按真实角色和好友状态恢复，确认离服后只读。

### 4.2 首版内容和保留期

支持 1 至 500 个 Unicode 字符的纯文字和换行，免费发送。复用确定性文本过滤，按纯文本渲染，不开放 HTML、任意 Markdown、图片、文件、红包或物品转移。首版不提供对方已读回执、正在输入、在线状态承诺、撤回或全文搜索。

建议正文保留 30 天，好友页和会话规则入口明确显示。师徒关系、最终出师结果和成就独立保存，不因私聊正文过期丢失。私聊使用独立清理规则，不能让公开聊天清理任务直接扫描私聊。

过期清除正文与引用内容，保留最小消息序号、发送成员及幂等标识作为占位；历史接口不返回过期正文。相同旧 `clientMessageId` 重试返回“原消息已过期”的确定结果，不当成一条新消息。账号注销另按第七节清理，不能以普通历史保留为理由继续保有注销内容。

建议统一 Redis 限流为账号每秒一条、每分钟 30 条，合法幂等重试不重复扣额。该限制与世界频道发言冷却分别管理，避免私聊次数挤占公开聊天额度。

### 4.3 发送与恢复

发送采用 HTTP。客户端生成 `clientMessageId`，界面显示发送中、已发送或失败；HTTP 成功表示已经持久保存，不等同于对方在线或已读。失败重试复用原 ID，修改正文后视为新的发送。

私聊新增现有实时通道中的账号定向通知，只携带会话 ID、目标角色和版本或序号，不广播正文。在线客户端收到通知后增量读取，离线期间消息直接留在数据库，不额外生成信件。通知丢失、重复、乱序均不改变数据库中的事实。

进入页面、断线重连和重新聚焦时刷新会话摘要，再从已连续同步的游标补齐消息。不能把推送中最大的序号直接当补拉起点。分页初始最近 50 条，向上加载更早记录，向后补齐漏掉的记录；游标不使用页码偏移。

前台每 30 秒进行一次有界摘要刷新，打开的会话同时按连续水位补拉；切到后台暂停轮询，恢复前台立即同步。即使 WS 保持连接但丢失某条 Core 通知，也会自动恢复，推送只负责缩短延迟。复用共享缓存与请求合并，避免每个页签、徽标各自轮询。

客户端以服务端消息 ID 去重，以 `clientMessageId` 合并乐观消息与 HTTP、WS 同时到达的结果。历史加载保持滚动锚点；阅读旧消息时不强制跳底，显示“有新消息”，由玩家决定何时回到最新。

### 4.4 未读和通知

只有会话可见、窗口可见且消息进入实际阅读位置时推进已读。服务端保存单调已读水位，多端共享；接收通知或仅打开好友列表不算读过。

未读计算为保留期内、对方发送、序号高于本成员已读水位的消息数。不能用“最大消息序号减已读序号”，因为其中包括本人消息。本人发送也不自动将未读的对方消息全部标为已读。

| 入口           | 提醒内容                               |
| -------------- | -------------------------------------- |
| 核心“传音”     | 邮件、私聊未读或好友申请的待处理红点     |
| 展开“师徒”     | 待确认申请或可出师状态         |
| 置顶“系统传音” | 邮件未读数；目录显示附件状态，当前信件原位领取 |
| 展开菜单按钮   | 师徒入口有待处理事项时的汇总红点       |

各项不累加成含义不明的总数量。当前会话不逐条弹成功或新消息 toast；战斗、地图等场景只更新导航提醒，不增加新的全局私聊浮条。

师徒交流未读由好友私聊统一处理，不再维护独立指导水位。申请待办由未决状态判断，可出师提醒由真实条件判断，不依靠一次 GET 隐式清空。首版不新增邮件待领附件的全局聚合徽标，不能按当前加载的邮件页数猜测总量。

## 5 师徒规则和关系生命周期

### 5.1 资格与匹配

| 项目 | 首版规则                                   |
| ---- | ------------------------------------------ |
| 师父 | 化神及以上                                 |
| 徒弟 | 拜师时当前角色低于元婴，即炼气、筑基、金丹 |
| 名额 | 账号共享一位在授师父、最多两名在授徒弟     |
| 宗门 | 可跨宗；同宗作为推荐因素，不影响资格       |
| 费用 | 系统不收拜师费，不允许师父从徒弟收益抽成   |
| 交互 | 主动拜师和邀请收徒都需要对方确认           |

收徒与拜师境界只在建立关系时判断，徒弟进入元婴或追上师父不会自动解除。教学关系属于角色，容量与永久首次拜师限制属于账号，不能用同账号多个角色绕过。

寻师只展示主动开放收徒的师父：道号、境界、宗门、擅长方向、常用时段、剩余名额和简短自述。擅长方向是自选标签，不能包装成系统认证。当前优先同宗，其次按招募更新时间排列；常用时段由玩家自行比较，不把自由文本伪装成精确时段匹配。不按战力或收徒数量做全服竞争榜。

师父可随时关闭公开招募，现有徒弟不受影响。申请有效七天，不预占名额。好友名片同时提供拜师或收徒入口；首次确认前明示资格、名额及会同时建立好友关系。

每账号最多五个未决主动师徒申请，同一角色对未决唯一；24小时最多发起十次，合法重试不重复扣额。拒绝、撤回和过期后需要再次明确申请，屏蔽不会泄露为专门的拒绝原因。

### 5.2 双方确认和退出

接受拜师在同一事务建立师徒与好友。双方原本就是好友时复用；好友容量不足、被屏蔽、角色失效、名额已满或申请已失效时整体失败，不留下半个师徒或额外好友。

请求状态采用 `pending → accepted / rejected / cancelled / expired`。关系状态只持久化 `active / graduated / dissolved`，暂停原因由角色转出、好友关系等当前事实推导，避免维护另一套相互矛盾的状态机。结束原因保存主动解除、屏蔽、死亡、删角或离服等内部事实。

双方可以随时解除，不扣资源、不产生负面称号、不需对方同意。解除前明确告知：首次拜师记录永久保留，解除后也不能重新拜师，师父离线、死亡、删角、转世或离服均不构成改拜例外。徒弟仍可独立成长，成就保留在原角色上。

解除师徒不删除好友。删除好友暂停私聊，仍占在授名额，双方可直接解除；个人成长和自主出师继续。屏蔽、死亡、删角和确认离服结束在授关系并释放名额。

### 5.3 出师

由服务端读取当前角色的权威状态，以下四项必须同时满足：

| 条件 | 固定门槛 | 归属 |
| --- | --- | --- |
| 境界 | 元婴后期及以上 | 当前关系中的徒弟角色，不累计前世境界 |
| 功法 | 至少一门元婴期功法修炼至六层 | 本人已学功法；无需占用生效槽；其他境界功法不替代 |
| 宗门心法 | 当前宗门至少三门各达到60级 | 当前有效membership与宗门定义，历史宗门不累计 |
| 炼体 | 至少两条轨道各达到20级 | 当前角色五轨炼体状态，不要求指定轨道或全部轨道 |

元婴后期人物等级75，对应心法人物等级加10的上限85，60级保留后续培养空间；炼体玉髓软上限22、金身软上限30，20级要求至少形成两轨基础。这两项阈值在 `game-content/mentorship` 配置中集中声明。

四项全部满足时，徒弟可自主出师，不需要师父确认、赠礼、共同讨伐、聊天次数或最低相处天数。未满足全部条件时明确列出差距。拜师时低于元婴的限制不影响关系成立后的成长。

出师释放师父的在授席位，保留桃李出师记录和好友联系。出师同样不清除永久拜师记录，不允许再次拜师。

## 6 私聊、出师奖励与成就

### 6.1 权威进度

在授徒弟查看四项固定出师进度，师父可查看弟子进境。页面按四项显示当前值和门槛，最终出师在事务内重新读取，客户端不能提交达标声明。

功法从本人已学状态和权威功法目录读取；心法从当前有效宗门归属和心法进度读取；炼体从 `cultivators.condition` 经当前规则规范化读取。换宗、洗炼或其他变化后以当前真实状态为准，不以历史截图或缓存永久锁定出师资格。

### 6.2 自由交流

师徒交流直接打开一体化好友私聊工作区，复用消息、未读、草稿、重试和阅读位置。师徒系统不再提供指导留言、授业基线、记功或已查看水位；原有指导接口和150修为研习补给入口退出运行。私聊内容不参与出师资格或奖励判定。

### 6.3 自主出师与桃李

徒弟达到四项条件后自行确认出师，师父无需在线或确认。结算事务向原徒弟角色增加100声望、向原师父角色增加300声望，更新双方资源版本，写入最终出师记录并持久化世界系统公告；失败整体回滚。每段关系只结算一次，同一请求重试仅返回原结果，不同请求不能重复结算。声望遵循现有资源上限，记录实际增量。

桃李记录只记录成功出师的师徒，人数按全部已出师关系累计，不要求曾写指导或私聊达到次数。死亡、物理删角和确认离服仍按既有规则结束在授关系，已解除关系不作为新出师入口。

历史已领取的150修为保留，旧版已经出师的关系不自动补发新声望或补发系统公告。

### 6.4 通用成就与名片展示

成就按本服角色独立解锁，使用独立的解锁账本、定义目录和服务端条件计算。拜师成功解锁「师父道号之徒」；原师父角色累计成功出师弟子2、6、12、20、30人，依次解锁「为人师表」「循循善诱」「诲人不倦」「厚德树人」「桃李天下」。既有可信师承和出师事实可补齐成就，补齐成就不发放声望。

名片设置可查看成就目录、条件与进度，从本人已解锁成就中选最多三项展示，可取消或更换。公开名片仅返回选定成就，不公开账号身份键、完整解锁账本或其他私有事实。通用条件以metric/target评估，动态名称通过服务端labels生成，未来玩法扩展定义和事实provider，不恢复授业记分。

## 7 角色变化和账号注销

| 变化 | 好友与私聊 | 师徒和成就 |
| --- | --- | --- |
| 改名、转宗 | 关系继续；消息保留发送时身份快照 | 关系继续，推荐标签按当前事实展示 |
| 删除好友 | 历史可读，停发；重新结缘复用会话 | 暂停私聊，个人进度、自主出师不受阻 |
| 账号屏蔽 | 停止新直接联系与通知，旧历史仍按权限可读 | 结束在授，取消请求，释放名额 |
| 死亡或物理删角 | 不级联删除私聊；旧会话只读 | 原事务内结束关系；保留账号永久拜师及领奖记录 |
| 转世 | 新角色重新建立好友，旧历史归原账号 | 不自动继承前世师徒，永久拜师限制保留；新角色不继承旧角色成就和桃李人数，出师奖励不重复，不能再次拜师 |
| `transfer_pending` | 暂停新发送 | 暂停互动，另一方可立即解除 |
| 转出回退 | 重新核对活跃状态、好友和屏蔽后恢复 | 未解除的关系恢复，不撤销已合法结束的关系 |
| `transferred` | 本服旧会话只读，不向远端转发 | 结束在授；社交关系与奖励权益不随跨服档案迁移 |

永久拜师限制对本服账号生效，成就与桃李计数对本服原角色生效，首版不建设跨服统一身份权益账本。跨服档案不携带社交关系；目标服依据本服账号记录核对，不能由客户端声明历史资格。

转出准备接当前 `export()` 的 `transfer_pending`。`departed` 事件在这一阶段已经发出，不能据此提前结束师徒；最终结束接 `resolveExport()` 确认 imported 回执、写入 `transferred` 的同一事务，不能等待当前并不存在的另一条确认离服事件。

账号注销与普通删角分开处理：立即停止新直接联系、取消申请并结束在授；擦除该账号发送的私聊正文、旧版自由文本指导、招募自述与身份快照。对方自己发送的正文按普通保留期处理；对方历史只保留“已注销道友”占位及不含身份的结果。删除注销账号的成就解锁和旧补给身份账本，清除或不可逆替换会话成员、关系、目标证据中的注销方原身份键；新注册账号按新账号处理。

现有 `beforeDelete`、`afterDelete` 只负责账号删除留档，没有社交清理执行者。实施时另增 `social_cleanup_status`、重试时间和错误摘要等状态，与现有账号删除完成状态分开。`beforeDelete` 保留清理身份，成功删除后登记待办；现有 `expired-data.cleanup` 后台任务接入可恢复的社交清理执行者，逐项清理正文、身份、请求、屏蔽、奖励账本和未发布通知，全部完成后才标记社交清理完成。保留失败待办重试，不让社交清理失败改变 Better Auth 已成功删除账号的结果；账号删除失败时也不能按已注销账号擦除仍在使用的数据。

死亡写入目前分散在寿元处理、资源结算和主动兵解等路径，不能只接一个尚不存在的死亡领域事件。实施时逐一接入事务内清理，角色删除前先结清关系；所有接受、发送和授业入口仍实时复核双方状态，不能仅依赖异步通知及时到达。

## 8 页面层次和状态验收

师徒首页按玩家阶段组织：未拜师时突出寻师；在授时突出当前出师进度与好友私聊；师父视角突出两个徒弟各自的下一步；可出师时突出自主出师；已出师时展示结果和继续联系。

在授首页始终展示四项固定出师进度，突出最近可做的下一步；四项全部满足才高亮出师。功法门数、心法达标数量和炼体轨数均来自服务端，进一步培养资料按需查看，不再出现课程选择或换师入口。

名额、拜师资格、同时建立好友的结果，以及删除或屏蔽对私聊和师徒关系的影响，均在对应提交前可见。完整规则、桃李出师统计及成就条件进入语义明确的详情，不和当前目标等权平铺，也不全部藏进一个“更多”。

| 状态                                 | 应有表现                             |
| ------------------------------------ | ------------------------------------ |
| 初次加载、空名录、没有合适师父       | 有场景化反馈和可行下一步             |
| 申请等待、拒绝、过期、撤回           | 状态明确，操作不依赖页面刷新才能恢复 |
| 容量不足、目标失效、权限失效         | 在动作旁解释真实阻碍，不只给灰按钮   |
| 断线、发送失败、结果未知             | 保留正文与草稿，可按原 ID 重试       |
| 翻阅历史、收到新消息、正文过期       | 阅读位置稳定，保留期边界明确         |
| 删除好友后的授业暂停、失联、转出准备 | 提供重新联系或解除，不阻断个人研习   |
| 可出师、已出师、死亡或离服结束       | 结果和可用动作与在授状态区分         |

复用 `InkButton`、`InkTabs`、`GameIcon`、默认 `font-mono` 和既有语义配色。只在确认风险时增加确认层，不为每条聊天增加弹窗。

桌面和 360px 均检查联系人切换、长道号、换行、返回和草稿保存。聊天输入区随可视视口处理软键盘，发送按钮和最近消息不能被 dock 或安全区遮挡；不新增全局 body padding。桌面 Enter 发送、Shift+Enter 换行，中文输入法组合输入不触发发送，触屏保留明确发送按钮。

| 表 | 核心职责和约束 |

继续使用原好友关系表，不重建好友主表。历史表引用角色时使用可空关联并保留不可变原身份键和快照，或明确不设会导致历史丢失的外键；不能只有一个删角后变空的 FK。账号永久师承不随角色删除；角色成就随角色隔离，物理删角级联删除，也不依赖会被清理的消息消费记录或玩家日志防重。

以上身份保留针对普通删角；账号注销是明确例外，按第七节清理身份和内容。私聊占位保留发送成员序号而非必须保留注销账号原键，避免防重与注销要求冲突。

主要索引包括会话成员账号与最近活动、消息 `(conversation_id, sequence)`、账号与客户端消息 ID、未决请求接收者与有效期、在授学徒账号唯一，以及在授 `(mentor_user_id, seat)` 唯一。导师席位固定为 1 或 2，同时用事务容量检查；请求待处理不占席。

## 10 接口和实时协议

路径是实施约定，正式 schema 位于 contracts。身份来自 Guard 和服务端归属查询，客户端不提交奖励金额、完成事实、消息作者或任意账号接收者。

| 能力 | 建议接口 |
| --- | --- |
| 好友 | 保留 `GET /api/friends`、search、invite 查询与 DELETE；旧直接添加 POST 改为申请语义，不留可绕过确认的入口 |
| 好友申请 | `GET/POST /api/friends/requests`，以及 `/:id/accept`、reject、cancel |
| 屏蔽 | `GET/POST /api/social/blocks`，创建只传目标角色；`DELETE /api/social/blocks/:blockId` 只管理本方记录，目标删角后仍可解除 |
| 获取或创建私聊 | `POST /api/direct-messages/conversations`，传目标角色；好友且可互动时幂等创建 |
| 私聊读取 | `GET /api/direct-messages/conversations`、`/:id/messages`，支持历史会话与游标 |
| 发送与已读 | `POST .../:id/messages`，`PUT .../:id/read` |
| 师徒总览与招募 | `GET /api/mentorship`、`/mentors`；`PUT /api/mentorship/profile` |
| 师徒申请 | `GET/POST /api/mentorship/requests`，以及 `/:id/accept`、reject、cancel |
| 关系管理 | `POST /api/mentorship/relations/:id/dissolve`、`/graduate` |
| 成就目录 | `GET /api/achievements`，只由服务端可信事实解锁 |
| 名片成就 | `GET/PUT /api/cultivator/card/settings`，最多选三项已解锁成就 |
| 社交摘要 | `GET /api/social/summary`，分别返回私聊未读、好友申请和师徒待办 |

私聊读取采用 `@Access('user')` 并逐次检查会话成员账号，支持没有活跃角色时的历史归属；发送、关系建立、出师和名片修改采用 `@Access('active')`。Web 当前活跃角色页不能成为唯一鉴权依据。历史会话后端可读，不在本轮扩出新的无角色游戏壳；转世后从好友页历史入口查看。

写入请求使用稳定 `requestId` 或 `clientMessageId`。需要条件更新的申请和关系携带 `expectedRevision`；同一 ID 不同正文或目标返回 409。资源领取复用现有命令执行与资源提交，并叠加账号永久权益约束。

实时新增社交摘要失效、私聊变化、已读变化、师徒变化等显式消息类型。网关只订阅会话认证确定的账号主题，并核对目标角色；客户端不能订阅任意账号或猜会话 ID 加入房间。转世、退出登录和角色切换时取消旧订阅、清除旧身份缓存；草稿按账号与会话隔离，不跨账号复用。

旧 WS 的失效由服务端落实：会话撤销、注销或角色变化后终止或重新验证私聊订阅，并在心跳或通知出口做有界身份复核。不能只依靠前端主动断开；即使不广播正文，会话 ID 和活动序号也不能继续发给已失效会话。

## 11 事务和可靠性

所有写路径传递同一 `DbTransaction`。涉及好友、屏蔽、师徒和出师奖励的操作先按统一顺序锁账号及角色，再锁关系、会话或权益；私聊发送与删除好友、屏蔽采用相同的参与者锁顺序，防止关系已解除后另一个旧事务继续写入。

账号锁行随 P1 引入，P3、P4和成就解锁复用。原邮件与定向寄售已经在同一事务锁定发送者角色，屏蔽会等待该角色锁；不向旧资源写路径反向添加账号锁。社交身份锁使用 `NO KEY UPDATE`，与旧邮件接收者外键的 `KEY SHARE` 兼容，避免因双方身份检查形成环等待。

私聊在会话行锁内分配下一个序号，插入消息、更新摘要并写双方通知 outbox，统一提交。不能使用普通自增 sequence 的分配顺序充当提交水位。唯一幂等键与请求指纹包含会话、当前发送角色、类型及规范化正文；已提交请求先按成员身份识别重试，再判断是否允许新发送。

已读请求传本会话消息 ID，服务端解析序号后以 `GREATEST` 推进，拒绝其他会话消息及未来序号。通知只在提交后发布，多端读水位变化也通过同一账号通知；客户端不依赖广播成功作为发送成功依据。

接受拜师原子完成资格复核、好友建立、师徒席位分配、请求终结及通知；同一徒弟的其他未决拜师请求随之失效。接受、出师、解除、屏蔽和生命周期清理使用相同锁与唯一约束，不能只靠前端禁用按钮。

固定出师条件直接读取当前权威事实，不增加指导或聊天次数条件。出师、双向声望、成就解锁与世界公告在一个事务完成，资源与聊天通知提交后发布。永久首次拜师时间独立于当前关系，不因解除、死亡、删角或转世清空；成就解锁以角色和定义ID唯一去重。

## 12 迁移和发布

只新增业务迁移和必要索引，不修改已发布迁移，不改 Better Auth 独立 schema。检查生成 SQL、snapshot、journal、外键和查询索引；禁止直接在 staging 或生产试写。

迁移保留原好友双向关系，先核对是否有残缺或重复数据；如发现单边遗留关系，实施前单独形成修复清单，不在迁移中悄悄扩大好友关系。原聊天、传音和附件不搬到私聊，也不将旧信件伪装成新的聊天消息。

上线不回填不存在的师徒历史，也不为旧出师自动发放新声望；只有本次明确出师请求提交奖励。既有真实师承/出师事实可以补齐成就。

新增功能按下面批次实施，但面向玩家只开放已完整可用的入口。部署时 API、contracts 与 Web 同步切换好友添加语义，避免旧客户端把申请误报为已成为好友；保留的旧 POST 返回明确申请状态，所有第一方调用方同步更新。

出现问题时先回退 Web 新入口和新写入调用，保留新增表及已提交记录，不执行反向删表或撤销已合法发放资源。回退版本仍需保留好友确认与屏蔽边界，不能回到任意单方添加即可私聊的服务端行为。完整替换部署按现有维护发布流程执行，生产发布另行安排。
