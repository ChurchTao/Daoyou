# Phase 9C：统一物品系统与兽诀培养

> 2026-09-07：代码已实现，静态检查与基础本地流程通过；有物品的完整交互与掉落消费闭环尚未实测，见第 8 节。依据：[总路线图](./combat-v6-mhxy-redesign-roadmap.md)、[灵兽设计基线](./combat-v6-summoned-beast-system-design.md)。

## 1. 已确认范围

- 建立可扩展物品类别的统一且唯一的新持有系统，v6 当前物品的获得、持有、消费和装备引用接入该系统；不按兽诀、药品、材料分别建立持有表。
- 持有物品直接通过 `cultivator_id` 归属角色，不使用 `container_id`，不建立容器实体表。
- `location` 区分 `bag` 与 `storage`；背包初始 40 格，首版不开放扩容。新储藏室空间无限，兽诀每格最多 99 本。
- 背包不足时，战斗奖励剩余部分进入新储藏室，结算明确去向，不丢弃、不阻塞结算。使用道具须先取入背包。
- 旧存储概念上作为洞府储藏室来源保留，本阶段不迁移旧玩法库存、不接兼容读取、不双写。后续另行打通旧库存取出转换。
- 不新增消费操作凭据表。使用现有角色 Redis 锁、数据库事务和 revision；不把分布式锁视为数据库原子性的替代。
- 兽诀获取与随机打书接入新库存。固定技能格不增长、等概率覆盖一个既有格位，不提供指定覆盖、锁定、保底或撤销；普通／高级同系占格但只生效高级。

灵兽、已学技能、修炼进度与灵石余额仍是各自领域状态，不转为背包物品。

## 2. 持久模型

固定物品定义初期放在有类型校验的共享配置，包含稳定 ID、分类、名称、描述、堆叠上限、实例 schema 和使用类型。具体玩法效果由领域服务执行，不建设通用脚本执行器或配置后台。

建议新增 `wanjiedaoyou_inventory_items`：

| 字段                        | 语义                                       |
| --------------------------- | ------------------------------------------ |
| `id`                        | 持有记录身份                               |
| `cultivator_id`             | 角色外键，唯一所有权来源                   |
| `location`                  | `bag` 或 `storage`                         |
| `slot_index`                | 背包格位 0～39；储藏室为 NULL              |
| `definition_id`             | 稳定物品定义 ID                            |
| `quantity`                  | 正整数；独立实例固定为 1                   |
| `instance_data`             | 经分类 schema 校验的个体事实，无差异时为空 |
| `revision`                  | 每次内容、数量或位置修改时递增             |
| `created_at` / `updated_at` | 创建与更新时间                             |

数据库对 `location = 'bag'` 建立 `(cultivator_id, slot_index)` 部分唯一约束，并检查位置与格位组合、正数量及非负 revision。背包格位仅在数据库中约束非空且非负；容量上限由共享 `BAG_CAPACITY` 配置统一校验，不写死在数据库 CHECK 中。服务端验证定义、实例 schema 和堆叠上限，不接受客户端提供权威效果。名称、展示描述和战斗投影不重复持久化。

堆叠资格由定义及有效实例属性决定，不能按名称合并；同种物品可因数量上限形成多堆，不能对角色和物品定义建立唯一约束。入包优先填充已有堆叠，再占空格。独立实例一件一格。迁移或整理不能重新生成随机属性。

## 3. 并发、转移与结果不明

获得、消费、移动、拆分、合并及整理统一通过库存服务，并传递调用方事务。角色锁内仍使用数量与 revision 条件更新；失败时整个事务回滚。

打书在同一事务内扣书并修改灵兽，请求包含物品及灵兽 revision。成功后响应丢失，客户端刷新库存及灵兽；旧请求不得被包装为新操作自动重试。没有持久凭据时不承诺返回原动画或原操作详情，也不提供跨任意业务的持久请求去重保证。

野外掉落沿用既有战斗结算凭据，先冻结奖励结果，再在奖励事务内入包／入储藏室；重试不得重掷或重复发放。恢复未知结果不重新生成权威奖励。

新背包与新储藏室之间复用同一持有表。转移时原子修改位置、格位与数量；背包容量不足的主动取出拒绝且不改库存。未来旧储藏室取出必须在同一事务内扣除旧持有并写入新库存，不能留下可重复消费副本；该转换不在本阶段实现。

## 4. 现有代码入口与接入结果

已核对 `schema.ts`：旧 `materials`、`consumables` 和 `creation_products` 继续由旧玩法管理；消耗品 `spec` 有既有类型协议，不将新兽诀塞入该协议。

v6 原有 `combatV6EquipmentInstances` 与 `combatV6EquipmentLoadouts`；本轮将装备个体完整迁入 `inventory_items.instance_data`，保留原 ID，再切换装备栏外键和 `combatV6BuildRepository.ts` 的属性／所有权读取，最后删除旧 v6 装备实例表。没有保留第二份持有状态。当前应用未发现独立的 v6 装备获得写入服务，新库存的统一获得函数同时支持固定堆叠品和完整装备个体。

已装备物品仍占背包一格，装备栏引用同一物品；卸装不需要空格，存入储藏室前必须卸装。更换装备会校验完整装备组合并使构筑资源缓存失效。迁移时已装备个体优先进入背包，其他个体超过 40 格进入新储藏室。旧版装备及造物库存不迁移。

## 5. UI 与实施顺序

1. 清点 v6 物品链路及装备装卸规则，确定实际数据迁移与路由落点；区分新旧玩法来源。
2. 实现共享定义、实例验证、格位／堆叠计算与库存表，审查迁移 SQL 和约束。
3. 实现统一库存服务与 API；角色认证、所有权和使用条件由服务端校验。
4. 建立响应式格子背包，展示已用格／40、数量、分类与搜索；通过现有详情抽屉完成移动、合并、拆分、整理及新储藏室存取，不依赖拖拽。旧储藏室聚合展示留待后续。
5. 接入 v6 现有物品及装备身份，再实现兽诀掉落、学习确认、覆盖结果与战斗投影；背包入口与灵兽详情入口复用同一学习交互。
6. 更新协议、发布步骤和实际验收记录。维护期硬切已接入的 v6 路径，不增加长期双写或功能开关。

使用 React 最佳实践及仓库格式规范，不引入新的全局状态库。不扩展交易、赠送、分解、合宠、洗点、装备生成规则或战斗药品机制。

## 6. 本轮内容配置

按前序推荐实施初版参数：正常野外胜利时，每只实际击败野怪 3% 掉一本；灵火、岩甲护身、疾风爪、普通连击各占 24%，高级连击占 4%。首批五种书跨物种学习，完全相同技能禁止重复学习，普通／高级允许共存，不增设高级书独立门槛。尚未进行经济平衡验证。

奖励随机流从战斗身份与原始种子独立派生，不消耗战斗 RNG；终局奖励冻结在既有野外结算摘要中，复用结算凭据与事务发放。概率失败没有奖励，捕获退场不算击杀，逃跑／战败／技术作废不发兽诀。

## 8. 实施、发布与验证记录

### 代码落点

- `src/shared/inventory`：固定定义、实例 schema、获得／堆叠／溢出／整理、学习和掉落纯规则；具体效果仍由 v6 领域负责。
- `InventoryService.ts`：统一查询、转移、移动／交换／合并、拆分、整理、学习与装卸。角色锁与 SQL 行锁保护事务，数量和 revision 校验防止旧请求重复消费。没有新增消费凭据表。
- `/api/combat-v6/inventory`：GET 分页查询与 POST 操作，复用活跃角色认证；储藏室每页 40 条，不一次下载无限库存。
- `/game/inventory`：新版格子背包；`/game/cave/storage/new?location=storage`：新储藏室；`/game/cave/storage`：原物品页面保留为洞府旧藏。旧消费玩法返回入口指向旧藏，不会把旧库存当成新背包可消费记录。
- 灵兽详情的学习入口进入同一物品选择流程；同系普通技能保留并展示抑制原因。技能描述复用统一 tooltip；道装详情展示属性，不向玩家展示 JSON。

### 发布步骤

1. 停机维护，先结束旧活动战斗与待结算任务，再备份数据库。
2. 执行 `0039_inventory_v6.sql`：先复制 v6 装备身份和冻结事实，再切换外键并删除旧 v6 装备实例表；不迁移旧版材料、消耗品或造物表。发布前核对每个角色已装备实例数量不超过背包容量，避免已有多套装配超出迁移前提。
3. 继续执行 `0040_inventory_slot_capacity.sql`，移除数据库格位约束中写死的容量上限，保留非负格位、位置组合、正数量、非负 revision 和格位唯一性；容量仍由应用配置控制为 40 格。本地已执行并核对实际约束。
4. 同步发布前后端，新野外内容戳为 `daoyou_wild_inventory_content_v1`；规则 RNG 未改，历史回放继续读取冻结资料。旧活动运行态不兼容续跑，页面需要刷新。
5. 恢复服务后验证库存、装备构筑、一次野外结算。无功能开关、双写或独立消费凭据。

本轮只在纯本地数据库执行迁移，未向预发布或生产写入，未部署。

### 本轮修复

发现 `CombatV6WildStore.complete` 会在结算后删除临时摘要，而战斗视图原先从该摘要读取 `itemRewards`。因此即使已经发放，刷新或后续轮询也可能丢失奖励提示。

将终局奖励展示列表与同次最终运行会话一并写入 Redis，更新 `WildRuntimeSchema` 校验；视图从运行会话读取冻结列表。原结算摘要仍按原生命周期清理，发放仍复用既有事务与幂等凭据，不新增表、重抽奖励或更改战斗 RNG。列表最多 3 项，运行会话退出／过期时随之清理。此次自然掉落已验证摘要删除后的刷新路径。
