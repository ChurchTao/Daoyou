# 频道聊天重设计提案

状态：设计提案，尚未实施。日期：2026-10-13。

## 1. 设计结论与范围

把聊天重做为「宣纸上的会话流」：稳定的频道导航、可以连续阅读的消息时间线、始终容易找到的输入器。纸墨承担风格，消息内容承担注意力，朱砂集中用于红包与重要异常。

本次覆盖世界、宗门、系统频道，以及其他主流程页面的聊天预览入口。世界与宗门支持文字、展示、回复、红包；系统保持只读。已有物品、灵兽、战绩回放、围猎传闻、组队招募继续可用。围猎队伍聊天暂不并入本次范围，其频道与生命周期另有归属。

首版交付包含全部需求：新的界面和渲染、回复、稳定历史加载、灵石红包。独立讨论串、私聊、表情反应、富文本编辑器、已读回执不进入本次范围。

假设与推荐值：

- 「最少发 5 万灵石」指单个红包的**总金额至少 50,000 灵石**。
- 推荐红包总金额 50,000–10,000,000，数量 1–100，24 小时到期；上限、数量和有效期是本提案建议值，并非现有规则。
- 支持拼手气与等额，默认拼手气；退款不收手续费。
- 推荐可回溯近 30 天聊天；资金账本独立保存，不跟随聊天保留期删除。
- 推荐首次进入默认世界频道；后续恢复玩家最近使用的频道。
- 正文保留现有 100 字上限，先解决阅读和操作，不把字数扩容混入本次改造。

## 2. 当前问题与依据

以下为代码审查结果，尚未在当前线上环境进行性能测量。

| 当前事实 | 对体验的影响与设计要求 |
| --- | --- |
| 消息窗固定为手机 22rem、桌面 20rem，输入器固定三行 | 对可用屏幕空间利用不足；改为随游戏壳可用高度分配空间 |
| 顶部按钮加载历史，应用只跳过一次自动贴底，没有保存可见消息锚点 | 应建立显式锚点；不能依赖浏览器恰好补偿滚动位置 |
| 重连重新获取第一页，并替换已加载列表 | 已加载历史会丢失；改为增量恢复，保留当前内容 |
| 进入活跃频道、收到该频道消息即推进已读 | 正在翻历史也会被当作已读；改为按实际可见消息推进 |
| 世界与系统共享 Redis 最近 100 条，宗门各保留 100 条 | 没有持久历史；仅调整前端无法获得可靠回溯 |
| 使用 page/pageSize 位移分页 | 新消息插入时可能重复或遗漏；改用稳定游标 |
| 所有消息逐条渲染、合并排序，没有长期窗口管理 | 长会话成本会增长；实际卡顿程度需浏览器测量 |
| 普通文字使用 break-all，未保留换行 | 多行表达被压平，英文及混合文字容易逐字断开 |
| 发送等待 HTTP 返回，期间禁用输入，每次成功弹提示 | 连续输入受阻；改为原地发送状态与失败重试 |

## 3. 页面与视觉

### 桌面

延续 `GameViewportLayout → GameSceneFrame`，HUD、场景身份和全局导航仍由游戏壳负责。正文只放聊天工作区，不再重复场景大标题。

- 左侧约 144–160px 频道栏：世界、宗门、系统。宗门归属只在当前频道上下文出现一次。未加入宗门时该项给出简短状态，不弹空聊天窗。
- 右侧为频道时间线：上方紧凑频道状态，中间消息列表，下方输入器。无需额外侧边资料面板。
- 消息列表占据扣除 HUD、场景标题、输入器与全局导航后的剩余空间；页面主体不再和消息列表同时滚动。
- 列表内容宽度限制在适合阅读的范围，长文本正常换行。右侧空余不填装饰或统计。

### 移动端

- 左侧频道栏变为顶部三个轻量页签，文字与未读数字在同一行。
- 消息头像 28–32px，正文保持 16px 左右；操作目标至少 44px。
- 输入器默认一至两行，随内容增长，上限约四行，之后内部滚动；展示和红包入口位于工具行，发送始终有文字按钮。
- 软键盘弹出时输入器跟随可视区域，消息区收缩并保持阅读锚点；输入器下方临时收起全局 dock，收键盘后恢复。该行为由聊天场景和现有壳层偏移协同，避免多个 fixed 层互相遮挡。
- safe-area、`visualViewport` 与现有 `--game-bottom-offset` 一并计算；正文不增加全局 body padding。

### 视觉语言

沿用宣纸 `#f8f3e6`、浅纸 `#f1ead8`、墨色 `#2c1810`、次级墨 `#5a4a42`、青绿 `#4a7c59`、朱砂 `#c1121f`。正式实现复用现有 tokens 和纸纹，不引入另一套主题。

- 场景标题继续由原壳使用马善政；消息、按钮与表单使用现有霞鹜文楷。
- 时间、红包金额、份数和余额使用 Tailwind 默认 `font-mono`；不设置新的数字字体。
- 普通消息不加气泡尖角、不逐条画虚线。通过留白和身份分组建立节奏。
- 本人的消息保留左对齐，正文用极浅青灰底和「你」标识辨认；频道多人对话维持同一阅读轴。
- 引用使用浅墨底、细青绿竖线、作者与一行摘要；金额高亮集中在领取结果和确认动作。
- 红包使用克制的朱砂封面、小封印图标与米金文字；不闪烁、不放大面积渐变或抢占整屏的动画。
- 实现图标统一经过 `GameIcon` 与 registry。样稿中的符号只表达位置和交互意图。

## 4. 消息渲染体系

| 消息类型 | 时间线中的展示 | 点击行为 |
| --- | --- | --- |
| 普通文字 | 头像、姓名、简短境界、正文；保留换行，长词按需折行 | 回复入口；选中文字不触发回复 |
| 回复 | 单层作者与摘要引用，下面是本条正文 | 点引用定位原消息，点回复按钮回复本条 |
| 物品展示 | 完整物品名、图标、必要短摘要、附言 | 沿用现有共享 `ItemPreview` 及发送时快照 |
| 灵兽展示 | 名称和少量识别信息、附言 | 沿用现有 `BeastTradeDetails` |
| 战绩回放 | 对阵、回合数、明确的「查看回放」入口 | 进入现有回放流程 |
| 组队招募 | 招募目标、必要状态、现有加入入口 | 执行招募的当前操作，权限由原业务校验 |
| 围猎传闻、系统公告 | 无玩家头像的淡墨事件行；长公告可展开 | 保留现有目的入口，系统消息无回复 |
| 灵石红包 | 祝福语、分配方式、份数、领取状态 | 打开领取/详情层；每次读取权威状态 |

同一作者、同一频道、两分钟内连续普通发言可以合并身份栏。日期、未读分隔、回复和独立卡片会打断分组，避免内容关系不清。分组只影响展示，每条仍保留独立消息 ID 和操作。

日期跨天时显示「今天 / 昨天 / 月日」，身份行显示 `HH:mm`，完整时间由可聚焦详情提示提供。历史年份不同时补年份。相对「刚刚」不作为长历史的唯一时间。

只渲染经过协议验证的消息类型。玩家文本按纯文本转义，不执行 HTML；暂不开放任意 Markdown 与自动外链卡片。物品展示和招募不因为点击事件冒泡误触回复或领取。

## 5. 回复流程

1. 桌面悬停或键盘聚焦消息出现「回复」；移动端轻点普通消息的非交互区域出现就地菜单，选「回复」。保留明确回复按钮；长按是补充入口。
2. 选中后，输入器上方显示「回复 云游子」与一行摘要，右侧取消；光标进入输入框，原有草稿保留。
3. 发出的消息显示引用和正文，仍然在当前频道主流。引用回复消息时仅引用该消息本身，不递归套引用。
4. 点击引用，原消息在当前窗口内则就地定位；不在窗口内则拉取其附近上下文，短暂轻底色高亮。
5. 跳转前保存阅读锚点，显示「返回刚才位置」；此入口与「回到最新」有不同职责。

引用卡片类消息时只显示「物品名 / 灵兽名 / 战绩摘要 / 灵石红包」，不把整张卡片塞进引用。

服务端接收 `replyToMessageId`，自行校验同频道、同宗门和可见权限，生成作者与短摘要快照。客户端不得任意提交被引用的正文或作者。原消息过期时提示「原消息已过期」；审核隐藏时引用摘要一并遮蔽。用户改名不修改历史作者快照。

## 6. 加载、滚动和已读

### 三种阅读状态

| 状态 | 新消息到达 | 加载与离开 |
| --- | --- | --- |
| 跟随最新 | 轻量贴底，不每条播放长滚动动画 | 离开时保存频道与窗口 |
| 浏览历史 | 保持当前消息不动；下方出现「↓ N 条新消息」 | 靠近顶部预取更早内容；点新消息入口才去最新 |
| 查看原消息 | 保持定位上下文；新消息不打断 | 提供返回刚才位置，以及回到最新 |

发送普通消息是主动继续对话：本地待发送行立即可见，回到会话尾部；若玩家之前在历史位置，保留返回历史的锚点。输入草稿本身不触发跳转。中文输入法组字时按 Enter 不发送，桌面 Shift+Enter 换行，手机 Enter 换行。

### 历史加载

- 首次无缓存读取最近 30 条，只有首次空白使用占位；有缓存先展示缓存并校正。
- 每次向前读取 30 条，距离顶部约 200px 开始预取；同方向一次只允许一个请求，重复游标不重复插入。
- 补页前记录首条可见 `messageId + offset`；补页、字体或卡片尺寸变化后按该锚点恢复。不要只用 scrollHeight 差值。
- 加载提示仅占列表顶部的小区域；失败在同位置显示「加载失败，重试」，原内容和输入器继续可用。
- 每频道保留草稿、回复对象、当前窗口、阅读锚点、已读游标；切回不借用另一个频道的滚动状态。
- 窗口管理和可变高度虚拟列表维持可控 DOM。初步目标约 150 条窗口，按 profiling 调整；裁剪旧窗口前保存锚点并保留可重新读取的游标。
- 读到最早可保留消息时显示「已到历史起点 · 可查看近 30 天消息」。无法恢复未存储的旧记录不伪造空白历史。

### 实时与断线

重连保持列表，通过 `afterCursor` 补缺失消息，按消息 ID 合并 HTTP 回应、实时推送和补页结果。缺口过长时分批同步；已超出保留期则说明缺口，并让玩家选择回到最新，不能静默丢弃历史。

连接状态只占频道头的小提示：「连接中 / 正在恢复 / 暂时离线」。离线时允许继续编辑草稿；不承诺已发送，也不在恢复后自动发送红包。

只有页面可见、频道在前台、消息进入可视范围后才推进该频道已读游标。首个未读位置有轻量分隔；向上浏览不倒退已读。对我的回复在未读提示中增加「有人回复你」，世界闲聊不连续弹 toast。

底部预览继续复用全局 Feed Provider，显示简短的最新传音或回复提醒，点击进入对应频道并恢复上下文。红包只提示「某道友发了灵石红包」，不自动弹领取层。聊天页内不再出现重复预览条。

## 7. 发送体验

文字发送采用本地待发送消息：点击后立即进入列表，标记「发送中」，输入器可编辑下一条；成功静默替换为服务器消息。失败留在原处显示「未发送 · 重试」，正文可恢复到输入框，避免丢稿。

沿用当前境界相关的 15–60 秒频道发言冷却，不把客户端输入锁死；发送按钮在冷却时显示可理解的倒计时，草稿和回复操作仍可用。发送中限制重复提交同一条，不增加排队自动连发机制。

文字、回复及展示统一携带 `clientMessageId`；服务器幂等约束与请求指纹防止 HTTP 超时后重发变成两条。红包有独立持久的资金幂等键，按钮禁用只提供界面反馈。

## 8. 灵石红包玩法

### 发红包

输入器的红包入口打开桌面确认层；移动端使用适配小屏的确认层，保留全部必要字段。

顺序为：当前发送频道 → 总金额 → 数量 → 分配方式 → 祝福语 → 扣款确认。

- 总金额输入整数，金额边上显示「至少 50,000 灵石」，允许快捷选 5 万、10 万、50 万。
- 份数为 1–100 的整数，每份至少 1 灵石。
- 拼手气由服务器预分配整数份额，总和严格等于总金额；结果不由客户端计算。
- 等额要求总金额能被数量整除，直接就地提示调整金额或份数，不自动多扣、不隐藏余数。
- 祝福语最多 24 字，默认「仙途同庆，见者有份」，沿用文本审核。
- 确认层展示可用余额、实际扣款、分配摘要，以及「24 小时未领完，余款自动退回」；二级说明补充「余额已满或角色变化时保留为待退款」。
- 最终按钮写「确认发出 50,000 灵石」，该点击本身完成金额确认，不再叠加相同的二次弹窗。
- 扣款成功并持久创建红包后，才显示聊天卡片；请求结果未知则保持「正在确认」，用同一幂等键查询/重试。

红包发布沿用频道发送权限、现有冷却与文本过滤。世界红包世界可见，宗门红包只能在指定宗门频道可见与领取。

### 领红包

点击红包卡片打开祝福语与「开启红包」。确认领取后显示到账整数金额、已领份数和领取明细。只在领取成功显示轻量盖印效果，约 200–300ms；减少动态效果偏好下取消动画。

- 活跃角色才能领取；同一账号每个红包只领取一次，换角色不增加机会。
- 发送账号不能领取自己发出的红包。
- 宗门权限在每次领取时重查；离宗后不能继续领取，不能依赖已经缓存的消息或旧 WebSocket 订阅。
- 领取者接近灵石余额上限时必须完整到账；无法容纳该份额则提示「余额已达上限，未领取」，不占用份额、不截断到账。
- 多人争最后一份时以服务器事务顺序决定；其余玩家看到「已领完」，不会先播成功动画再回滚。
- 再次点击已领红包只显示原结果和明细，不再次扣减库存或增加余额。

### 状态与退款

| 红包状态 | 卡片文案 | 详情中的动作 |
| --- | --- | --- |
| 可领取 | 点击领取 | 开启红包 |
| 当前账号已领取 | 已领取 · 查看详情 | 显示本次到账与领取明细 |
| 当前账号为发送者 | 查看领取详情 | 查看份数和明细 |
| 已领完 | 已领完 | 查看明细 |
| 已过期，退款完成 | 已过期 · 余款已退回 | 查看退款金额 |
| 已过期，退款待处理 | 已过期；发送者可见「退款待领取」 | 发送者处理退款，其他人查看已领明细 |

已领取是账号视角，和红包全局的「可领取/已领完/已过期」组合使用，不用一个全局状态覆盖所有玩家。

到期未领金额精确退回一次，已领金额不退。通知延迟不改变资金事实；领取、过期关闭和退款必须共享同一套状态判断。卡片样式随状态轻量淡化，状态文案仍可读。

退款账本归发送账号独立保留：原出资角色仍是该账号当前活跃角色、且余额能完整容纳退款时，自动退回；余额已满、角色死亡、消失或轮回导致不能入账时，保留待退款权益，不随角色删除级联消失。**本提案建议待退款可由该账号当前活跃角色领取**，不为红包阻塞轮回。这会允许未领取余款跨角色/轮回，属于需要随红包一起评审的经济规则，不是当前已有能力；若选择限制跨轮回，应在角色退场流程明确定义资金结算规则，不能静默吞掉余款。

初版不允许发出后撤回已公开红包，也不提供定向赠送或密码红包。

## 9. 最小技术落点

### 前端

全局 `WorldChatFeedProvider` 继续持有最近消息与实时连接，给其他场景的底部预览供数。聊天组件拥有局部窗口与滚动交互，避免把全量 30 天历史加载进全局上下文。

建议在现有 `components/feature/world-chat` 内拆分频道导航、时间线/锚点、消息 renderer、输入器/回复、红包卡片与确认层。复用 `InkButton`、输入与模态原语、`GameLoadingState`、道友详情和资源 store；不新增第二套余额状态、通用消息插件系统或场景壳。

### 协议与历史

协议仍归 `packages/contracts`。补充回复关系、客户端幂等 ID、红包消息类型及带 revision 的状态更新。

PostgreSQL 保存聊天真相，Redis 最多作为最近消息缓存。历史接口支持 `beforeCursor / afterCursor / aroundMessageId`；消息排序与游标由服务端决定。稳定排序键需要处理并发事务的提交顺序，不能把事务提交前提前分配的自增 ID 直接当作「已全部同步」水位。

新增业务表最小集合为 `chat_messages`、`chat_red_packets`、`chat_red_packet_claims`，实际表名遵循 `wanjiedaoyou_*`。红包记录还需发送请求唯一键、请求指纹、退款状态和退款到账记录；资金记录不得级联依赖消息保留期或角色生命周期。领取唯一约束至少覆盖 `(packet_id, claimer_user_id)`。

部署时可导入仍在 Redis 中的最近消息并按 ID 去重；更早已经淘汰的数据无法补回。世界与系统历史独立过滤与读取，不再竞争同一个 100 条池。

### 金额事务

现有 `updateSpiritStones` 将单次 delta 夹至 ±1,000 万，并将最终余额夹至 10 亿；这类静默截断不能作为玩家转移资金的结算方式。红包必须精确、有条件地扣减/增加，任何无法完整完成的写入都整体回滚。

- 发放：权限、金额/数量、余额、冷却、请求指纹校验 → 精确扣总额 → 创建红包和消息 → 提交资源版本及事件；同事务提交。
- 领取：当前身份/宗门权限、账号是否已领、过期状态、剩余份数校验 → 锁定下一份额 → 精确入账 → 扣剩余 → 写领取记录及资源事件；同事务提交。
- 到期：关闭领取 → 计算未领剩余 → 精确退款或形成待退款记录；同事务保证只退一次。
- 待退款领取：锁定退款权益 → 确认发送账号与当前活跃角色 → 精确到账 → 写唯一到账记录并关闭权益；全部同事务，与自动退款和任务重试互斥。
- 重试：发放和领取都返回已有结果；同幂等键换金额或数量返回冲突，不再次扣款。
- 锁：所有资金路径按一致的角色与红包锁顺序，避免领取和过期退款互相死锁；统一现有事务执行器。
- 推送：提交后再广播；推送失败不回滚已提交资金、不引导重扣。可靠通知需轻量事务 outbox，复用现有 NATS，不能声称 NATS Core 自带持久重放。

复用 `PlayerCommandExecutor`、`ResourceEventCommitter`、mutation response 和前端资源 store。红包 revision 单调增长，乱序推送不得把「已领完」覆盖成旧「可领取」。客户端展示状态可以缓存，领取动作永远查服务端权威状态。

## 10. 实施顺序与验收

| 步骤 | 完成内容 | 验证 |
| --- | --- | --- |
| 会话基础 | 持久历史、稳定游标、频道窗口、增量重连、已读和新输入器 | 历史与新消息并发、切频道、断线恢复不丢列表与草稿 |
| 阅读与回复 | 新渲染、引用、原消息附近读取、返回锚点、现有卡片兼容 | 手机/桌面回复完整流程，过期与无权限目标，已有展示入口 |
| 红包 | 纯份额规则、资金事务、幂等、状态更新、领取与退款 | 完整真实请求、余额读回、最后一份并发、超时重试、到期一次退款 |
| 整体收口 | 软键盘、安全区、连续阅读、触控与性能 | 360px/桌面、弱网、长会话、键盘和 reduced-motion |

建议验收标准：

- 历史补页、新消息到达、字体或卡片高度变化时，可见锚点偏移不超过约 2px；这是目标，需要真实浏览器验证。
- 已加载消息在后台请求和重连时保持显示；失败可就地重试。
- 快速切世界/宗门后草稿、回复与阅读位置分别恢复；页面不可见时不误标已读。
- 中文输入法组字不会发出半句话，普通文字换行可读；头像/物品/回放/招募点击互不冲突。
- 读取原消息后可以返回之前位置；审核隐藏不经引用泄漏正文。
- 红包最低金额边界 49,999/50,000、最大金额、整数/小数、份数、等额余数、完整客户端 payload 均经过真实本地 API 验证。
- 发放余额只扣一次，同账号只领一次，到账不足容纳不占份额；总额始终等于已领金额、仍可领金额、已退金额与待退款金额之和。
- 超时后重试不重复扣款，已提交而推送失败可恢复；领取/过期竞争、退款重试和角色变化均有明确结果。
- 使用 `docs/testing.md` 的本地账号，准备数据可恢复；测试写入不进入 staging/production。

实现时运行 lint、typecheck/build，纯整数份额和守恒规则可在 `packages/game-rules/src` 添加确定性单元测试。UI、API、数据库、Redis/NATS 用代码检查与本地浏览器/真实接口验收，不添加 app 层单测或独立 smoke 脚本。

本次仅方案和模拟交互样稿：未修改应用代码，未执行业务资金操作；未运行应用 lint、typecheck/build 或领域测试。样稿的静态与浏览器检查在交付说明中单独报告，不能替代真实加载性能和资金并发验收。

## 11. 成熟产品参考与取舍

- [Slack 已读偏好](https://slack.com/help/articles/360043037853-Manage-your-Mark-as-read-preference)：区分恢复上次位置、进入最新和未见消息保持未读。采用真实可见位置与每频道锚点。

不抢滚动、提前补页和可见锚点恢复是本提案的设计要求，并非以上官方资料已经证实的内部实现。仅借鉴成熟操作习惯，视觉继续服从本项目的纸墨与主流程规范。
