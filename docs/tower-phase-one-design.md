# 蜃楼幻境第一阶段：开发边界与方案

日期：2026-09-19。状态：第一阶段已实施，验收结果见文末。上线方式已按用户补充改为直接硬切。

本文落实新增约束：领奖权威每人只保留一条可覆盖记录；随机周配置每周一条。相较 `tower-completion-audit.md`，以本文的数据模型和阶段范围为准。

## 1. 第一阶段目标与非目标

目标是让现有内容成为可维护、可冻结、可按周编排的完整遭遇池，并建立最小可靠领奖权威。

本阶段包括：

1. 将现有主组合和合法阵容明确登记为完整遭遇，完善类型、校验和战前说明来源。
2. 在现有主套路轮转基础上，按完整遭遇编排整周四个关键层，加入有限的重复抑制。
3. PostgreSQL每周一条发布配置，生成结果和实际敌人定义一并冻结。
4. PostgreSQL每角色一条当前领奖记录，四档奖励的幂等与资产发放同事务。
5. 收口跨周切换、内容更新、缓存丢失后的权威读取与当前周展示。

不包括：新增大批词条、放开封印多敌、设计15/20层新机制、全境界重新调参、修改祝福数量或效果、重做战斗UI、独立管理后台、排行榜持久化重构、历史领奖查询、完整战斗回放留存。

不新增通用规则语言、轮转任务表、领奖明细表、挑战SQL表或独立消息队列。Redis活动战局、既有战斗结算凭据和资源事件基础设施继续使用。

“每人”沿用当前玩法的角色归属，即 `cultivatorId`，不是登录账号 `userId`。这是延续既有领奖口径的方案假设；转成账号级会改变重建角色等行为，应视为单独产品变更。

## 2. 最小数据模型：两张业务表

名称为建议，实施时遵循现有Drizzle命名规则。

### 2.1 `tower_reward_states`：每角色至多一行

| 字段 | 用途 |
| --- | --- |
| cultivator_id | 主键，关联角色；不使用角色＋周复合主键 |
| season_key | 这行当前服务的周 |
| claims | JSONB，键只能为5/10/15/20，最多四项 |
| updated_at | 最近更新时间 |

每个claim保存 `battleId`、`claimedAt` 及实际发放的 `TowerReward` 摘要（灵石、声望、物品）。摘要服务现有“本周机缘”展示，避免缓存丢失后为恢复展示另外查流水或重抽奖励。它仍是一个固定最多四项的对象，不是不断追加的历史日志。

示意：`claims["5"] = { battleId, claimedAt, reward }`。

- 判断某档是否已领只看键是否存在；不再另存一份claimedFloors数组或位图，避免双重事实。
- 不按境界、runId或battleId拆行；同周突破、退出重开都不重置资格。
- 新周首次有效入境时覆盖周标识并清空四项，离线玩家无需定时刷新。
- 旧周在途战斗仍待结算时可以暂保留旧周标识，待结算完成后再进入新周。
- 历史周领取明细不保留，这是该简化模型的明确边界。

### 2.2 `tower_weeks`：每周一行

| 字段 | 用途 |
| --- | --- |
| season_key | 主键，全球共享；不带境界或内容版本 |
| schema_version | JSON结构版本，用于解析兼容 |
| content_version | 生成这一周时使用的内容版本 |
| generator_version | 编排算法版本 |
| config | JSONB，四个关键层结果与冻结敌人配置 |
| created_at | 发布时间 |

`config`包括：

- 周起止时间、四个关键层的完整遭遇ID及必要的模块标识。
- 战前预览所用的名称、成员、说明，保证与实际战斗同源。
- 已解析的NPC单位、数值与行动计划，按开放境界和1–20层组织在一份JSON内。
- 共享敌人技能与状态定义只保存一份；单位以技能/状态ID引用。
- 生成时用于软去重的有限历史输入摘要，便于解释结果，无需另建历史索引表。

推荐复用当前 `compileTowerEncounter` 编译结果制作冻结包，避免先建设一套支持任意历史公式的解释器。7个境界×20层属于有界配置集，不拆成140条数据库记录；实施时测量包体积，必要时仅消除重复定义。

只冻结敌人内容。正常角色、装备、灵兽和祝福仍在每场入场时按现有规则装配，不写入周配置。公共引擎规则升级的兼容性仍须单独验收，冻结JSON并不意味着任意引擎语义升级都不影响旧内容。

已发布行不做普通UPDATE替换。下次部署新内容只影响尚未发布的新周；不得给同周再创建一个“v2周表”。

## 3. PostgreSQL与Redis的职责

| 内容 | 权威存储 | 规则 |
| --- | --- | --- |
| 每周遭遇配置 | PostgreSQL周记录 | 可缓存；缓存失效从DB恢复，不能重新抽取 |
| 每角色已领奖档位 | PostgreSQL领奖记录 | 每次发奖在事务内读取并校验；Redis不得决定资格 |
| 当前爬塔进度、祝福 | 现有Redis run | 保持现状，不承诺Redis全损后恢复整趟挑战 |
| 活动战斗、RNG、命令 | 现有Redis战斗快照 | 继续公共V6规则 |
| 同一战斗是否已结算 | 既有SQL战斗归档凭据 | 与资源写回、奖励提交共事务 |
| 排行榜 | 现有Redis榜单 | 本阶段保留，不新增榜单流水或SQL镜像 |

首版直接读取SQL周记录，不再设置一层周配置Redis缓存或进程内缓存。实际周包约128 KiB；后续确有性能证据时再增加只读缓存。

当前旧 `tower_enemy_floors` 表是按周/境界/层拆分的历史模型，不适合本次要求。当前V6塔入口未使用它；新增两张小表，不复活旧模型，也不顺手DROP旧表和仓库。

## 4. 完整遭遇池的边界

定义一个类型化清单，将现有六个主组合与现有合法关键层阵容展开为可选完整遭遇。稳定ID代表主组合＋阵容，另列适用精英/首领；不必为每一个境界或每层再注册一个ID。

首阶段沿用现有规则：

- 精英：单体或主攻＋治疗。
- 首领：单体、主攻＋治疗、主攻＋双镜侍。
- 封印：仅单体。
- 铁甲：不与双镜侍结合。
- 辅助不继承主怪特性或低血阶段。

当前六套主组合产生10个精英候选、12个首领候选；其中一些共享完整遭遇身份，不应宣传成22种独立玩法。

内容仍分为主套路、特性、阵容三种可复用定义，但抽取只能从完整遭遇清单中选择。用Zod/类型校验检查引用、适用楼层、角色份额、周期技能和预览一致性，避免只检查两个标签是否兼容。

该清单表示本阶段允许编排的现有内容范围，不宣称全部境界已经平衡。全境界策略和数值验收仍属于后续阶段。

## 5. 抽取与轮转方案

### 硬约束

1. 保留现有按绝对周序确定的三套路骨架。
2. 5/15层主套路不同，10/20层主套路不同，同层相邻周主套路不同。
3. 保留同周主组合不重复这一现有保证，不因换了阵容而允许同一主组合重复占位。
4. 只取适用楼层的完整遭遇，每周至少一个多敌关键层。
5. 同一周所有境界使用相同遭遇主题，境界只决定冻结数值档。

### 软目标，按顺序比较

1. 减少最近三周已发布周表中完整遭遇的重复，优先照顾10/20层。
2. 减少同位置与上一周相同的阵容。
3. 减少同周阵容同质化。
4. 并列候选使用 `seasonKey + generatorVersion + 候选稳定签名` 的哈希确定顺序。

使用按优先级比较的评分元组，不做一堆需要调参的权重。输入包括候选池和有限历史；“确定性”指同样全部输入得到同样结果，不只看seed。

### 执行步骤

读取目标周 → 已存在直接使用 → 未存在则读取最近三个日历周内已发布记录 → 有界枚举四个位置的合法组合 → 选择最优候选 → 编译/校验冻结包 → `INSERT ... ON CONFLICT DO NOTHING` → 重新读取DB中胜出的周记录。

历史缺周时不递归补生成过去周表，缺失的历史不参与软惩罚。硬约束不依赖历史查询，仍由周序骨架保证。并发实例只能使用DB胜出记录，不能将本地失败候选返回或写缓存。

第一阶段不要求每个条目在固定N周内必出、不设置硬冷却和出场权重、不允许人工覆盖已发布周表。先通过连续周模拟观察分布；分布明显失衡再针对性调整。

空池或硬约束无解应由发布前共享测试阻止。线上意外无解时返回“本周幻境暂未就绪”，不放宽禁配、不覆盖已有周表。当前池固定，不为理论异常搭备用内容管理系统。

周表在该周首次请求时按需发布，不新增必须成功运行的周一cron。若两个版本部署恰好跨过换周，首次成功发布者决定本周内容；发布过程需避免未完成版本混跑，后续请求服从已发布行。

## 6. 领奖事务与重试

继续使用角色级Redis锁和SQL角色行锁，不新增每个档位的分布式锁。

终局处理：

1. 按现有流程保存Redis终局快照；服务器决定胜负和奖励候选，重试不重抽。
2. 开SQL事务、锁角色，检查该battleId是否已有结算凭据。
3. 已有凭据则跳过资产和condition写回；按SQL领奖记录同步展示状态，完成Redis确认。
4. 未结算则读取/初始化领奖行；若周不匹配，按跨周规则处理，禁止盲目覆盖。
5. 胜利且为关键层、对应档未领时，在同一事务内发放资产并写claims条目。
6. 同一事务内完成正常资源写回、资源事件和现有战斗结算归档；即使该档已领，本次战斗仍需正常结算和推进。
7. 提交后发布资源变化，更新Redis run和榜单，响应客户端。

数据库失败则资产和claims一起回滚；SQL成功但Redis确认失败时，重试依据SQL凭据/claims恢复，不能再次发奖。首次创建领奖行也在角色行锁内完成，主键作为最后一道并发约束。

不增加手动“领取”按钮或新的claim接口，沿用关键层胜利自动到账。发奖逻辑仍由服务器当前合法战斗驱动，客户端不能提交周标识或奖励内容来决定资格。

## 7. 一行领奖记录下的跨周规则

核心不变量：新周挑战不能与该角色尚未处理的旧周战斗并存；领奖行只能向新周推进，不能回退。

| 情况 | 处理 |
| --- | --- |
| 只查看页面 | 返回当前周信息和上次挑战结果；不清空/切换领奖行 |
| 旧周无活动战斗 | 旧挑战结束；首次有效进入新周时锁内覆盖领奖行 |
| 旧周仍有活动战斗/待结算 | 先完成旧战结算及确认，领奖行仍服务旧周；再允许新周入境 |
| 旧周战斗已结算，确认请求重试 | 依据已有战斗凭据处理，不碰新周领奖资格 |
| 领奖行已在新周，却出现未结算旧战 | 这是违反串行不变量的异常；拒绝旧奖励写入并明确报错，不能回退或清空新周行 |
| 角色数周未登录 | 下次有效入境直接跳到当前周，不逐周创建空记录 |

跨周旧战暂沿用现有“周末后额外保留一天”的有效窗口，不引入无限保留。若需要延长，应作为单独变更。Redis全量丢失可能丢失活动战局，本阶段保证持久化的已领奖事实与周配置可恢复，不承诺恢复丢失的战斗。

周切换必须在 `/start` 的角色锁与SQL事务内重检旧战占用；GET不执行换周写入。创建新run的Redis写入失败后允许重试，重复切到同一周是无副作用操作。

## 8. 内容冻结与接口边界

- 当前周发布后，普通词条、阵容、NPC数值改动在下一周生效。
- 新run绑定该周的已发布配置，后续每层从同一冻结包取敌人，不能读取最新全局常量重新解释组合ID。
- 已开始战斗继续自身冻结快照；不因部署新内容无故结束当前版本仍兼容的挑战。
- 确需紧急停用严重问题内容时，先暂停新的开战；本阶段不制作同周多版本榜或后台替换器。引擎不兼容升级另定迁移，不能靠改内容版本号自动解决。
- 保留现有路由、鉴权、runId/revision/所有权检查，调整内部读写路径和必要契约。
- 顶层 `season`、`weeklyEnemies` 和“本周机缘”均属于当前周；旧结果在state内携带自身season信息。旧战页面仍按旧战绑定内容显示。
- 若领奖行仍为旧周，当前周奖励展示为空，旧战收益留在其结果信息中；不为展示触发清空。
- 复用现有页面层级、弹层和公共战斗组件，不额外添加周历或版本面板。

## 9. 直接硬切与旧数据

用户已明确要求上线直接硬切，不等待下周。部署时先应用 `0052_tower_week_publication.sql`，停止旧实例后启动新版，禁止旧新实例长期同时服务塔请求。

- 活动挑战改用 `tower:v6:published:run:*`；旧版挑战立即不再可恢复，旧版指令不能命中新战斗。已入场恢复的正常角色资源不回滚，也不补发未结算战斗的奖励。
- 榜单改用 `tower:v6:published:leaderboard:*`，避免不同敌人配置的成绩混排；原榜不删除，按原TTL自然过期。
- 本周新配置按需发布到SQL一条记录，随后不可因部署版本更新而替换。
- 领奖资格不重置：首次新入境在角色锁内合并旧Redis本周奖励列表、旧run中的已领摘要，以及旧终局已存在SQL结算凭据的奖励，写入每角色唯一领奖行。之后只使用SQL资格。
- 导入记录 `battleId` 可为null，`claimedAt` 为导入时间；不伪造旧系统未保存的准确领奖时刻。
- 本阶段不做旧表删除、全局Redis清空或全库回填。旧Redis记录自然到期；导入仅用于尚无SQL领奖行的角色。
- 旧系统如果在硬切前已经同时丢失Redis领奖列表与run摘要，现有SQL凭据不足以反查每角色每档历史，这是既有数据不可恢复的限制；新版SQL权威消除了之后的该类资格丢失。

当前蜃楼属于非竞技战斗，`archiveCombatV6Replay` 只保留战斗结算凭据，不保存完整replay或参与者信息。本阶段不扩展回放基础设施。

## 10. 文件与验收边界

主要改动预计在：

- `src/shared/lib/tower/weekly.ts`、`formations.ts`：完整遭遇清单与编排。
- `src/shared/engine/combat-v6/tower/content.ts`、`host.ts`：编译冻结敌人包、读取发布内容。
- `src/shared/contracts/combatV6Tower.ts`：当前周与旧挑战归属。
- `src/server/lib/drizzle/schema.ts`、主业务迁移：两张表。
- 一个小型塔持久化仓库：读写周记录和领奖状态，透传事务，不建立泛化仓库框架。
- `src/server/lib/tower/combatV6.ts`：周发布、领奖事务、换周与兼容。
- `src/react-app/routes/game/tower/route.tsx`：仅同步周归属与奖励展示。

纯共享测试：完整遭遇引用合法；禁配；同周及跨周约束；缺历史；多周分布；冻结包与预览一致；更新源配置不改变已有包；领奖状态纯转换的同周保持、向前切换及拒绝回退。

服务端/数据库验收：唯一周记录的并发发布；角色唯一行；同档不同run不重复领奖；SQL回滚；SQL已成功后的重复确认；跨周旧战结算后再入新周；缓存丢失后读取DB；发布升级不改变本周敌人。只用项目允许的代码检查与运行验收，不新增服务端/数据库单元测试或一次性故障脚本；无可用验证手段的场景明确标注未实测。

页面验收：当前周信息、旧战结果、奖励摘要归属一致；刷新与返回不重抽；战斗继续公共页面；移动端布局不回退。

实施后运行针对性共享测试、lint、build及必要的迁移检查；需要应用迁移时仅针对明确本地环境。第一阶段完成不等于已通过高境界与完整20层平衡验收。

实施没有新增词条、技能或数值倍率；保持现有五项祝福和公共战斗UI。验证记录见文末。
