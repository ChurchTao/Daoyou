# 道装铸造命名

## 行为

- 玩家可填写100字以内的铸器心念；为空时仅根据材料和图纸命名。心念只影响器名和描述。
- 服务端读取投入材料的名称、描述与数量，结合图纸境界、部位请求 `equipment-forge-naming`。每份材料描述最多传入240字符。
- 模型只输出 `name`（2至8个汉字）与 `desc`（60字以内，含标点的单行纯文本）。心念和描述按 Unicode 码点计数。
- 新打造装备保存 `crafterName`：提交事务中读取的角色名称快照，不保存铸造者角色ID，不随改名或转手更新。
- 预览头部在要求后展示铸造者；描述使用既有底部描述栏。旧装备缺少新字段时直接省略。
- 命名或校验失败时使用原有默认器名，不生成描述；仍保存铸造者快照，照常完成打造。
- 不改装备数值、随机流、品质、器蕴或器诀，不强制全服器名唯一，不提供重新抽名。

## 提交边界

`ForgeRequest` 增加必填 UUID `requestId` 与可选 `intent`。前端一次开炉生成一个请求ID，错误后的“重试本次开炉”复用原参数。

1. 获取仅用于开炉的准备锁，查询已完成的幂等记录；已完成请求跳过材料预检和模型调用。
2. 未完成请求预检角色操作状态、背包物品版本、材料、境界、灵石和灵气。
3. 在角色写锁和数据库事务外调用 `generateAiObject`，总超时8秒，复用既有提供商、BYOK、指标与结构化纠错机制。提供商接收基础 schema，返回值由本地严格 schema 校验。
4. 通过 `playerCommandExecutor` 获取角色写锁并开启事务，重新校验物品版本和资源，生成装备，读取铸造者名称，原子完成扣料、扣费、入包与幂等结果记录。
5. 提交后通过既有资源事件刷新货币、角色、背包和材料。

同一请求ID返回原来的装备；同一请求ID换参数返回409。准备锁只限制同角色并发开炉，不阻塞命名期间的其他角色写操作；其他操作改变材料时，提交阶段会拒绝旧版本。

新字段存于既有 `inventory_items.instance_data`，无需数据库迁移。库存严格解析与V6装备校验同时支持新字段，打造名称不再要求命中旧词池；原部位、版本和数值校验保持生效。

## 库存读取 400 修复（2026-09-21）

本地报错“未知物品定义”来自历史青溪材料：固定定义已删除，但库存仍引用旧 ID，严格解析导致整页读取失败。新打造装备的名称、描述和铸造者字段本身有效。

迁移 `0054_restore_legacy_material_facts` 将青溪铁砂、青溪磨石、青溪兽骨、青溪灵玉转换为 `material.v1`，恢复删除前的名称、类型、凡品品阶、无五行和描述。保留实例 ID、归属、数量及位置，按当前 UTF-8 长度前缀算法重算堆叠键，并递增物品及库存资源版本。仅转换四种已知旧 ID，不跳过非法库存或恢复废弃运行时定义。

本地已执行 `bun --env-file=env/local.env node_modules/drizzle-kit/bin.cjs migrate`，迁移 9 条记录；全库 113 条库存记录通过当前 schema，迁移后的堆叠键与运行时算法一致。浏览器实测背包与储藏室接口均返回 200，“归家玄铁冠”的名称、描述和铸造者展示正常。

其他环境需通过各自环境的正式业务迁移流程应用 0054；本轮未写入预发布或生产。迁移不推送实时事件，已打开页面需刷新以取得最新数据。
