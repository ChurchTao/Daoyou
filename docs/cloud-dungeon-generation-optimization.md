# 云游探秘：生成与审校成本优化方案

日期：2026-11-04。状态：供应商调研、依赖更新与最小改造已完成，单本完整生成入库已验证；调试用的本地后台消费禁用限制已撤销，首批生成由用户自行启动。

> 现行模型配置：BYOK 已退役，全部调用只使用服务端路由和凭据；历史实测及验收结果不因此改写。模型配置见 [AI 能力](development.md#ai-能力)。

执行范围已收窄：当前仅统一 Alibaba 开启思考时的预算为 4,096，并补齐程序事实、变体角色说明和审校上下文；提示词模板、调用轮数、重试、入库门槛保持原样。下文的审校去重、分阶段预算、总时限和新门槛属于前期方案，未实施；当前运行结果见末节。

## 1. 实测基线与目标

基线为《云梦逆纹案》，`SAT_TN_02 / inheritance_murder / decoy_liar`，生成版本 6。任务 `1d401559-8220-411a-8bf9-a907dee95520`，剧本 `df7e2fbb-86e5-4698-a77a-0391d2f2fd72`，模型 `alibaba/qwen3.8-flash`。

token 来自供应商 usage 和 `[LLM_METRICS]`；耗时由 Redis 中各调用的完成时间还原，串行阶段包含少量本地处理时间。三段正文并行，不能将其耗时相加。

| 阶段 | 耗时约 | 输入 token | 思考 token | 可见输出 token | 总 token |
| --- | ---: | ---: | ---: | ---: | ---: |
| 大纲 | 7分31秒 | 6,658 | 26,977 | 1,881 | 35,516 |
| 场景正文 | 23秒 | 4,381 | 0 | 1,030 | 5,411 |
| 证据正文 | 21秒 | 3,627 | 0 | 1,022 | 4,649 |
| 人物正文 | 13秒 | 3,627 | 0 | 650 | 4,277 |
| 修正审校 1 | 10分14秒 | 4,819 | 36,980 | 671 | 42,470 |
| 修正审校 2 | 9分37秒 | 4,834 | 30,704 | 246 | 35,784 |
| 独立入库审校 | 11分48秒 | 4,660 | 37,091 | 324 | 42,075 |
| 合计 | 39分33秒 | 32,606 | 131,752 | 5,824 | 170,182 |

- 7 次调用全部成功，`retryCount = 0`。此次成本来自正常链路，不是重试。
- 思考占总 token 的 77.4%；三次审校占总 token 的 70.7%、墙上耗时的约 80%。
- 第二次审校只修改 2 处 minor，却花费 35,784 token；第三次审校又重新审查全文。
- 入库审校报告 2 major、1 minor，按现有门槛通过；该报告不代表问题已经修复或全部判断准确。

首轮改造验收目标：正常路径 5 次调用，允许最多 1 次局部复核；单本总 token 目标不超过 45,000，正常完成时间目标不超过 5 分钟，执行总时限 6 分钟。这些是待实测的目标，不是已经取得的结果。

## 2. 供应商调研结论

本项目使用 `@ai-sdk/alibaba` 的 OpenAI 兼容 Chat Completions，结论按这一接口核对，不能直接套用 Responses API 的参数。

### 2.1 开关、数值预算、原生强度分别控制什么

| 控制项 | 请求字段 | 对当前 Qwen 的作用 | 本方案选择 |
| --- | --- | --- | --- |
| 思考开关 | `enable_thinking` | 开启或关闭思考 | 正文显式关闭 |
| 思考预算 | `thinking_budget` | 达到预算后结束思考并进入回答 | 大纲与语义审校显式设置 |
| 原生强度 | `reasoning_effort` | `low / medium / xhigh` 档位 | 了解映射，但首批使用数值预算 |
| 回答长度 | `max_tokens` | 当前 Qwen 仅限制回答，不包含思考 | 由现有 SDK 的 `maxOutputTokens` 设置 |
| 总输出长度 | `max_completion_tokens` | 包含思考及回答 | 当前 Alibaba 适配器没有对应选项，不假定已生效 |

数值预算的行为见[百炼深度思考说明](https://help.aliyun.com/zh/model-studio/deep-thinking)。Qwen3.8 的原生强度默认 `xhigh`，`low / medium / xhigh` 对应 4,096 / 16,384 / 262,144；原生强度与数值预算互斥。`max_tokens` 与 `max_completion_tokens` 的范围不同，详见[Chat Completions 参数](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions)。本方案不依赖供应商缺省预算。

### 2.2 当前 SDK 确实支持什么

核对 `@ai-sdk/alibaba@2.0.82` 的 `src/alibaba-chat-language-model-options.ts` 与 `src/alibaba-chat-language-model.ts`：

- `providerOptions.alibaba.enableThinking` → `enable_thinking`。
- `providerOptions.alibaba.thinkingBudget` → `thinking_budget`，要求正数；关闭思考应传开关，不用预算 0。
- 目前没有 `providerOptions.alibaba.reasoningEffort` 或 `maxCompletionTokens`，不能添加不存在的选项并假定适配器会透传。
- `maxOutputTokens` → `max_tokens`，因此本项目必须同时限制思考预算与回答长度。
- 供应商思考选项优先于通用 `reasoning`。本项目现有 `thinking: true` 会发送 `enableThinking: true` 并选择 `provider-default`，不附带预算。

SDK 官方的[Alibaba 选项说明](https://ai-sdk.dev/providers/ai-sdk-providers/alibaba)也提供 `enableThinking` 和 `thinkingBudget` 的组合用法。首批不改接口、不改写第三方包源码，使用安装版已经支持的字段。

安装版的通用 `reasoning` 并不发送百炼原生强度，而是以固定的 16,384 为基数换算数值预算。结合 `@ai-sdk/provider-utils@5.0.74/src/map-reasoning-to-provider.ts`，实际如下：

| SDK 通用 reasoning | Alibaba 实际发出的预算 |
| --- | ---: |
| `none` | `enable_thinking: false` |
| `minimal` | 1,024 |
| `low` | 1,638 |
| `medium` | 4,915 |
| `high` | 9,830 |
| `xhigh` | 14,746 |
| `max` | 15,565 |
| `provider-default` | 不设置预算 |

该表是当前安装版实现，不是百炼的原生强度表；版本升级后应重新核对。为使业务成本可解释，本次采用精确数值预算。

### 2.3 模型兼容边界

- 第一批仅以 `alibaba/qwen3.8-flash` 为预算控制目标。官方模型页确认其支持结构化输出，但具体密钥、区域或代理是否接受预算，仍需小额实际调用验证，见[模型能力](https://help.aliyun.com/zh/model-studio/qwen3-8-flash)。
- 百炼 Chat 参数明确 `kimi-k3` 不支持 `thinking_budget`；深度思考总览与 Chat 参数页对它能否关闭思考的描述不一致。不得因同属 Alibaba 就自动套用 Qwen 策略，也不得静默删除预算后继续无上限调用。
- 新预算校验在服务端解析完实际 provider/model 后执行，覆盖高级组与权重选择得到的服务端路由。只对传入新预算选项的调用检查；既有其他 AI 场景保持原行为。
- 需要预算而实际模型不支持时，在发送请求前返回明确的不可重试配置错误。后台生成应固定到支持预算的目标路由；不擅自改服务端模型配置或供应商。
- 各步继续只传结构化事实，不回传上一阶段的思考内容。升级适配器支持保留历史思考，但本链路是独立请求，目前没有历史思考回放，不能把这次 17 万 token 归因于它。

## 4. 先修事实边界，再减少审校

### 4.1 大纲拿到完整的不可变关系

大纲当前只收到房间、人物、守卫、答案等摘要，缺少物件位置和线索来源。本次大纲将碑面写在静室，而程序规定它在剑冢；这份冲突随后被三个正文请求继承。

补充的最小事实包括：物件所属房间、线索／物品的发现对象、角色真实职责、反应触发证据及效果、事件影响对象。ID 和结构不交给模型修改。位置等事实在展示时尽量由程序统一引用，避免不同段落自由重新指定地点。

变体覆盖后的角色规则作为统一输入。当前 `decoy_liar` 要求凶手不说谎，但基础模板仍要求凶手必须有可戳穿的谎言；人物 Schema 也残留“凶手说出谎言前”。同步修正这些角色描述，改用本局实际的说谎者。

### 4.2 审校同时看到事实和触发条件

每次审校使用同一份服务端 `reviewContext`：canon、人物真相、房间归属、证据关系、对话触发条件与结果。事实边界来自程序和已确认大纲，不从正文中反推。

审校字段分为只读参照与允许修改的正文。当前 `locked` 直接过滤掉字段，后续应保留只读事实供对照，模型只对可修改路径提出 patch。程序生成的谎言原话、机关答案、引用关系继续由程序控制。

本次首轮审校将碑面正文从剑冢改成炼剑池，但 `roomId` 仍指向剑冢；最后一轮还省略了 canon。新审校必须识别权威位置，修改冲突的正文，不能移动事实去迎合其他文字。

人物的初始说法、澄清嫌疑、被戳穿后坦白需标明阶段。既允许设计中的谎言，也检查没有暴露谎言的反应是否提前坦白。不能简单把所有人物反应并列为同时成立的事实，也不能一律豁免人物台词矛盾。

### 4.3 共享确定性校验继续负责结构

保留 `MysteryCaseFileSchema` 与 `validateMysteryCase`。结构、引用、答案、机关解法和可解性继续由程序验证；LLM 只核对文义与明确事实是否相符。纯文字语义不能用几条关键词匹配冒充完整验证。

## 5. 目标生成链路

程序骨架与事实摘要 → 受限思考大纲 → 三段无思考正文并行 → 程序组装与校验 → 一次语义审校并修正 → 程序复验 → 必要时局部复核 → 入库。

正常路径是 1 + 3 + 1 = 5 次调用。生成器返回同一份审校结论和阶段指标，由 `ScenarioLibrary.runJob` 执行入库门槛，不再丢失上下文后另做一次全文审校。

### 5.1 首轮参数

以下为拟实施的初始值，集中维护在 `mysteryGenerationSettings.ts`；需要用真实小样本验证质量、预算和时限。

| 阶段 | 思考预算 | 回答上限 maxOutputTokens | 单步时限 | 执行条件 |
| --- | ---: | ---: | ---: | --- |
| 大纲 | 4,096 | 4,096 | 120秒 | 每本一次 |
| 场景正文 | 关闭 | 2,048 | 60秒 | 与其他正文并行 |
| 证据正文 | 关闭 | 2,048 | 60秒 | 与其他正文并行 |
| 人物正文 | 关闭 | 2,048 | 60秒 | 与其他正文并行 |
| 全量语义审校及修正 | 2,048 | 2,048 | 90秒 | 每本一次 |
| 局部复核 | 1,024 | 1,024 | 45秒 | 发生重大语义修改时，最多一次 |

大纲的 SDK 参数示意：

```ts
{
  reasoning: 'provider-default',
  providerOptions: {
    alibaba: { enableThinking: true, thinkingBudget: 4096 },
  },
  maxOutputTokens: 4096,
}
```

项目公共调用层需先增加并校验服务端 `thinkingBudget` 选项（正整数、阶段上限、实际模型兼容性），以上配置才会真正传到 SDK。本轮没有实现该选项。

保留现有 `thinking`／`reasoning` 的调用兼容性；预算只在明确请求时生效。新预算与 `thinking: false` 或另一项强度设置冲突时直接报错，不通过优先级悄悄忽略。预算路径不发送原生 `reasoning_effort`。

### 5.2 审校输出和入库规则

- 一次全文审校同时输出问题依据、关联字段和必要 patch；每个确认问题必须指向事实或另一个字段，减少无法核实的风格意见。
- 报告区分已修复问题与剩余问题，不能用“曾发现多少 major”代替“仍有多少 major”。
- minor 修正后做程序校验，不再因此触发全文重审。
- 重大语义修改触发一次局部复核：带上修改前后内容、不可变事实及关联字段，保持足够上下文，不只发送孤立的一句。
- 建议新门槛为“剩余、确认的 major 为 0”，minor 可保留；证据不足的疑点标记待人工判断，不自动改权威事实。该门槛比现有“最多允许 2 major”更严格，需在小样本确认误报控制后再启用。
- 结构不合法、确认的重大矛盾未解或复核失败，不入库生成本，也不把保底案卷标成生成成功。

## 6. 时限、重试与模型预算一起控制

### 6.1 消除多层重试放大

目前包含 SDK 传输重试、`generateStructured` 的结构重试、`callStage` 再调用、大纲真相重写、队列任务重试。虽然本次样本没有重试，受限预算上线后更容易遇到截断，必须先统一重试责任。

- 为解谜生成调用设置 SDK 自动重试为 0，由链路协调唯一的重试入口；其他 AI 场景的缺省行为保持不变。
- 每次任务认领执行最多追加一次模型调用：用于允许的格式／网络重试或局部复核，二者共用额度。不能各层分别再试一次。
- 有效但质量不达标的稿件只修复问题范围，不重跑成功的大纲和三段正文。
- 当前截断重试会将 `maxOutputTokens` 放大 1.5 倍，最高到 16,384。解谜预算路径应固定上限，截断进入受限修复或失败，不自动放大回答或思考预算。
- 普通调用失败在已有额度内处理后仍失败，任务标为 failed，等待管理员决定重试；停止当前失败即回 queued、工作者立即再领的连续整本重跑。进程中断的恢复另按已有尝试次数处理，并在观测中区分。

### 6.2 单本时限和用量阈值

- 每次认领执行共用 6 分钟总 deadline；每步使用“单步时限与剩余总时限的较小值”，包括重试和复核。
- 先停止发起后续调用，再取消该次执行的其他未完成请求；不能因其中一段失败仍让其余无用调用继续运行。
- 已发出的请求可能已经产生费用，取消不能当作撤销费用。全书 token 目标为 45,000，用量达到 50,000 后停止追加调用；这是依据已返回 usage 的停止阈值，不是供应商层面的整本硬配额。
- 并发正文的在途用量、协议记账差异及进程崩溃后的未知消耗都使“精确整本硬上限”无法仅靠事后求和保证。请求级预算、回答上限和总 deadline 才是本轮可以实施的强约束。
- 首轮不新增业务表字段。跨进程累计费用先做可追踪观测；若需要严格持久化配额，应另做数据模型与事务设计。

## 7. 预期收益与取舍

使用本次输入、可见输出保持不变，按正常路径只保留一次审校计算：

- 无思考的静态账面为 28,366 token。
- 加上大纲 4,096 和审校 2,048 的思考预算，约 34,510 token，比本次低约 79.7%。
- 新上下文会增加输入，生成内容与审校结果也会变化，所以以 45,000 作为首轮验收目标，而不是承诺一定等于 34,510。
- 受限思考可能影响复杂案型的细节判断，局部复核上下文过少也会漏检；用明确事实和针对性人工抽查验证，预算不足时先分析失败原因，不自动升级到无预算思考。

模型继续使用当前 Qwen，便于比较参数与链路变化；首轮不同时换模型。三段正文保留并行，增加工作者并发不能降低单本 token，也不能消除串行审校。

输入裁剪和缓存属于后续优化：本次输入只占约 19.2%，优先处理思考及审校重复。首次改造避免再扩大分段数量或引入多模型投票。

## 9. 实施顺序和验收
