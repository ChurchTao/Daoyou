# Phase 8C：房间观战与在线验证

> 2026-09-06：观战代码已接入，真实 1v1 加观众的完整主链路复验通过。未部署远程环境；4v4 观战负载与故障矩阵未通过前，不宣称 Phase 8 整体验收完成。

## 产品边界

- 沿用擂台六位邀请码，选择参战席或观战席。房间单独展示观战名单；准备、阵容冻结、房主交接只计算参战者。
- 首版每房最多 50 个观战席，作为有界资源限制，不代表已验证的在线容量。每账号每 API 实例最多四条战斗连接，沿用既有连接约束。
- 候场时可入席，战斗中可凭同一邀请码中途加入；开战创建期间及终局不接受新观众。观战者可退出，不参与收令、离线自动普攻、角色战斗占用或奖励结算。
- 双方固定青方、赤方；公开 HP/MP 比例、护盾、状态、提交状态及已发生行动。精确属性、私有资源和未执行指令不发送给观众。
- 中途进入及重连恢复最新完整基准，后续逐行动实时播放。无实时暂停、回退、倍速或人为延迟。
- 观众不写入回放参与角色关联表，不获得历史战绩或回放权限。既有回放 API 的参与者鉴权保持独立。
- 不包含 PvE 观战、公开大厅、分享、聊天、匹配、排位、召唤兽及全仓 v5 清理。

## 实现

### 房间与生命周期

房间 Redis 文档增加独立 `spectators` 集合；使用既有房间账号／角色索引恢复席位，但不写入 v6 战斗占用索引。入席、退出沿用房间 revision CAS。观战席不会进入 frozen roster 或引擎参与者列表。

开战时原子延长房间与关联索引有效期至 7500 秒，覆盖战斗两小时绝对期限。终局立即释放账号／角色房间索引、邀请码及战斗反向索引，同时保留五分钟 `finished` 房间，供已入席观众获取终局、完成播报。终局写入检查房间 revision，避免与观众退出竞争后恢复已撤销的席位；终局房间不重新建立或续期其他房间的占用索引。

### 读取与推送

- `GET /api/combat-v6/arena/:battleId/watch`：校验当前账号、活跃角色、该战斗绑定的房间及观战席；返回公共完整基准或匹配游标的差量。
- `GET /api/combat-v6/arena/:battleId/watch/socket`：相同观战鉴权，另有 WebSocket Origin 校验。观众不调用参战 presence 的 touch/disconnect。
- 沿用人物战斗 URL，`?watch=1` 只选择页面模式，不授予服务端权限。现有 commands/replay 端点仍只认可真实参与者。
- 公共视图独立生成，双方均隐藏精确值。每次引擎权威行动观察额外产生一份公共差量，不按观众数量重复演算。
- 每 API 实例同场观众共用 NATS 订阅、运行态读取、公共投影和消息序列化；积压通知合并为待处理标记，不无限排队。发出前核对房间席位。
- 回合消息仅携带该结果的新增战报；状态通知不重复发送完整历史。缺口通过 HTTP 恢复。单消息超过既有大小门槛发送 resync；观众发送缓冲超过 512000 字节时断开慢连接并允许恢复。
- 复用既有会话 reducer、单位结构共享、战报整理和逐行动计时。观战页面移除指令栏与查看回放链接，退出操作先撤销房间席位。

无需新增数据库表或迁移，也不新增功能开关。维护期同步发布前后端，不续跑旧擂台战斗。

## 完整主链路复验（2026-09-06）

仅使用现有纯本地服务，local1 为房主，local2 为另一参战者，local3 为观众。Chrome 房主使用 localhost 会话，内置浏览器分别使用 127.0.0.1 与 localhost 的独立 Cookie 会话；页面确认三个角色身份。local2 经 Mailpit 正常验证邮箱后登录，未改写认证数据或构筑。

第一场 `506a8f2a-b757-4bb4-8b70-7edb04b43e83`（房间 `arena-d3843265-dd64-4207-9369-bf49ad869b00`）验证：

- 双方准备、房主开战后，观众自动进入只读战斗页面；观众不影响收齐指令。正常攻击／防御以及超时普攻持续推进到第八回合，逃跑成功后赤方获胜。
- 实际 WS 公共消息仅含比例血条、公共事件及差量；单位无精确 attributes、私有 resources，commandOptions 缺失。第一回合的 HP 差量为 `9484`（94.84%），防御和回合末各保留空更新帧，界面未提前改变血条，后续显示攻击及防御战报。
- 详情弹窗只显示百分比与公开状态；观战刷新恢复当时最新回合。战中退出后返回擂台，直接重开观战地址显示入席要求；凭原邀请码重新入席后恢复最新状态。
- 关闭观战标签页后，双方提交防御仍完成第五回合；重新建立观战连接恢复第六回合与既有战报，不要求观众回执。
- 观战者直接进入参战页面显示“无权访问此战斗”。终局继续收到并完成播报，显示“赤方获胜”，没有查看回放链接；直接请求该场归档的页面收到 `/api/combat-v6/replays/:id` HTTP 404。相同 battle ID 由参战者打开则正常显示 23 帧回放及八个回合选项。
- 360px 战斗布局采用既有敌方／战报／我方纵向排列，页面 clientWidth 与 scrollWidth 均为 360，无横向溢出。

本场网络发现重复推送：锁令和结果通知先后触发读取时，可能都读到同一个最新结果 revision。客户端已有去重，未重复播放，但服务端多发送了一份结果。修复观战广播组：记录已发送 revision，同时在接收通知和读取权威状态后去重，保留缺口 HTTP 恢复与席位鉴权。

第二场 `1badf7eb-7390-426e-bfa5-62593442dc8d` 验证修复：第一回合双方防御，第二回合逃跑终局。网络记录 revision 1、2、4、5、6、7、9 均各出现一次；回合结果 revision 4 含三帧，终局 revision 9 含两帧，赤方获胜。1200px 下双方血条 top 均为 145.7890625、height 均为 36.796875，页面无横向溢出。已退出观战和双方战斗页面，恢复临时视口；两场均正常终局，不遗留活动战斗。

修复后执行 `bun run lint`、`bun run build`、触及文件 Prettier 与 `git diff --check`，均通过。仅变更服务端推送去重，未修改引擎或共享规则，本次未重复运行共享单元测试，也未新增服务端测试或一次性脚本。上述结果限于真实 1v1 加一名观众，不替代多实例、4v4 加 10／50 观众或网络故障压力验收。
