# 修仙日志

入口为展开导航中的「修仙日志」（`/game/journal`）。页面按时间倒序紧凑展示，一次结算一条，可筛选闭关／突破／其他玩法并加载更多。旧记录不回填。

## 存储与展示

数据库迁移为 `drizzle/0060_player_journal.sql`，已合并本轮未上线的讨伐与日志迁移，仅创建最终使用的日志表。

`wanjiedaoyou_player_journal` 同时保存业务执行凭据和玩家可见的结构化结果，不另建收支明细表。`event` 使用 `packages/shared/src/contracts/playerJournal.ts` 的可辨识联合契约，前端按类型渲染、按资源统一颜色与数字格式。

- 闭关：年数、实际修为与感悟收益、实际灵气消耗、寿元耗尽结果。
- 突破：成功／失败、前后境界、实际修为与感悟变化、灵气消耗、寿元上限和属性奖励。
- 契约保留原结算摘要，用于重复请求返回原结果；重复请求不会重新生成突破故事。
- `GET /api/player-journal` 只查询当前登录角色。每页最多 30 条，以毫秒时间和 UUID 组合游标分页；接口不返回幂等键或请求指纹。

## 执行凭据

`(cultivator_id, operation_key)` 唯一。闭关／突破请求必须携带 UUID `requestId`，键为 `retreat.cultivate:{requestId}` 或 `retreat.breakthrough:{requestId}`；指纹包含动作和年数。同键不同参数返回 409。

`PlayerCommandExecutor` 的 `journal` 选项在现有角色事务中占位，业务成功后补全 `event`，失败整体回滚。占位时的空事件不会提交；重复请求读取已提交事件并跳过结算。该选项与旧 `idempotency` 选项互斥，接入玩法不会再写 `player_mutation_requests`。

闭关入口在角色锁内先读取已完成凭据，再判断当前突破门槛，避免原操作改变进度后阻止正常重试。事务内仍通过唯一键保护实际写入。客户端在 sessionStorage 中保存未确认结果的请求键，收到结算结果后删除；重试回放后重新获取当前角色资源，避免把旧状态当作当前状态。

已接入的普通玩家请求改用日志保存执行凭据和原结果，不再同时写 `player_mutation_requests`；读取兼容旧凭据，防止上线前请求再次结算。灵气预留／提交账目、限购事实、战斗归档和独立消息消费者凭据仍由各自流程维护，不删除旧表。

## 保留与演进

组队讨伐使用 `hunt_reward:{出现ID}` 作为每个角色的唯一领奖键，复用日志的私有结果保存战斗 ID、实际奖励与邮件 ID，替代独立的 `hunt_reward_claims` 表。首次胜利提交凭据和发奖同事务；同次出现再次胜利判作助战，不能重复发奖或寄信。纯邮件奖励或资源全部达到上限时仍保留不可见凭据。

执行凭据不参与普通历史清理。清理一条记录会重新开放对应业务键，因此不能按日志展示时长直接删除。角色删除仍跟随角色生命周期级联清理。

新增玩法需定义事件契约、渲染分支，并在权威结算入口提供稳定业务键与实际结果。事件结构发生不兼容变化时使用新事件类型版本并保留旧记录解析；幂等键不随展示契约版本变化。

## 第一、第二批玩法

只展示发生 **道具、修为、灵石、感悟、声望、宗门贡献** 实际得失的结算。只有灵气、气血／法力或灵兽变化不展示。铭刻、客栈恢复、丹药使用、炼体／洗髓突破没有启用日志采集；也没有扩展到秘境、爬塔和拍卖结算。

| 玩法 | 已接入的结算 |
| --- | --- |
| 野外 | 权威战斗结束结算中的道具奖励；无道具得失不记 |
| 组队讨伐 | 首次胜利实际到账的灵石、修为、感悟；道具随邮件领取再记 |
| 历练 | 领取时实际到账的灵石、修为、感悟 |
| 邮件 | 单封／批量领取新旧附件；赠送时送出道具和消耗传音符 |
| 商店与回收 | 坊市、黑市、声望兑换、宗门兑换、批量道具回收 |
| 炼制与参悟 | 按方／即兴炼丹、炼器、功法参悟的道具和资源得失 |
| 灵田 | 领取初始灵种、播种、培育、收获 |
| 宗门 | 任务操作及任务战斗结算、俸禄、贡献兑换道具、灵石建设投入 |

邮件发出只表示待领取，不计作收件人的道具收入；实际领取再记。历练发往邮件的道具也按这个规则处理。灵兽不作为道具计算。声望兑换与宗门兑换同时记录道具收入和货币支出；仅声望或宗门贡献得失也独立成条。贡献指当前宗门的可用余额，累计贡献不重复计入。

新增事件契约为 `resources.settled`：`activity` 标识玩法、可选 `detail` 保存短上下文、`changes` 保存有符号的资源／道具数量。前端统一渲染资源颜色及数字，长行在手机上自然换行。

### 采集与幂等

- `JournalSettlement.ts` 仅对已登记的业务结算开启事务级采集。复用 `saveInventoryPlan` 已有的前后数量，旧邮件宝库附件和传音符消耗在各自真实写入点补充；不额外扫描角色全部背包或储藏室。
- 数值资源读取同一事务内结算前后的角色行及当前 active 宗门身份的贡献余额（无宗门按零处理），只保存实际差值；不使用配置中的名义奖励，避免上限裁剪后记多。同一道具多次同方向变更合并，消耗与产出保留各自方向。
- 普通请求必须有稳定业务键；炼丹、历练领取、一键领邮件补充 UUID `requestId`，客户端在 sessionStorage 保留尚未确认的请求。炼丹与历练在材料／领取时间校验前识别已结算请求，重试不会再炼制、扣费、发奖或生成结算故事。
- 原响应以存储专用 `result` 保存在同一行，不通过日志列表接口返回。旧的查询前置检查也能读取新日志凭据。
- 有幂等请求但没有这些资源变更时，仅保留不可见的执行凭据。列表查询先过滤再分页，因此不会出现空白页吞掉下一页记录。无掉落的异步野外结算不新增日志行。
- 野外结算在现有消息消费事务中记录，消费者凭据用于 Redis 终局资料过期后的重复投递识别；宗门任务战斗与战斗归档同事务。不新增独立流水表，不在异步发奖之前预记收入。

### 本轮验证

纯共享差量／契约测试覆盖已有堆叠增量、全部消耗、移动不记、同物消耗与产出、内部结果不外泄和闭关回放类型隔离。前后端通过 lint、TypeScript 与构建检查；运行验收结果见任务交付说明。

本地浏览器已验收新旧邮件附件、批量领信、道具回收、灵石培育、功法参悟失败和历练领取。邮件／批量领信／回收／培育／历练的重复请求均回放原结果，培育同键换参数返回 409。旧版对纯声望领取的隐藏规则已取消；旧记录不回填。即兴炼丹被现有药蕴不足规则拒绝，未扣费、未产生日志，成功炼丹链路尚未运行验收。野外及宗门战斗、其他商店和灵田完整周期本轮以接入点与事务代码检查为主，未逐个完成实际玩法。

特殊货币补充验收：纯声望邮件领取显示 `声望 +3`，宗门建设显示 `灵石 -10,000、宗门贡献 +1`，两者重复请求均回放且只保留一条记录。声望／贡献的正负数契约测试通过。宗门兑换因本地角色职阶不足未执行，支出路径完成事务代码检查。
