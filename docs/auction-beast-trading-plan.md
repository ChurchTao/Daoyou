# 灵兽本体接入拍卖行：实施计划

日期：2026-09-19。状态：已在本地实施，公开／好友专属成交及下架领取闭环已验证；未部署。验收结果及未覆盖项见第 8 节。

本计划基于当前工作区；四种青溪固定材料已移除，不纳入本轮。只扩展灵兽本体交易，不调整材料品质门槛、普通物品价格或灵兽生成与培养规则。

## 1. 已确认规则与建议默认值

用户已确认：

1. 所有合法灵兽均可交易，包括初始赠送灵兽。
2. 成交、主动下架、到期退回均通过邮件领取。
3. 灵兽仓满时保留未领取附件，腾出位置后再领取。
4. 成交领取后不自动携带或设为首发。

其余建议默认值如下，实施时按此收敛，不引入额外经济系统：

| 项目 | 首期方案 |
| --- | --- |
| 可售个体 | 当前灵兽协议可完整解析、属于卖家且版本匹配的普通／变异个体；不限制来源、成长、资质、技能数或等级 |
| 携带与首发 | 上架前须取消首发并移出携带编组；不在上架时静默调整玩家编组 |
| 战斗与结算 | 卖家存在灵兽管理所覆盖的战斗／结算占用时，禁止上架；领取灵兽同样检查，避免干扰捕获结算与容量计算 |
| 寿命 | 允许低寿命和寿命为零的合法个体，购买前明确展示；交易不补寿命 |
| 数量 | 每单一只，购买数量必须为 1，不支持打包或拆分 |
| 价格 | 1～9,999,999 灵石，沿用无旧品质资产上限，不合成凡品／玄品品质 |
| 货单规则 | 与普通物品共用每角色 5 单、48 小时、现有阶梯税和同账号角色禁购规则 |
| 交易对象 | 同时支持公开及好友专属；专属仍消耗一张随身拍卖行贵宾符 |
| 购买与使用 | 不按买家等级限制购买或领取；出战、加点等继续执行现有使用限制 |
| 仓位 | 寄售和邮件待领期间不计入可操作灵兽仓的 24 只上限；领取时校验实际余量，不增加溢出仓 |
| 初始领取 | 出售或转让不改变 `starterClaimedAt`；卖家不能因此重新领取初始伙伴，买家也不因此失去原有领取资格 |
| 培养事实 | 保留原 ID、名字、物种、变异、等级、经验、资质、成长、已分配／未分配点、技能、寿命与生成信息；仅变更归属并推进版本 |

邮件待领允许暂存超出仓位的灵兽，这是所选交付方式的明确结果；待领灵兽不能出战、培养、放生或再次上架。首期不新增交易冷却、绑定、鉴定、竞价、求购或直接赠送灵兽。

## 2. 实施前代码基础

- `cultivator_beasts` 的行 ID 和 `cultivatorId` 是身份与归属权威，JSON `individual` 不重复保存它们；通过 `beastIndividualData`／`beastFromRow` 转换。
- 灵兽仓最多 24 只，携带最多 6 只；个体与编组分别有 `revision`。`starterClaimedAt` 独立于个体生命周期。
- `CombatV6BeastService` 的变更使用角色 Redis 锁、数据库角色状态锁及战斗占用检查。捕获和战斗结算也会修改灵兽状态，交易必须保持这些协调边界。
- 现有拍卖快照只有 `inventory_v1`，展示和交付假定标的是背包物品。货单已具备原资产 UUID、JSONB 快照、类型、余量与条件状态转换。
- 邮件附件没有灵兽类型；单封领取与一键领取在 `PlayerMailApplicationService`。一键领取当前合并全部待领附件，必须适配灵兽容量不足的情况。
- 灵兽页面当前直接请求 `/api/combat-v6/beasts`，没有已注册的灵兽资源 topic，不能假设背包失效事件会刷新灵兽列表。

## 3. 资产与交付设计

### 3.1 复用货单托管，保留灵兽独立资产模型

采用现有物品寄售相同的托管方式：上架成功时，从可操作的 `cultivator_beasts` 中移除原行，将完整个体事实存入货单快照。不得同时保留一只仍能被普通灵兽查询读到的副本。

快照扩展为显式版本联合：保留原 `inventory_v1`，增加 `beast_v1`。灵兽分支保存原 ID、原 `createdAt` 和不带归属字段的完整个体事实；所有人由当前容器确定：有效货单的卖家、待领邮件的收件人、领取后灵兽行的 `cultivatorId`。

`beast_v1` 是交易快照版本，与个体的 `generationVersion` 分开。不可为了交易重新生成、洗炼或按当前内容包重掷个体。解析或引用不合法时拒绝操作，不能自动修补属性。

原货单表的 UUID、varchar 和 JSONB 能容纳这个分支，首期优先不新增托管表、不修改灵兽表归属为空的约束。实现时核对实际生成 SQL 和查询需求；若不增加列／索引，则不制造空迁移。只写业务 schema 的类型与注释变化也不应触及 Better Auth 迁移。

### 3.2 可转移权利只存在于一个位置

```text
卖家灵兽仓
  └─ 上架事务 → active 货单
       ├─ 成交事务 → sold + 买家未领取邮件
       ├─ 下架事务 → cancelled + 卖家未领取邮件
       └─ 到期事务 → expired + 卖家未领取邮件
                            └─ 领取事务 → 收件人灵兽仓 + 邮件已领取
```

结束货单和已领取邮件中的快照仅供历史展示，不能再次用于交付。每次领取都保留原灵兽 ID，以主键唯一性提供额外保护；不能遇到冲突就生成新 ID 或吞掉错误。

上架快照推进个体版本，领取再次推进，版本不归零。这样下架后原 ID 回到卖家时，上架前的改名／放生／培养旧请求也不能重新生效。保留原创建时间；返回仓内不恢复原编组。

## 4. 服务端流程

### 4.1 上架

建议新增 `POST /api/auction/list-beast`，保留现有普通物品上架请求不变。客户端只提交 `requestId`、`beastId`、`expectedRevision`、单价、公开／专属范围及目标好友，不提交个体快照、卖家身份或数量。

在同一个命令事务内：

1. 取得卖家角色变更锁及数据库角色状态锁，复用灵兽占用规则；只抽取必要的公共检查函数，不重构全部灵兽服务。
2. 校验货单额度、灵兽归属和版本、未携带／未首发、个体合法性、价格、好友权限。
3. 专属寄售通过既有服务扣贵宾符，并在同一事务内落账。
4. 使用归属与版本条件删除原灵兽行，必须恰好删除一行；创建数量固定为 1 的灵兽货单。任何失败全部回滚。
5. 复用持久幂等与提交后缓存清理，指纹包含资产引用、版本、价格和交易对象；重试不能重复扣符或移除资产。

上架成功刷新可售灵兽列表与我的寄售；专属寄售使背包资源失效。灵兽不是背包物品，不伪造 `inventory.bag` 事件表达灵兽变化。

### 4.2 购买

复用现有购买入口与货单锁，根据快照版本分支：灵兽单只允许数量 1。沿用指定买家、同账号、过期、余额与税费检查。

买家扣款、货单 `active → sold`、买家灵兽附件邮件、卖家税后灵石邮件必须同事务成功。成交时不写买家灵兽仓，因此不因满仓或买家正在战斗阻止购买；实际领取时再校验。

### 4.3 下架与到期

沿用条件状态转换和到期任务，在改变货单状态的同一事务内创建原个体附件邮件。不得直接插回卖家仓，以免满仓时无法下架或到期。

购买／下架／到期竞争最多一个成功转换，最多生成一个有权领取该灵兽的邮件。反复执行过期任务不得重复返还。贵宾符沿用现有规则，不退还。

### 4.4 邮件领取

增加仅供可信服务端交付的 `beast_v1` 附件分支，数量严格为 1。同步修改附件类型、运行时 Zod 校验和公共展示转换；普通玩家写信接口仍不接受灵兽附件。

单封领取在角色锁和同一个数据库事务内完成：重新验证未领取状态及收件人、灵兽占用、剩余仓位、附件合法性；插入原 ID 灵兽行，将归属设为收件人并推进版本；再条件标记邮件领取。任一步失败全部回滚，邮件继续未领取。

一键领取以整封邮件为单位按稳定顺序（创建时间、ID）规划：先计算可用灵兽位；容量不足或灵兽操作被战斗占用时，跳过对应整封邮件，继续领取其他符合条件的邮件。被跳过邮件的灵石／普通物品也不能部分领取，因为现有领取标识在邮件级。

返回实际领取 ID／数量、跳过数量及原因，让界面说明“部分灵兽待腾出仓位后领取”或“战斗结束后领取”。全部跳过时允许正常返回，不能误标已领取。只跳过可预期的容量／占用条件，数据损坏、主键冲突或未知异常仍使事务失败，不能静默丢附件。

同步检查 `attachmentsToResourceOperations`：灵兽走专用交付，不能折算为通用资源或因没有数值收益而漏领。领取和捕获结算共用角色协调，避免先检查容量再并发超限。

## 5. 展示与查询

- 拍卖新增“灵兽”分类；上架窗口在“物品／灵兽”之间切换，灵兽读取自己的真实名册，不塞入背包格位模型。
- `AuctionListingView` 改为可判别联合，普通物品保留原展示数据，灵兽提供专用公共预览。不能让所有展示分支继续调用 `itemDefinition`。
- 公共预览展示自定义名字与物种名、普通／变异、等级、成长、五项资质、技能、寿命及已分配／剩余点；保留这些信息供买家判断。生成种子、内部版本及非必要归属字段不对外透传。
- 列表只展示物种、变异、等级、技能数与价格等摘要；完整事实放详情，低／零寿命与无法立即出战的原因在购买确认时明确提示。
- 首期提供物种筛选并保留价格排序；建议将 `itemCategory` 用于物种 ID，先核对现有 50 字符列长与所有物种 ID。暂不新增成长、资质、技能组合等复杂查询或 JSONB 索引。
- 灵兽分类不显示旧品质筛选，切换分类时清理不适用的品质条件；服务端也校验该组合，避免保留 URL 参数造成空列表误导。
- 复用 `components/feature/beasts` 的肖像、变异标识与技能展示；从页面私有 `BeastPanel` 中仅提取需要跨拍卖／邮件使用的只读详情部分，不能直接跨路由引用整块带培养操作的页面组件。
- 邮件列表摘要和详情支持灵兽附件；领取结果显示去向为灵兽仓，不显示为背包／储藏室。
- 首期沿用灵兽页现有请求方式：上架选择器每次打开获取最新名册，上架后重新获取；灵兽页重新进入、窗口重新聚焦时重新获取并取消过时请求。每次变更仍由服务端版本校验。暂不为本功能迁移整个灵兽资源体系，普通背包、货币、邮件摘要继续走既有资源提交。

## 7. 必须覆盖的验收

### 共享纯规则测试

- 普通／变异、初始／捕获／洗炼后的合法个体均可交易；零寿命不被隐式修复。
- 非本人、旧版本、携带、首发及非法个体的准入判断；数量只能为 1；公开与专属参数不能混用。
- 快照序列化保留培养事实，公共视图不含生成种子；归属与版本变更规则明确。
- 批量领取容量规划：0／1／多个余位、混合邮件、稳定顺序、跳过整封、全部跳过。
- 普通物品原有快照、部分成交、品质限价及税费测试继续通过。

### 本地浏览器与运行验证

- 两账号完成公开、好友专属交易，第三账号不可见且不能购买专属货单；同账号角色禁购。
- 上架前取消携带；上架后无法改名、加点、洗炼、打书、喂养、放生或被战斗装配；初始赠兽售出后不能重复领取。
- 逐字段核对成交、下架、过期三条路径的原 ID 与培养事实，版本递增，归属正确，不自动恢复编组。
- 买家满 24 只仍能购买；领取失败保留附件；腾位后成功。一键领取跳过装不下的灵兽且其他邮件正常到账。
- 已有捕获待结算时拒绝领取灵兽；交易上架与培养、购买与下架／到期、重复领取等竞争不复制、不丢失、不超仓。
- 无效归属／版本、缺少贵宾符、余额不足、货单已结束等失败不留下半条交易；重试不重复扣款、扣符、发信。
- 桌面及窄屏检查选择、只读详情、购买确认、邮件领取、筛选切换及返回灵兽页后的刷新。

实施后运行 `bun run lint`、`bun run build`、聚焦纯规则测试；若协议影响多个共享模块，再运行完整 `bun run test`。不新增服务端、数据库或 React 单元测试，不新增一次性验收脚本。

## 8. 本轮产物与验证边界

### 已实现

- 增加 `beast_v1` 货单快照及邮件附件、只读公开预览、`POST /api/auction/list-beast`，复用原货单与邮件表，无数据库迁移。
- 上架在角色锁和事务内移除仓内原个体，成交／下架／过期沿用条件转换与回邮；收件人领取原 ID、原创建时间和全部培养事实，版本每次上架与领取各推进一次，不恢复编组。
- 单封领取满仓失败保留附件；一键领取按创建时间和 ID 规划整封领取，跳过容量不足或战斗占用的灵兽邮件。纯灵兽领取只更新邮件摘要，不伪造背包变化事件。
- 拍卖选择器支持物品／灵兽切换，灵兽按物种筛选并展示成长、资质、技能、寿命及培养点；所有灵兽购买均展示确认详情。邮件共用只读详情，灵兽页重新聚焦会刷新名册。
- 所有合法来源均可寄售，包含初始赠兽；普通玩家写信仍不能提交灵兽附件。未修改物种、生成、培养或普通物品准入规则。

### 本地已验证

使用独立 Chrome／应用内浏览器会话的 `local1`、`local2`，通过正式 API 与页面操作，数据库只读核对：

- 公开成交 100 灵石，卖家税后邮件 97；好友专属反向成交同价。缺贵宾符被拒绝，发放一张测试符后成功；重放上架只返回原结果，不重复扣符，数据库确认符已消耗。
- 上架请求重放、同请求 ID 不同价格冲突、同账号禁购、非本人及旧版本拒绝；购买请求重放不重复扣款；重复下架不重复发信。
- 买家满 24 只仍可购买，单封领取返回 409 并保留附件；一键领取跳过灵兽但领取另一封 1 灵石邮件；全部跳过返回正常结果。腾出仓位后成功领取。
- 成交领取版本为 2，下架再领为 4，好友专属成交再领为 6；逐字段核对原个体事实一致，仅归属与版本变化。原创建时间始终为 `2026-09-19T04:48:29.119Z`。均未自动携带或首发。
