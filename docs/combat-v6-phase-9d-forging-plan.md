## 1. 已确认范围

- 新增道装图纸，固定属性为槽位和等级；铸造产物对应图纸部位与等级。
- 将物品定义抽到独立代码目录分类管理，包括已有兽诀、道装、图纸与材料；统一库存继续负责角色持有、格位、数量和消费。

- 不接图纸掉落，通用掉落池及成品掉落另行设计；战斗药品和物品指令继续延期。
- 提供仅开发环境可用的无鉴权发放接口，为指定测试角色发放支持的物资和资源。环境判定不能仅依赖 NODE_ENV：现有预发布启动命令也使用 development。推荐仅显式 local 环境注册路由，其他环境及缺省环境不开放。

## 2. 已确认的材料增益算法

用户已确认采用“额外抽样取高，同类叠加触发概率”。每件合格材料增加 1.8 个百分点，同组最多 9%。

1. 按原规则执行正常抽样。
2. 根据投入材料对应类别的累计增益概率，判定是否额外抽样一次。
3. 触发时使用两次抽样的较高值；未触发时保留首次值。两次相同或第二次更低均不产生实际提升。

| 材料 | 作用对象 | 不受影响的部分 |
| --- | --- | --- |
| 矿石 ore | 白字数值的择优概率 | 数值上限、附加属性、器蕴、器诀 |
| 天材地宝 tcdb | 器蕴条数的择优概率 | 器蕴固定强度、器诀出现概率 |
| 辅助 aux、妖兽 monster | 附加属性数值的择优概率 | 附加属性条数、属性种类、器诀 |

天材地宝仅提高器蕴数量概率，仍遵守现有最多两条、不重复与合法性规则。器诀保持独立随机，不受材料影响。不为器蕴新增个体强度随机字段。

辅助与妖兽材料合并计入同一个附加属性增益组；每件合格材料贡献相同概率，高品质只满足门槛、不额外乘算。白字及已有附加属性的每条数值独立判定是否择优；没有附加属性时不会凭空生成词条。天材地宝对器蕴条数判定一次，再选择合法器蕴。元素、名称不影响概率。新生成算法发布新版本，旧装备事实及回放不重新计算。名称随机与属性随机分离，名称池变化不改变数值抽样。

基础分布沿用现有规则：白字合法区间内均匀抽取，附加属性 0／1／2 条为 50%／40%／10%，器蕴 0／1／2 条为 82%／16%／2%，器诀出现概率 8%。本阶段不同时引入白字分段权重。

## 3. 已确认实现边界

- 物品定义推荐放在 `src/shared/items/definitions`，按类别组织并统一注册；铸造规则与装备效果仍由独立共享领域负责，不放入库存操作服务。
- 图纸同槽位、同等级可堆叠，上限 99；可堆叠材料每格上限 99。1～5 件材料按实际消耗件数计算，允许同种材料多件及混合类型，必须恰好满足配方数量，不额外加料。
- 宝库取出在同一事务中扣减旧材料并写入新库存，失败整体回滚。保留材料有效事实，按结构校验转换，不重新随机，不将旧自由 details 作为规则执行。
- 铸造在同一事务中完成资源、图纸、材料扣除及成品入包；校验消耗完成后的背包容量。服务端检查归属、数量及版本，复用角色锁，不新增通用任意数据写入接口。
- 新炼器业务独立于旧 AI 炼器；交互使用备料、铸造、结果三个步骤，复用基础 UI 与统一 tooltip。
- 暂不开发市场、交易、重铸、锁灵、灵纹操作、材料整体迁移和旧装备转换。不增加装备品质、评分、耐久、负属性或鉴定系统。

- 宝库首版仅开放四类铸造材料取出；单向转换进入新库存，之后存入储藏室不转换回旧材料表。
- 成品自动入包，结果页只展示，不增加领取事务，不自动装备。处于战斗、结算或擂台占用中时禁止铸造。
- Dev 发放仅支持指定已有角色的图纸、兽诀、新库存材料、道装、旧宝库材料、灵石及天地灵气；不支持任意数据库字段写入、账号创建或整库重置。调用正式资源校验服务，不绕过容量规则。

## 4. 已确认成本、成功与等级规则

图纸等级不得高于人物等级，即使成品可能带降低御使要求的器蕴，也不豁免铸造等级校验。用户确认中的“任务等级”按上下文理解为“人物等级”。

满足全部条件必定产出一件，消耗一张图纸，固定已鉴定。不增加失败率、火候、熟练度、等待队列或批量铸造。

设图纸等级为 L（10～180，10 的倍数），t = L / 10：

- 灵石：100 × t²。
- 天地灵气：5 + 2 × t。
- 材料数量：ceil(t / 4)。
- 最低品质：按下表要求，允许更高品质替代，无额外概率加成。

| 图纸等级 | 材料件数 | 最低品质 |
| -------- | -------: | -------- |
| 10～40   |        1 | 凡品     |
| 50～80   |        2 | 灵品     |
| 90～120  |        3 | 玄品     |
| 130～160 |        4 | 真品     |
| 170～180 |        5 | 地品     |

例如 60 级消耗 3600 灵石、17 灵气、2 件灵品或以上材料；180 级消耗 32400 灵石、41 灵气、5 件地品或以上材料。现有灵气常规上限 200、每小时自然恢复 10；本表为已确认的首版配置，尚未经过长期经济平衡验收。

## 5. 本阶段验收目标

本地发放图纸与材料 → 宝库材料取出 → 统一库存备料 → 铸造消费与生成 → 装配 → 下一场白字、器蕴或器诀生效 → 旧回放不变。

共享纯测试覆盖成本、白名单、材料增益、固定种子生成、上限及旧生成版本稳定性；API、数据库和页面使用本地真实交互验收，不新增其单元测试或一次性测试脚本。开发发放接口需验证 local 可用、预发布和生产不可用。9C 其余验收暂缓且继续保留记录，不视为通过。

## 6. 实现与发布

- `src/shared/items/definitions` 按兽诀、道装、图纸、材料分类；108 种图纸覆盖六个槽位与 10～180 级。材料使用校验后的名称、类型、品质、元素、描述作为堆叠事实。
- `src/shared/forging` 管理成本与名称池；装备生成器 v3 独立材料增益随机流，基础 v2 随机流与器诀分布不变。v3 按对应槽位和等级的名称池校验，旧版本仍按旧模板名校验。历史名称池需保留，调整已有名称规则时发布新生成版本。
- 复用现有库存表及装备装配表，无数据库迁移、无新增消费凭据表。角色 Redis 锁、角色行锁、同一事务串联校验、资源消费与成品入包；容量按消费后的格位判断。
- `/game/craft/refine` 硬切新炼器室；旧 `refine` 估价、生成与确认入口返回 410，放弃旧任务入口保留用于释放既有占用。
- `GET /api/combat-v6/forging` 读取背包及资源；`POST` 提交图纸和材料的 ID、revision、消耗数量。`GET /vault` 分页搜索旧宝库；`POST /vault/withdraw` 提交 ID、数量及 expectedQuantity。所有正式入口校验登录和角色归属。
- 变更响应使用 `{ success, data, state }`，页面通过现有资源 store 消费变更，刷新 HUD 及旧宝库资源。失败后清空铸造备料并重读，不自动重试消费请求。
- Dev 接口用法见 [测试规范](./testing.md)。`dev:api` 显式使用 `APP_ENV=local`，`prd:api` 使用 `APP_ENV=staging`；生产即使误设 local 也不开放 Dev 路由。发布前后端需同步，旧页面刷新后使用新版入口。
