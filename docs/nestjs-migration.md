# NestJS 后端迁移


> 2026-10-03 架构整理补记：已补齐 AppConfigService、Nest SQL/资源读取的 Drizzle 注入、领域实现归位、shared 包边界、显式 apiFetch 和 PR 质量检查。此前材料堆叠与九劫内容哈希的两项测试失败已按既有规则提交核对并修正断言，完整 237 文件/2403 测试通过。下文历史阶段结果保持原样；特殊数据、自然续期和生产灰度/回滚验收不因本次构建验证而视为完成。现行结构见 [架构审查与规范](monorepo-architecture.md)。

## 目标与边界

最终由 NestJS 承载全部 HTTP、SSE、原生 WebSocket、调度与消息生命周期，移除 Hono 运行依赖和构建插件。保留 React、共享战斗规则、Zod 契约、Better Auth 会话、Drizzle、Redis CAS、NATS JetStream 及资源／奖励提交语义。

采用按功能划分的模块、构造器注入、单例无请求状态的服务、显式导出与导入。共享引擎与仓储不依赖 Nest。遵循项目测试规范，不引入服务器、数据库或第三方服务 mock 单元测试。

## 可行性与方案取舍

可行。主要迁移对象是传输层和进程生命周期：原有应用服务、共享战斗引擎、Drizzle仓储与资源提交机制已有独立边界，可以继续复用。Nest的收益在功能模块、依赖注入、统一鉴权与生命周期管理；没有基准数据支持吞吐或延迟会因此改善，也不需要同时拆微服务、替换ORM或重做数据库模型。

- HTTP采用Nest＋Express；Controller负责契约、身份和响应，功能Service编排已有应用服务。保留Zod，避免同时维护class-validator DTO及前后端共享Schema。
- Better Auth继续拥有认证原始请求；业务Guard、Pipe、Filter分别处理授权、输入和异常。API方法、路径、JSON结构、Cookie及错误顺序都属于兼容范围，不能只按Controller数量验收。
- POST SSE保留现有事件格式、AbortSignal和业务幂等；原生WebSocket保留既有协议，不改Socket.IO。重点验证掉线、重连、权限撤销、终局及结算，不重写战斗核心。
- Nest生命周期统一拥有调度和消息设施。迁移双入口并存阶段要避免重复启动Cron或消费者；上线仍按已有锁、消息去重、outbox与事务规则运行，不另加一条奖励发放路径。
- 工具链使用pnpm workspace与Turborepo，运行Nest编译产物采用Node 24。开发watch、镜像生产依赖、健康检查和停机信号一起验证。
- 实施顺序为基础设施适配→按功能迁入HTTP→SSE／WS／调度→协议及真实玩法验收→默认入口与构建切换→生产灰度和回滚演练。当前代码已完成入口切换，生产发布仍应以剩余验收收口为前置条件。数据库结构未随框架迁移改变，回滚以固定旧镜像及其匹配的Compose健康检查配置为基础。
