# combat-v6 构筑内容配置化与代码治理规划

> 建立日期：2026-09-11。
> 状态：G1（含基础生成概率）已获确认并完成代码实施、自动检查；本地实际打造与装卸闭环待补验。G2～G6、A1 仍按轮讨论。
> 上位路线：[combat-v6 改造路线图](./combat-v6-mhxy-redesign-roadmap.md)。
> 发布收尾：[V6 打磨收尾规划](./combat-v6-polish-and-closure-plan.md)。本规划不替代发布验收门槛。

## 1. 目标与边界

让策划能够通过领域数据包维护常规内容和数值，代码承担加载、校验、编译及运行机制；同时减少内容、生成、校验、装配混在一起的文件。

本次治理默认保留玩法、数值、成本、产出概率和确定性结算。玩法调整另行提出，不混入等价重构。已完成的[境界功法数据包](./combat-v6-manual-system-design.md)作为轻量参考，不照搬为所有领域的统一大框架。

配置负责：内容身份、描述、属性参数、效果引用、成长曲线、解锁要求、抽取权重、资源成本。

代码负责：效果原语、执行顺序、随机算法、取整语义、状态变化、人物装配、事务、授权和回放恢复。复杂效果可通过已支持的声明式操作描述，新增机制仍需要扩展代码，不引入任意 JavaScript 脚本。

`src/shared/engine/sect` 仍承担宗门组织与外围玩法，不视为整套废弃实现。治理宗门时，需要核定其与 combat-v6 对名称、ID、心法与解锁信息的权威归属。

## 3. 推荐推进顺序

### 第零步：随第一轮完成小范围依赖审计

- 找到当前真实生成、校验、展示、战斗装配入口。
- 列出该领域哪些旧版本入口仍有消费者，哪些只剩导出或测试。
- 记录当前固定输入／种子的输出基线。
- 此步只收集事实，不以全局装配重写作为配置化的前置条件。

### 第一轮 G1：道装基础、阵纹与基础生成参数

先建立简单属性领域的完整数据入口，具体提案见第 5 节。

### 第二轮 G2：器蕴、器诀与打造

沿用装备领域数据包边界，补齐特殊效果、产出与经济配置。生成概率和材料增益需要检查 `generator.ts` 与 `forging.ts` 的共同使用，避免只改一个入口。涉及技能与状态的配置验证能力供之后兽诀和宗门参考。

### 第三轮 G3：召唤兽与兽诀

先分离物种／技能数据、个体生成、养成规则、个体校验和战斗投影，再迁移数据。明确野外物种与可捕捉物种的身份引用关系，允许两者使用不同战斗参数。兽诀物品注册不再另行手写一份技能 ID 清单。

### 第四轮 G4：宗门，分三批

1. 心法、技能解锁关系、心法修炼和经脉解锁成本。
2. 技能、状态、战斗资源；先完成一个宗门的配置样板。
3. 流派、经脉、技能修改项及五行反应等特殊内容，再逐宗门完成迁移。

同一宗门内跨批引用保持明确，不同时修改五个宗门的大量机制。已有 `SkillPatchV6` 等声明式操作优先复用；执行器和语义校验仍留在代码。

### 第五轮 G5：炼体与修炼

统一五轨、位阶门槛和收益参数。核对炼体成长读写、前端预览与 v6 投影，不能只迁移标签和名称。

### 第六轮 G6：局内祝福、敌人与遭遇

先整理临时祝福 build，再处理配套遭遇内容。敌人模板、战斗编组和掉落池是不同数据职责，通过 ID 引用，不嵌入人物永久成长包，也不把 Host 编排写成配置。

### 独立任务 A1：人物装配与历史入口收敛

完成依赖审计后独立安排，建议在宗门大规模迁移前完成。目标为一个当前人物装配入口和一个当前宗门目录，各领域贡献通过各自编译器进入装配。保留或删除历史入口以实际消费者和回放恢复依赖为依据，不凭名称或版本号判断。

## 4. 各轮共用约定

- 数据包按领域放置，采用 JSON 与编辑器 JSON Schema；不建立一个覆盖全游戏的总配置文件。
- 结构校验与语义校验分开：结构负责类型和范围，语义负责唯一 ID、引用存在、属性兼容、成长表完整及概率有效。
- 错误至少包含文件、内容 ID 和字段路径；失败即停止加载，不静默跳过或回退到另一套默认内容。
- 策划输入经校验后转换为运行时类型。业务代码不直接遍历未经校验的 JSON。
- 每个领域明确一个内容权威来源，派生物品、展示与产出引用要么自动生成，要么明确引用并校验。
- 格式版本与内容修订分别表达；生成算法版本、持久化格式和回放版本不与它们混为一谈。具体落点逐领域确定，不先搭建版本平台。
- 第一阶段通过重新构建／启动发布配置，不做热更新、后台编辑器、可执行脚本或通用效果 DSL。
- 默认不改变既有 ID、排列、取整和随机调用顺序；相同种子生成一致是首轮硬验收项。
- 内容参数调整对已生成装备及旧战斗快照的影响必须明确。存量校验不能无意间用新生成范围否定合法旧实例；真实需要版本分支时另定最小方案，不默认做数据补偿或大规模兼容。

## 5. 第一轮实施范围（已确认）

### 5.1 做什么

搬迁现有内容并保持结果一致：

| 内容 | 当前事实 | 首轮目标 |
| --- | --- | --- |
| 装备模板 | 六部位、名称、基础属性 min/max 系数、偏好属性 | 策划在模板配置中编辑 |
| 阵纹 | 九种阵纹、属性、每级加成、允许部位 | 策划在阵纹配置中编辑 |
| 基础附加属性 | 0／1／2 条概率为 50%／40%／10%；偏好权重 2、普通权重 1 | 移入基础生成规则，算法与抽取顺序保持一致 |
| 附加属性数值 | 下界为等级 ×0.08、上界为等级 ×0.14，取整并至少为 1 | 系数配置化，取整语义保留在生成器 |

阵纹的实际产品入口以审计为准。已有内容可以配置化，但首轮不新增阵纹镶嵌、升级或获取玩法。

### 5.2 建议的文件职责

在现有 `equipment/` 下增加：

```text
data/
  equipment-base.json       # 模板、阵纹、基础生成参数
  equipment-base.schema.json
pack.ts                    # 加载与严格校验
```

单包对当前六模板和九阵纹足够。先按内容区块组织，规模增长再拆文件，不为未来内容预设复杂包管理器。

- `content.ts`：从已验证数据生成现有运行时定义和查找入口，不再手写数值列表。
- `generator.ts`：读取基础生成参数，保留确定性抽样、去重和取整。
- `compiler.ts`：保留实例合法性及装配校验，核对其白名单／范围与数据来源是否重复。
- `forging.ts`：核对基础属性重抽逻辑是否读同一配置；本轮只同步基础参数来源，材料加成和特殊效果参数留第二轮。
- `types.ts`：保留稳定领域类型，不把整个底层战斗类型直接暴露给策划。

### 5.3 本轮不扩大的范围

不调整装备强度、数量概率、材料成本或掉落，不添加新模板和新阵纹；不改器蕴、器诀内容，不重构人物装配入口，不修改持久化模型，不创建在线编辑页面。未来新增部位、属性种类或效果原语仍属于代码扩展。

### 5.4 执行步骤与验收

1. 查明基础生成、打造重抽、编译校验、物品和前端引用 → 形成调用清单，并在改代码前保存代表性确定性输出。
2. 新增 JSON、Schema 与加载校验 → 非法 ID、重复属性、上下界颠倒、非法部位、概率无效等均有明确诊断。
3. 接通旧入口与生成器 → 无双份数值来源；保持既有 ID、数组顺序、随机次数与取整。
4. 验证行为等价 → 比较六部位、代表性等级及基础／打造生成路径的固定种子输出，检查阵纹装配效果与白名单。
5. 运行质量检查 → 聚焦共享纯逻辑测试，按影响范围运行全量测试、lint、两端类型检查／构建；本地检查装备详情、打造和装配面板。不得新增数据库／API 单元测试或一次性测试脚本。
6. 更新配置说明和本轮记录 → 明确已验证、未验证及存量数据影响，不把静态通过记作真实玩法通过。

首轮成功标准：策划调整已有模板数值、阵纹属性加成与基础附加属性概率时只修改 JSON；沿用旧参数时，生成与战斗收益保持一致。
