# 机器人交易与挑战方案评估

## 1. 结论

可以为当前游戏引入机器人购买、出售商品，以及参与挑战。

推荐采用“规则机器人”，而不是让每个机器人定期调用大模型自主决策。购买条件、出售价格、库存、预算、挑战对象和战斗结果都由服务端规则控制。

采用该方案后：

- 机器人购买、出售商品：新增 LLM Token 消耗为 0。
- 排行榜挑战和赌斗模拟：新增 LLM Token 消耗为 0。
- 可以继续复用现有事务、分布式锁、幂等和战斗模拟能力。
- Qwen 只作为可选的文案生成器，不参与资产和胜负判定。

## 2. 当前系统能力

### 2.1 普通市场

当前普通市场属于系统商店，不是玩家自由交易市场。市场定时刷新时主要从物品库、材料库和预设池中抽取商品，本身不需要调用 LLM。

普通市场已经可以在玩家数量较少时稳定提供商品，因此没有必要伪造机器人在普通市场中买卖。机器人交易应主要用于拍卖行，为玩家提供流动性。

### 2.2 拍卖行

拍卖行已经具备：

- 玩家库存扣除和商品上架。
- 购买者灵石扣除。
- 卖家收益和税费结算。
- 上架价格及品质限制。
- Redis 锁、数据库事务和幂等保护。
- 私有商品、过期商品和禁止购买自己商品等校验。

机器人可以直接复用 `AuctionApplicationService`，不需要模拟网页操作，也不应该绕过现有服务层直接修改数据库。

需要解决的一点是：拍卖商品的 `sellerId` 必须关联真实修士。建议为机器人创建正常的系统用户和修士记录，并增加 `isBot` 或机器人配置表进行区分。

### 2.3 排行榜挑战

排行榜挑战已经使用 V5 确定性战斗模拟。只要将机器人修士加入排行榜，玩家就可以正常挑战机器人，不需要额外定时任务，也不调用 LLM。

不建议机器人在玩家离线时主动挑战并降低玩家排名。这种行为容易让玩家感到处罚不可控。机器人更适合作为稳定存在的被挑战目标。

### 2.4 赌斗挑战

赌斗系统已经具备：

- 灵石或物品押注。
- 境界匹配。
- 待挑战、取消和过期处理。
- V5 战斗模拟。
- 胜者奖励邮件和战斗记录。
- 事务、锁和幂等处理。

机器人可以定期创建低风险赌斗，或按规则接受玩家创建的赌斗。该过程不需要调用 LLM。

### 2.5 实时竞技场

实时竞技场涉及房间状态、准备状态、WebSocket 和实时战斗控制器。虽然战斗本身不需要 LLM，但机器人需要实现一套实时操作协议，开发和维护成本明显更高。

不建议将实时竞技场机器人放入首期范围。

## 3. 推荐架构

### 3.1 机器人身份

首期可以创建 10～20 个机器人账号，覆盖主要境界和战斗流派。

每个机器人包含：

- 系统用户记录。
- 修士记录。
- `isBot` 标记。
- 独立库存和灵石余额。
- 每日购买预算和出售额度。
- 可参与的业务类型。
- 启用、停用开关。

所有机器人行为必须记录真实的机器人身份，不能与普通玩家混用，也不能使用不存在的卖家 ID。

### 3.2 后台调度

建议新增机器人后台命令，并复用当前内部 Cron 和后台消息处理机制。

推荐执行频率：

- 拍卖扫描：每 10～15 分钟一次。
- 赌斗扫描：每 2～5 分钟一次。
- 每日预算和库存补充：每天一次。

一次调度可以批量处理所有机器人，避免每个机器人分别启动任务。

### 3.3 购买规则

机器人只购买公开的玩家商品，并满足以下条件：

1. 卖家不是机器人。
2. 商品价格低于系统参考价或近期成交中位数的一定比例。
3. 机器人本日预算充足。
4. 没有超过单种物品持有上限。
5. 同一玩家没有处于购买冷却期。
6. 本轮和本日的全局灵石投放量没有超过上限。

机器人购买玩家商品会向玩家经济注入灵石，因此必须监控每日净注入量。

### 3.4 出售规则

机器人出售商品时应满足：

1. 商品来自机器人真实库存。
2. 机器人不能无限生成高级物品。
3. 价格由服务端参考价或近期成交价格计算。
4. 只允许有限幅度的随机波动。
5. 设置每种品质和每种物品的每日投放上限。
6. 禁止机器人购买其他机器人出售的商品。

机器人出售商品会回收玩家灵石，可以与机器人购买带来的灵石注入形成平衡。

建议每日统计：

```text
净灵石变化 = 机器人购买支出 - 机器人出售收入 - 拍卖税费
```

初期目标应接近收支平衡，避免机器人变成无限灵石来源。

### 3.5 挑战规则

排行榜机器人：

- 按境界和目标排名配置固定强度。
- 装备、功法和属性必须符合正常玩家规则。
- 主要作为玩家主动挑战的对象。

赌斗机器人：

- 每个机器人同时最多保留一个待挑战赌斗。
- 只接受相近境界的对手。
- 对单个玩家设置挑战冷却。
- 押注金额设置固定上限。
- 根据近期胜率调整机器人强度或停止接单。
- 不允许利用机器人向指定玩家转移资产。

## 4. LLM Token 消耗评估

### 4.1 推荐的规则机器人

| 操作 | 单次 Token | 说明 |
|---|---:|---|
| 扫描拍卖商品 | 0 | 数据库查询和服务端规则 |
| 决定是否购买 | 0 | 参考价、预算和阈值判断 |
| 商品上架 | 0 | 复用拍卖服务 |
| 排行榜战斗 | 0 | V5 确定性模拟 |
| 赌斗战斗 | 0 | V5 确定性模拟 |
| 模板式名字和台词 | 0 | 从预设池抽取 |

因此，无论有 10 个还是 100 个机器人，只要采用规则决策，机器人运行本身都不会产生 LLM Token。

### 4.2 可选的一次性人物生成

当前运行日志中，一次人物生成实际消耗约 1,272 Token。可以按 1,200～1,500 Token/机器人估算。

| 机器人数量 | 一次性预计 Token |
|---:|---:|
| 10 | 1.2万～1.5万 |
| 20 | 2.4万～3万 |
| 50 | 6万～7.5万 |

这部分不是必须的。机器人名称、简介和性格也可以使用预设模板，保持 0 Token。

### 4.3 不推荐的全 LLM 机器人

如果每个机器人每轮都把市场信息发送给 Qwen，并要求模型决定购买、出售和挑战，按每次决策 900～1,700 Token 估算：

| 机器人数量 | 调度频率 | 每日调用次数 | 每日预计 Token |
|---:|---:|---:|---:|
| 20 | 每 15 分钟 | 1,920 | 173万～326万 |
| 50 | 每 15 分钟 | 4,800 | 432万～816万 |
| 20 | 每 5 分钟 | 5,760 | 518万～979万 |
| 50 | 每 5 分钟 | 14,400 | 1,296万～2,448万 |

上述估算假设每轮只调用一次模型。如果购买、出售和挑战分别调用，消耗还会继续增加。

这种方案还会引入：

- 价格和行为不稳定。
- 模型超时导致后台任务堆积。
- 提示词注入和异常输出风险。
- 难以复现经济问题。
- 无法严格限制资产投放。

因此不建议采用。

### 4.4 当前市场已有消耗

普通市场刷新本身不调用 LLM。

当前每日材料库默认生成 20 个材料，会进行一次批量材料文案生成。粗略估计约 1,500～3,000 Token/天，实际值取决于生成文本长度。这属于现有系统基线，不是机器人引入后的新增消耗。

## 5. 风险和保护措施

上线前至少需要以下保护：

- 全局机器人开关和单机器人开关。
- 每日灵石净注入上限。
- 每日物品投放上限。
- 禁止机器人互相交易和刷战绩。
- 对玩家设置购买、挑战冷却。
- 所有机器人交易写入审计记录。
- 监控成交价格、成交量、机器人胜率和净灵石变化。
- 后台任务使用幂等键，避免重复执行。
- LLM 不得直接决定价格、奖励、库存、胜负和资产转移。

## 6. 建议实施顺序

### 第一阶段：排行榜机器人

- 创建机器人用户和修士。
- 将机器人加入各境界排行榜。
- 玩家可以正常挑战。
- 不需要后台调度。

预计工作量：0.5～1 人日。

### 第二阶段：拍卖行机器人

- 增加机器人配置和审计记录。
- 实现批量购买、出售规则。
- 增加预算、库存、价格和经济总量限制。
- 增加管理开关及基础监控。

预计工作量：2～4 人日。

### 第三阶段：赌斗机器人

- 定时创建或接受赌斗。
- 增加押注上限、胜率和冷却保护。
- 防止定向资产转移。

预计工作量：1～2 人日。

完整 MVP 预计约 4～7 人日，稳定运行时新增 LLM Token 可以保持为 0。

## 7. 最终建议

首期采用以下组合：

1. 每个主要境界配置少量排行榜机器人。
2. 5～10 个拍卖机器人共享一次批量调度。
3. 少量机器人创建和接受低额赌斗。
4. 所有决策由确定性规则完成。
5. Qwen 只用于可选的一次性人物文案，或完全不使用。

这套方案能够缓解玩家较少时的拍卖流动性和挑战对象不足，同时把经济风险、运行成本和 Token 消耗控制在较低水平。
