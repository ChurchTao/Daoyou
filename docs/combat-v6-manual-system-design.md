# combat-v6 功法系统设计

> 状态：Phase 5A 纯逻辑纵切已实现（Canonical）
> 建立日期：2026-09-02  
> 上位设计：[`combat-v6 梦幻式战斗体系设计稿与迁移路线图`](./combat-v6-mhxy-redesign-roadmap.md)  
> 适用范围：combat-v6 人物跨宗门被动、功法玉简、参悟与战斗投影

本文定义 combat-v6 的全新功法系统。它在玩法上采用“角色版魔兽要诀”结构：玩家消耗功法玉简，将跨宗门被动铭刻到有限槽位中；槽满后需要主动改修并替换已有功法。

本系统从内容定义、角色状态、学习规则到战斗投影均为 combat-v6 独立领域。首版不使用 AI，不读取或转换其他功法系统的数据与运行时产物。

Phase 5A 的首批十谱系、数值和精确结算语义见 [`combat-v6 Phase 5A 功法内容与数值基线`](./combat-v6-manual-phase-5a-balance.md)。

---

## 1. 已确认的首版约束

1. 功法只提供跨宗门被动，不提供主动技能。
2. 玩家在炼气境初始拥有 2 个功法槽位。
3. 每提升一个大境界增加 1 个槽位。
4. 槽位最多 6 个，达到化神后不再增加。
5. 境界小阶段不会增加槽位。
6. 首版每个角色只有一套功法构筑，不能保存或切换方案。
7. 首版不提供固印、锁定或锁槽功能。
8. 槽满时由玩家明确选择要被替换的功法，不随机覆盖。
9. 功法玉简参悟必定成功，不设置失败概率。
10. 首版功法的规则、名称、描述、数值和掉落表均无 AI 参与。
11. 功法没有随机属性；同一功法 ID 的玉简效果完全一致。
12. 功法不提供人物等级、技能等级和四项修炼等级。
13. 功法不能按宗门 ID、宗门技能 ID 或经脉节点 ID 编写特判。
14. 首版只实现一套构筑，但领域边界必须允许未来平滑增加多构筑方案。

## 2. 定位与系统边界

功法是角色长期学习的跨宗门被动 build。它的主要价值是改变战斗行为，而不是继续叠加一套垂直属性成长。

功法负责：

- 追击、反击、反震、回生等触发型被动。
- 会心、法术会心、封禁反制等战斗倾向。
- 气血、法力和治疗相关的条件式续航。
- 感知、隐匿识破等通用能力。
- 通过有限槽位形成攻、防、续航和反制取舍。

功法不负责：

- 宗门主动技能和默认攻击。
- 宗门心法等级与技能等级。
- 经脉对宗门技能的 patch、grant 或 revoke。
- 攻法、防御、法术、抗法四项修炼。
- 道装白字、附灵、器蕴或器诀。
- 可主动下达的战斗指令。
- 任意脚本或运行时生成效果。

系统职责：

| 系统 | 主要职责 |
| --- | --- |
| 修炼 | 四修炼与生命根基的永久数值成长 |
| 道装 | 可装卸面板、器蕴与器诀 |
| 功法 | 铭刻于角色的跨宗门通用被动 |
| 宗门心法 | 宗门技能等级、解锁与少量宗门面板 |
| 经脉 | 宗门技能和宗门流派改造 |
| 法宝 | 未来独立的特殊战斗器物 |

## 3. 世界观术语

| 机制 | 游戏内名称 | 说明 |
| --- | --- | --- |
| Manual system | 功法 | 跨宗门被动系统 |
| Manual item | 功法玉简 | 未参悟时可持有、掉落和交易的物品 |
| Passive slot | 道印位 | 角色承载功法的有限槽位 |
| Learned manual | 道印 | 已铭刻于角色的功法 |
| Learn | 参悟 | 消耗玉简并写入道印位 |
| Replace | 改修 | 用新功法替换已有功法 |
| Forget | 散功 | 主动移除功法并腾出槽位 |
| Base version | 本篇 | 功法谱系的基础版本 |
| Advanced version | 真解 | 同一谱系的强化版本 |
| Duplicate fragments | 悟法残页 | 重复玉简的回收产物 |

世界观解释：外来功法需要被炼成道印铭刻于道基。角色境界越高，道基越稳固，能够同时承载的道印越多；达到六印后，后续境界提升不再扩张数量，而是通过宗门、经脉、修炼和其他系统继续成长。

## 4. 槽位规则

当前大境界顺序为：

```text
炼气 → 筑基 → 金丹 → 元婴 → 化神 → 炼虚 → 合体 → 大乘 → 渡劫
```

首版槽位表：

| 大境界 | 可用道印位 |
| --- | ---: |
| 炼气 | 2 |
| 筑基 | 3 |
| 金丹 | 4 |
| 元婴 | 5 |
| 化神 | 6 |
| 炼虚 | 6 |
| 合体 | 6 |
| 大乘 | 6 |
| 渡劫 | 6 |

建议唯一公式：

```ts
function getManualSlotCount(realm: RealmType): number {
  return Math.min(6, 2 + REALM_ORDER[realm]);
}
```

规则要求：

- 槽位数量由当前大境界派生，不作为独立权威值持久化。
- 初期、中期、后期、圆满等小阶段不影响槽位。
- 突破到新大境界后，新槽位自动可用，不需要额外购买或激活。
- 达到化神后的所有大境界均固定为 6 槽。
- 未来增加更高大境界时仍受 6 槽上限约束，除非先修改本设计并发布新规则版本。

## 5. 首版单构筑与未来多构筑

### 5.1 首版行为

首版每个角色只有一套功法构筑：

- 没有方案列表。
- 没有方案命名。
- 没有方案复制。
- 没有切换按钮或切换接口。
- 战斗投影始终读取唯一构筑。

### 5.2 首版数据边界

建议把“构筑”定义为独立值对象，但首版状态只持有一个：

```ts
interface ManualBuildV1 {
  slots: Array<{
    slot: number;
    manualId: string;
  }>;
}

interface CultivatorManualStateV1 {
  version: 1;
  revision: number;
  build: ManualBuildV1;
}
```

`slots` 只保存已占用槽位。合法槽位为 1～6，是否已解锁由角色大境界实时校验。

首版刻意不保存：

```text
activeBuildId
savedBuilds
buildName
locked
switchCooldown
```

### 5.3 保留未来多构筑的技术可行性

所有参悟、改修、散功、校验和投影逻辑应以 `ManualBuildV1` 为输入，不直接把算法写死在角色持久状态上。

未来可以演进为：

```ts
interface CultivatorManualStateV2 {
  version: 2;
  revision: number;
  activeBuildId: string;
  builds: Array<{
    id: string;
    name: string;
    build: ManualBuildV1;
  }>;
}
```

这样未来增加保存和切换方案时，只需：

1. 把 V1 的唯一 `build` 迁移为 V2 默认方案。
2. 让投影器读取 `activeBuildId` 对应的 `ManualBuildV1`。
3. 复用现有构筑校验和编译逻辑。

首版不提前实现 V2 字段、接口和 UI。这里保留的是聚合边界与迁移路线，不是预埋未使用功能。

未来若开放切换，至少应限制为战斗外操作，并通过 revision 保证原子切换；不能在已创建的战斗快照中途更换。

## 6. 功法玉简与参悟

功法玉简是确定性物品：同一个 `manualId` 对应唯一功法定义，不生成随机数值、随机词条或临时脚本。

### 6.1 有空槽位

```text
选择玉简
→ 预览效果和冲突
→ 选择可用空槽
→ 服务端校验
→ 消耗玉简
→ 写入道印
```

### 6.2 槽位已满

```text
选择玉简
→ 选择要被替换的现有道印
→ 展示失去/获得的完整差异
→ 二次确认
→ 在同一事务中消耗玉简并完成改修
```

替换目标由玩家明确选择，不做随机打掉。

### 6.3 参悟约束

- 参悟必定成功。
- 不能学习完全相同的功法 ID。
- 同一谱系不能同时保留本篇和真解。
- 已有真解时不能学习同谱系本篇。
- 学习真解时，若已有同谱系本篇，优先原位升级，不额外占槽。
- 存在显式机制冲突时，必须先选择被替换的冲突功法。
- 未解锁槽位不能写入。
- 战斗、匹配或已锁定战斗快照期间不能参悟或改修。
- 玉简只有在所有校验通过后才被消耗。

---

## 7. 不设计固印

首版没有功法锁定状态：

- 道印位不含 `locked` 字段。
- 没有固印材料、固印数量或解锁成本。
- 改修依赖明确选择和二次确认防止误操作。
- 服务端请求必须携带预期 `revision` 和被替换的 `manualId`，防止并发或过期页面误覆盖。

示例：

```ts
interface ReplaceManualCommandV1 {
  expectedRevision: number;
  slot: number;
  expectedManualId: string;
  newManualItemId: string;
}
```

如果槽位内容已经变化，操作整体失败并返回最新状态，不能继续覆盖。

---

## 8. 散功

玩家可以主动移除一个已学功法：

- 散功后槽位变为空位。
- 不返还原功法玉简。
- 可以返还少量悟法残页，具体数量属于经济配置。
- 散功不影响宗门、经脉、修炼和道装状态。
- 战斗、匹配或已锁定快照期间不能散功。
- 散功也使用 revision 进行并发保护。

首版没有“恢复最近遗忘功法”功能。

---

## 9. 本篇与真解

每个功法谱系首版最多两个版本：

```text
追击诀 → 追击真解
回生诀 → 回生真解
反震诀 → 反震真解
```

```ts
type ManualRankV1 = 'base' | 'true';
```

规则：

- 本篇和真解共享 `lineageId`。
- 真解是独立内容定义，不是随机品质或功法等级。
- 真解强化同一核心机制，不应额外拼接多个无关效果。
- 真解替换本篇后仍只占一个道印位。
- 不设计功法经验、熟练度和 1～100 级成长。
- 若以后需要第三层级，必须重新评估内容膨胀和获取经济，首版不预留枚举值。

## 10. 内容契约

```ts
interface CharacterManualDefV1 {
  id: string;
  lineageId: string;
  rank: ManualRankV1;

  name: string;
  description: string;

  passiveId: string;
  conflictGroups: string[];
  capabilityKeys: string[];
  replaces?: string[];
}
```

功法定义只引用 v6 内容注册表中的被动 ID。角色持久状态不保存 Hook、`SkillDef` 或面板计算结果。

```ts
interface ManualProjectionV1 {
  passiveIds: string[];
  panel: CombatV6PanelContribution[];
  unitTags: string[];
  diagnostics: CombatV6ProjectionDiagnostic[];
}
```

### 10.1 功法允许输出

- v6 被动 `SkillDef` ID。
- 少量经过白名单校验的面板贡献。
- innate 能力。
- 通用单位标签。

### 10.2 功法禁止输出

- 主动技能和器诀。
- 人物等级、宗门技能等级。
- 四项修炼等级。
- 角色持久六维修改。
- 宗门技能 patch。
- 经脉节点选择。
- 任意代码、表达式脚本或未注册效果。

## 11. 通用触发条件

功法只能依赖通用战斗语义：

- 使用物理攻击后。
- 使用法术后。
- 造成伤害后。
- 受到伤害时。
- 受到致命伤害时。
- 回合开始或结束。
- 造成或受到治疗时。
- 自身气血、法力比例。
- 物理、法术、治疗、封禁等通用技能标签。
- 目标种类或通用单位标签。
- 每回合首次、每场首次或明确触发上限。

功法不得依赖：

```text
具体宗门 ID
具体宗门技能 ID
具体经脉节点 ID
具体道装实例 ID
具体器蕴或器诀 ID
```

确有技能联动需求时，只能匹配稳定的通用技能标签，保证功法跨宗门成立。

---

## 12. 冲突与跨系统能力键

冲突必须在创建战斗单位前完成解析，不能把两项冲突能力同时交给 core 再依赖运行时顺序决定。

### 12.1 同源覆盖

```text
追击真解 > 追击诀
```

最终投影只输出真解对应被动。

### 12.2 机制互斥

通过 `conflictGroups` 声明不能同时生效的机制，例如多个致命复起、多个同类追击或会形成无限循环的组合。

### 12.3 跨系统能力键

功法、器蕴和经脉可能提供相似能力，必须使用全局能力键：

```ts
interface CombatV6CapabilityContribution {
  capabilityKey: string;
  sourceType: 'manual' | 'equipment' | 'sect' | 'meridian';
  sourceId: string;
  stackPolicy: 'unique' | 'highest' | 'stack';
  priority: number;
  passiveId: string;
}
```

例如：

```text
功法·回生
+ 道装器蕴·不屈
+ 经脉·护命
→ survival.revive-on-fatal
→ 按 stackPolicy 只保留合法结果
```

当前 core 的 `SkillDef.conflicts` 可以保留为最终安全校验，但本篇/真解优先级、功法学习冲突和跨系统合并以投影编译器为权威。

## 13. 触发链约束

首版统一遵守：

1. Hook 产生的追击默认不能再次触发追击。
2. 反击不能触发对方再次反击。
3. 反震不能触发吸血、追击或另一次反震。
4. 一次致命事件最多结算一个复起能力。
5. 功法可以声明每回合或每场触发上限。
6. 多个伤害、治疗修改器必须具有稳定优先级。
7. 所有概率使用 Battle RNG，禁止 `Math.random`。
8. 相同种子、构筑、内容版本和指令序列必须产生相同事件流。

v6 当前已有 `suppressHooks` 防止部分二次打击互相触发；新增功法时仍需为每个触发族编写黄金测试，不能只依赖该全局开关推断安全。

## 14. 首批内容建议

首版建议先交付 10～12 个谱系，每个谱系拥有本篇与真解。

### 14.1 攻伐类

| 功法 | 作用方向 |
| --- | --- |
| 追击诀 | 物理命中后概率追加攻击 |
| 法连诀 | 法术行动后概率追加法术打击 |
| 断岳诀 | 物理会心倾向 |
| 凝光诀 | 法术会心倾向 |
| 饮血诀 | 物理伤害后恢复气血 |

### 14.2 防御类

| 功法 | 作用方向 |
| --- | --- |
| 回生诀 | 致命伤害时概率复起 |
| 反击诀 | 受到物理伤害时概率反击 |
| 反震诀 | 受到物理伤害时概率反震 |
| 护元诀 | 满足低气血条件时减伤 |
| 定魂诀 | 封禁抵抗或首次封禁保护 |

### 14.3 续航与功能类

| 功法 | 作用方向 |
| --- | --- |
| 冥思诀 | 回合结束恢复法力 |
| 生息诀 | 回合结束恢复气血 |
| 感知诀 | 看破隐匿单位 |
| 破禁诀 | 提高封禁命中 |
| 轻身诀 | 条件式速度调整 |

首批不必一次实现全部建议。应优先选择现有 v6 Hook 和 Effect 原语可以稳定表达的 10～12 个谱系，再根据内容缺口扩展通用原语。

## 15. 数值原则

- 本篇提供完整机制，真解只提高同一机制的概率、系数或上限。
- 功法主要价值来自机制，不成为大量固定面板的来源。
- 功法不直接增加六维和四项修炼。
- 固定伤害、治疗或恢复量应通过人物等级或面板缩放。
- 每场一次的强能力可以明显强于每回合可触发能力。
- 追击、法连、回生等高价值机制必须有触发链和次数限制。
- 同一 `manualId` 没有随机数值，不存在同名不同强度的玉简。

具体概率和系数属于内容版本平衡表，不写进 combat-v6 core。

---

## 16. 无 AI 设计

首版功法系统所有战斗和内容事实均由人工配置、代码审查和测试确定。

AI 不参与：

- 功法 ID、名称和描述生成。
- 功法效果、Hook、条件、概率和系数生成。
- 功法玉简掉落池与掉落权重生成。
- 参悟、覆盖、散功和冲突决策。
- 功法强度评估与自动平衡。
- 玩家功法推荐和自动构筑。

允许的内容来源只有：

- 版本控制中的人工内容表。
- 确定性规则配置。
- 经过测试的 v6 被动、Hook、Effect 和条件原语。

任何未来引入 AI 的提案都必须单独修改本文；首版不预留 AI provider、prompt、生成状态或降级链路。

---

## 17. 获得与经济循环

- 未参悟的功法玉简可以作为独立物品持有和交易。
- 参悟后只在角色功法状态保存 `manualId`，玉简被消耗。
- 重复玉简可以分解为悟法残页。
- 悟法残页可用于定向兑换部分本篇；真解的兑换范围和成本单独配置。
- 掉落只随机决定获得哪个已注册玉简，不随机生成战斗效果。
- 所有同名玉简完全同质，市场不需要比较同名玉简数值。
- 参悟、改修、散功和物品消耗必须在同一事务边界完成。

具体掉落、兑换、交易和回收实现属于后续数据与经济阶段，本设计只锁定功法领域事实。

## 18. 战斗投影

```text
读取唯一 ManualBuildV1
→ 按境界校验已解锁槽位
→ 解析 manualId 内容定义
→ 处理本篇/真解和 conflictGroups
→ 生成 capability contributions
→ 与道装、宗门、经脉贡献统一合并
→ 输出最终 passiveIds、面板和标签
→ 写入投影诊断
```

投影器不修改角色功法状态，也不创建 `BattleSession`。

阻止开战的错误包括：

- 使用未解锁槽位。
- 重复功法 ID。
- 同一谱系同时存在多个版本。
- 引用了不存在的功法或被动 ID。
- 存在未解决的互斥冲突。
- 功法输出主动技能、四修炼或非法面板属性。
- 内容版本和投影版本缺失。

## 19. 第一版实施范围

### 19.1 必须交付

- `getManualSlotCount(realm)` 及完整境界表测试。
- `ManualBuildV1` 和 `CultivatorManualStateV1`。
- 唯一构筑的读取与保存。
- 功法定义和被动内容注册表。
- 玉简参悟、明确覆盖和散功。
- 本篇/真解同源升级。
- 冲突组与跨系统能力键。
- 功法到 v6 passives/innate/panel 的投影器。
- 10～12 个可完整测试的功法谱系。
- revision 并发保护。
- 无 AI 的确定性内容与操作链路。

### 19.2 首版明确不做

- 多构筑保存和切换。
- 固印、锁槽和解锁材料。
- 随机覆盖目标。
- 参悟失败。
- 功法等级、经验和熟练度。
- 多于本篇/真解的层级。
- 主动功法技能。
- 宗门专属功法。
- 随机数值或随机效果玉简。
- AI 命名、描述、效果、掉落和构筑推荐。

### 19.3 后期可演进

- `CultivatorManualStateV1` 迁移为多构筑 V2。
- 保存、命名、复制和切换功法方案。
- 战斗外切换冷却或成本。
- 更丰富的通用 Hook 与功法谱系。

后期功能不得改变“战斗创建后使用不可变功法快照”的原则。

## 20. 测试与质量门禁

纯领域测试位于 `src/shared`，至少覆盖：

- 炼气至渡劫的槽位数分别为 2、3、4、5、6、6、6、6、6。
- 小境界变化不改变槽位。
- 未解锁槽位不能参悟。
- 有空位时参悟成功且只消耗一份玉简。
- 槽满时必须明确指定替换对象。
- `expectedRevision` 或 `expectedManualId` 不一致时不消耗玉简。
- 同名功法不能重复学习。
- 真解原位替换本篇且不增加槽位占用。
- 已有真解时拒绝本篇。
- 散功后槽位释放且不返还原玉简。
- 所有冲突在创建 `Unit` 前被解决。
- Hook 二次伤害不会形成无限触发。
- 相同输入、种子和版本产生相同战斗事件。
- 首版状态和内容契约不存在固印与 AI 字段。

架构测试还必须保证功法领域不导入其他功法实现、AI provider、prompt、creation-v2 或 battle-v5。

## 21. 尚待经济与后续内容确认

- 功法玉简的掉落来源和权重。
- 本篇、真解分解得到的悟法残页数量。
- 悟法残页定向兑换范围和成本。
- 散功是否返还残页及返还数量。
- 第七、第八、第九类后续功法的内容扩展节奏。
- 未来多构筑切换是否有冷却或成本。

这些内容通过版本化配置管理，不得写入 combat-v6 core。
