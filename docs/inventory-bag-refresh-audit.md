# 公共物品栏刷新排查（2026-09-14）

## 根因与刷新约定

公共随身物品栏通过 `useInventoryBag` 共享 `inventory.bag` 快照。成功响应由 `consumeResourceMutation` / `useResourceMutation` 消费；`ResourceStore` 仅处理相同角色、相同资源主题的事件。收到失效事件后，有订阅者的快照自动重读，无订阅者的缓存标记过期，重新进入时读取。

鉴宝回收的 `confirmBagRecycle` 已在事务中扣除库存、增加灵石，但只提交 `player.currency` 事件。页面的 `setRefresh` 仅重新驱动报价，不会刷新背包。已有 `withBagInvalidations` 会将旧库存主题和角色装备相关变更传播给背包，但不会从货币或进度变更猜测库存变化。

修复采用现有协议：在拥有库存变更的业务事务中显式提交 `inventory.bag` 失效事件；保留幂等、角色作用域、版本与事务后发布机制。没有增加页面轮询或全局请求拦截。

## 排查结果与修复

| 入口 | 原有缺口 | 本次处理 |
| --- | --- | --- |
| 鉴宝回收 | 扣库存后只发灵石事件 | 成交事务增加背包失效事件 |
| 坊市购买 | 新物品入库后只发灵石事件 | 购买事务增加背包事件 |
| 万界商行／声望商店 | 入库后只发声望事件 | 增加背包事件 |
| 宗门宝库兑换 | 入库后只更新商店、贡献 | 增加背包事件 |
| 拍卖上架，包括定向上架 | 移除物品、消耗所需符箓后返回空资源事件 | 增加背包事件 |
| 好友传音 | 消耗传音符、可选附件后返回空事件 | 增加发送者背包事件 |
| 邮件单封／一键领取 | 新版附件直接入库，不进入旧 `settlement.inventoryChanges` | 领取成功增加背包事件 |
| 即兴炼丹／照方炼丹 | 新材料消耗和丹药产出未填充旧库存变更数组 | 炼丹提交统一增加背包事件 |
| 灵田 | 初始灵种、播种、收获事件为空；物品培育只通知其他资源 | 补齐三类操作及消耗物品的培育事件 |
| 宗门任务交物与材料奖励 | 交付仅返回展示用 settlement；材料奖励 effects 为空 | 交付按批补一个背包事件，材料奖励显式指定获奖角色 |
| 秘境材料交付与物品奖励 | 新库存写入不进入旧 settlement 数组 | 有持久化回调的秘境命令统一使背包失效 |
| 野外战斗掉落 | 只写角色 condition 事件，提交后未广播 | 有物品奖励时增加背包事件，并在事务提交后发布 |
| 通天塔里程碑奖励 | 只写货币事件，提交后未广播 | 增加背包事件，并在事务提交后发布 |
| 锻造、宝库取出及功法玉简操作 | HTTP 响应已有可传播的事件，但服务未广播，其他已打开页面可能滞后 | 保留现有事件，补齐事务后的广播 |

额外核对：背包整理、移动、使用物品、兽诀学习、灵露洗炼已有背包事件；装备穿脱与功法操作已有 `player.profile` 事件，由公共传播逻辑使背包失效。拍卖购入／下架通过邮件交付，实际入袋由邮件领取负责，不应提前假定物品已经入袋。

秘境采用保守失效：有持久化回调时即刷新背包，因此只改变其他资源的秘境操作也可能多一次背包读取。纯查询不会触发；本次未扩展旧结算协议或重构库存持久化。

## 本轮验证

- 本地环境：`127.0.0.1:5174` 页面、`127.0.0.1:3001` API，专用本地 PostgreSQL／Redis／NATS；复用浏览器内的 `local8@daoyou.local` 测试会话。
- 通过本地 dev 发放入口准备独立命名的三份凡品矿石「回收刷新验收玄铁0914」。在鉴宝页面连续出售，数量自动 `3 → 2 → 1 → 消失`，占格从 `1/40 → 0/40`，灵石 `0 → 13 → 26 → 39`；未点击刷新。
- 首次成交的网络记录显示成交 POST 200，随后一次 `/api/combat-v6/inventory?location=bag` GET 200；浏览器控制台无 error。
- 同一页面通过导航进入储物袋后立即显示剩余两份。另开储物袋标签页，再在鉴宝页面出售，另一个标签页自动从两份更新为一份、最后移除，验证实时广播。
- 三份准备物品已全部通过正式回收流程消耗；保留实际成交所得 39 灵石。
- `bun run lint`、`bun run build`（包含前后端 TypeScript）通过；`bunx vitest run src/shared/lib/bagResourceChanges.test.ts` 的两项已有纯函数测试通过；`git diff --check` 通过。
- `bun run db:migrate` 的认证迁移成功，但业务段的 `bun ... x` 未传入 DATABASE_URL；改用 `bun --env-file=env/local.env run bunx drizzle-kit migrate` 后业务迁移成功。本次没有修改迁移、环境配置或启动脚本。
- 本地 API 已有 watch 进程占用 3001，本次组合启动的重复 API 实例未启动，复用了已有本地 API。

未实走灵田 LLM、炼丹、商店、宗门任务、秘境与战斗奖励的完整流程；这些入口完成了库存写入、事件生成、消费／广播路径的代码核对及静态检查，不能视为已完成浏览器验收。未新增前后端／数据库单元测试，未运行全量纯引擎测试，因为本次没有修改共享引擎规则。
