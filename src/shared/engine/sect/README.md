# 宗门系统架构

宗门系统采用“注册表 + 运行时门面 + 构建器 + 插件流水线 + 策略”的组合架构。通用核心只认识稳定字符串 ID 和插件契约，任何具体宗门、流派、节点都只能存在于 `content`。

## 目录职责

- `core/domain`：序列化定义、持久化状态、编译结果和上下文值对象。
- `core/plugin`：`BaseSectModule`、`BaseSectPathModule`、节点插件和准入、试炼策略契约。
- `core/authoring`：宗门神通、战斗效果、法力消耗和战术候选构造器。
- `core/compilation`：`SectBuildBuilder` 和统一编译导演 `SectCompiler`。
- `core/progression`：可注入成长策略、心法等级上限、成本和有序层解锁规则。
- `core/validation`：定义、组合、编译契约和持久化状态校验流水线。
- `core/runtime`：`SectRegistry` 与客户端、服务端共用的 `SectRuntimeFacade`。
- `core/presentation`：神通效果说明、心法属性投影、四槽装配和完整宗门展示主题等纯逻辑。
- `content/productionRuntime.ts`：领域模块与可选前端主题的唯一生产组合根。
- `content/lingxiao`：保留 `lingxiao` 稳定 ID 的红尘剑宗传承，以及快剑、重剑两个流派插件。
- `testing/fixtures`：不会进入生产目录的扩展性宗门。

根目录只保留本说明、公共 `index.ts` 和上述分层目录。通用能力从 `@shared/engine/sect` 导入；生产运行时从 `@shared/engine/sect/content` 导入。

## 编译流程

```text
CultivatorSectState
  -> SectRuntimeFacade
  -> SectRegistry.require(sectId)
  -> BaseSectModule.createBaseBuilder
  -> BaseSectPathModule.compile
  -> SectNodePlugin.apply（按层级和声明顺序）
  -> SectBuildBuilder.build
  -> AbilityFactory 契约校验
  -> SectCompiledBuild
       -> battle-v5 战斗投影
       -> ResolvedSectAbility 展示投影
```

战斗和页面详情必须读取同一个 `SectCompiledBuild`。Service、Repository、API、UI 和 battle adapter 不得重新解释宗门资源、倍率或节点效果。

## 对象与模式

- `SectRegistry` 使用注册表模式完成模块发现和 ID 分派。
- `SectRuntimeFacade` 使用门面模式统一校验、编译、战斗投影和详情解析。
- `StandardSectModule` 是普通宗门聚合根，自动注入成长、组织、准入和试炼策略；`BaseSectModule` 只留给确需替换核心规则的特殊宗门。
- `BaseSectPathModule` 使用模板方法固定初始化、逐层应用节点和统一 finalize 生命周期，并由流派模块自动生成序列化流派定义。
- `SectBuildBuilder` 使用构建器模式提供受控修改面，节点不能直接共享可变 `AbilityConfig`。
- `SectNodePlugin` 是定义与行为一体的装饰器；编译器将已选节点组成稳定流水线。
- 战术、准入和试炼通过策略对象注入，通用层不根据内容 ID 选择实现。
- 校验器使用组合规则流水线，分别检查定义、对象组合、运行时产物和持久化状态。

设计模式只用于封装变化方向。纯定义和值对象继续使用 TypeScript 数据结构，不为形式上的“面向对象”制造空类。

## 新增宗门

1. 在 `content/<sect>` 定义六本心法、基础神通和稳定内容 ID。
2. 继承 `StandardSectModule`，实现基础能力编译并注入流派模块；普通宗门不自行实现组织、成长、准入或试炼流程。
3. 每个流派继承 `BaseSectPathModule`，声明有序层、基础变体、战术策略和节点插件。
4. 节点使用 `ConfiguredSectNodePlugin` 或专用子类，将定义与 `apply` 行为放在一起。
5. 可选定义纯数据 `SectPresentationTheme`，然后在 `content/productionRuntime.ts` 的 `PRODUCTION_SECTS` 注册一个条目。除这个组合根外，不修改服务端、前端页面或导航。

完整目录模板、能力联合类型和注册步骤见 [`docs/sect-authoring-guide.md`](../../../../docs/sect-authoring-guide.md)。

## 新增流派或节点

- 新流派只新增所属目录并加入宗门构造参数，不修改 Compiler、Registry、Service、Repository、API 或 UI。
- 新节点只新增一个节点插件并加入流派节点列表，不在流派基础编译器增加节点 ID 判断。
- 多个节点修改同一组神通时，建立流派私有 Build Facade，用语义特征组合变化；禁止恢复 `nodes.has(id)` 中央分派。
- 节点每次应用必须造成可观察的最终运行时变化，空实现会在注册时失败。

## 标准心法成长

标准宗门心法覆盖 0～180 级。每本心法必须声明 `growthProfile`，面板属性与所属神通共用同一条连续曲线：

```text
t = clamp(floor(level), 0, 180) / 180
早成型 = 0.8t + 0.2t²
均衡型 = 0.5t + 0.5t²
后劲型 = 0.2t + 0.8t²
实际收益 = 满级上限 × 曲线值
效果倍率 = 1 + 分类满级增幅 × 曲线值
```

伤害、治疗、护盾和状态分别配置上限；状态包含 Buff 属性、伤害修正和动态标量。结构规则不自动成长，持续时间与计数仅响应显式声明的里程碑。无来源神通保持中性，显式跨心法 Buff 仍按指定心法结算。运行时统一保留四位小数。

目标等级 `L` 的单级研习成本独立于境界突破经验表：

```text
修为 = ceil((50 × 1.05^(L - 1)) / 10) × 10
灵石 = ceil((修为 × 3) / 100) × 100
道心感悟 = 0
```

跨级研习逐级取整后累加。境界每个小阶段开放 5 级；有效上限取境界、弟子身份与藏经设施三者的最小值。

| 弟子身份 | 心法上限 |
| -------- | -------: |
| 记名弟子 |       45 |
| 外门弟子 |       90 |
| 内门弟子 |      135 |
| 真传弟子 |      180 |

| 藏经设施等级 | 心法上限 |
| -----------: | -------: |
|            1 |       40 |
|            2 |       75 |
|            3 |      110 |
|            4 |      145 |
|            5 |      180 |

外门、内门、真传的最低晋升境界依次为炼气、筑基、元婴；贡献、任务与试炼仍由标准组织策略判定。

## 标准流派参悟

标准流派共六层，参悟成本独立于境界突破经验表。第 `N` 层成本为：

```text
修为 = 5,000 × 4^(N - 1)
灵石 = 修为 × 5
道心感悟 = 100
```

| 层级   | 境界要求 |      修为 |       灵石 | 道心感悟 |
| ------ | -------- | --------: | ---------: | -------: |
| 第一层 | 筑基中期 |     5,000 |     25,000 |      100 |
| 第二层 | 金丹圆满 |    20,000 |    100,000 |      100 |
| 第三层 | 化神中期 |    80,000 |    400,000 |      100 |
| 第四层 | 炼虚圆满 |   320,000 |  1,600,000 |      100 |
| 第五层 | 大乘中期 | 1,280,000 |  6,400,000 |      100 |
| 终式   | 渡劫圆满 | 5,120,000 | 25,600,000 |      100 |

每个流派底层保留三套参悟方案，当前只开放方案一。节点首次保存后锁定；未选择节点的已解锁层级仍可继续补选，替换、移除和重置暂不开放。两个已习得流派可以随时免费切换。

## 欺天改宗

《欺天符》以欺瞒天道名录为核心：一次性改写当前宗门归属，而不是永久解锁多宗自由切换。六本心法等级不变；两条流派可以按顺序对应，也可以交换对应，并保留各自已经解锁的层数；目标宗门节点、战术与四槽神通需要重新选择。弟子身份、当前贡献和历史总贡献保留，宗门职务不保留。原成员档案标记为 `transferred`，仅用于审计，不能再次激活。

转宗前必须领取已完成任务奖励，进行中的任务会自动放弃；历史任务与俸禄领取记录会改挂到新的宗门记录下，避免同一周期重复领取。服务端在同一玩家事务内完成旧档封存、目标进度写入和欺天符消耗，任何一步失败都会整体回滚。

《欺天符》由管理员在后台道具库手动创建，并通过现有游戏邮件/奖励发放流程发给目标玩家。道具库中的符箓场景必须填写为 `sect_transfer`，使用模式为 `consume_on_action`；服务端只依据该场景识别和消耗符箓，不负责自动创建或自动发放。

## 标准宗门任务

手动任务只在领取事务中生成。领取前的任务视图只包含任务类型、名称和通用描述，不生成或返回执行变体、交付要求、难度和奖励；领取时根据当前周期、身份与境界生成完整 offer，并将执行方式、要求、难度和奖励作为 v2 快照原子写入任务记录。领取后不能刷新或更换快照。

手动任务领取满 15 分钟后可以回到发放事务的 NPC 处放弃。放弃只允许作用于尚未完成的 active 任务，会删除当前任务记录、进度、执行会话和目标快照；随后可以在同一周期重新领取，并生成新的任务快照。已完成待领奖或已结清的任务不能放弃。

任务修为继续使用境界每日预算。日常周期倍率为 1，周常周期倍率为 3；easy、normal、hard、elite 分别取得每日预算的 5%、8%、12%、18%。灵石与贡献公式为：

```text
境界灵石保底 = roundTo100(
  (境界序号 + 1) × 1,000 × 周期倍率 × 贡献难度倍率
)
倍率灵石 = ceil((修为 × 5) / 100) × 100
最终灵石 = max(境界灵石保底, 倍率灵石)
贡献 = round(贡献基数 × 贡献难度倍率)
```

贡献难度倍率依次为 1、1.15、1.35、1.6。清扫山门、巡视矿场、宗门小比和悬赏令的最低难度依次为 easy、normal、hard、hard；交付要求生成的难度只能继续提高最低难度。

交付任务每次都生成核心限制：丹药必有最低品质、目标丹类、功效和品相；法宝必有最低品质、部位和未装备要求；材料必有数量、最低品质和类型。复合丹药只要实际 operation 投影出的功效满足目标丹类对应功效，即使持久化的主丹类不同也可提交；不能仅凭主丹类推断功效。完美词条与元素仍是可选的额外条件。丹药品相要求按下品 30%、中品 45%、上品 20%、完美 5% 生成，完美必须精确匹配，其余均表示最低品相。

常规宗门任务不奖励道心感悟，不按交付物市场估值追加补偿；长老试炼只提供晋升资格。

### 战斗任务

战斗任务在领取或自动首次创建时生成版本化 `battleTarget`，执行时只读取任务内的目标快照。所有战局均为 battle-v5 临时战局，不写战绩、不影响排名；失败后任务保持 active，并使用同一快照重试。

- `mine_patrol`：领取时按玩家境界和阶段生成固定的“裂岩獠兽”。六项主属性按境界预算均分后乘 `0.75`，固定装备三门玄品技能“碎岩扑击”“撼地怒吼”“妖血沸腾”，在本宗灵脉开战。
- `weekly_tournament`：领取时随机锁定同宗、与玩家同大境界或低一大境界且双方角色与成员关系均有效的玩家完整战斗构筑；无候选时不创建任务。开战入口位于演武场设施“宗门擂台”。
- `weekly_bounty_battle`：独立周常“悬赏令·讨伐”，领取时随机锁定异宗、与玩家同大境界或低一大境界且成员关系有效的玩家完整战斗构筑；无候选时不创建任务。玩家经访宗舆图进入目标宗门专用山门，与目标 NPC 开战。
- `weekly_bounty_material`：独立周常“悬赏令·征集”，继续使用材料要求生成与提交链路，可与讨伐悬赏在同周同时完成。两种悬赏各自按 60 贡献档结算，任一完成都满足 `promotion.bounty`。
- `elder_trial`：在事务堂传功长老处直接开启。四宗长老均为元婴圆满标准属性、六卷 135 级心法、完整流派层与固定四神通，并装备三件元婴圆满锚定的地品法宝。

玩家目标快照保存来源角色、来源宗门、锁定时间和完整 `CultivatorCombatInput`；任务视图只返回名称、描述、宗门、境界与阶段摘要，不暴露技能和装备数据。小比和讨伐悬赏候选均匹配同大境界或低一大境界，阶段可以不同。玩家后续换装、突破、转宗、死亡或注销不会改变已领取任务中的目标。

## 边界约束

- 每个宗门固定六本心法，每本至少拥有一个基础神通。
- 流派层数与每层节点数由内容声明；层 ID、顺序和节点归属必须稳定且可校验。
- 玩家只保存已按顺序解锁的层 ID；流派编译器不得从等级推导倍率或层级。
- 四个主动槽固定、不可重复，只能装配已解锁主动神通。
- 每个流派独立保存层级、战术和三套参悟方案，只能激活一个流派；当前开放方案由标准规则统一声明。
- 未注册 ID、未知配置版本和非法持久化状态必须明确失败。
- battle-v5 运行时标签只能通过 `GameplayTags` 生成。
- 普通宗门不得复制组织模块，不得绕过 `SectAbilityFactory`/battle-v5 `AbilityFactory`，不得在流派编译器中按节点 ID 集中分派。
- 普通宗门不得修改宗门路由页面；展示差异只能通过生产目录中的纯数据主题注入。
- `core` 禁止依赖 `content`，生产内容禁止回流到通用入口。
- 宗门复杂机制优先在内容编译期展开为固定 effect plan，或使用隐藏 marker、通用 counter 与既有条件组合；单一宗门且存在近似方案时不得扩展 battle-v5 主管道。
- battle-v5 新原语必须至少有第二个独立生产消费者，或用于修复明确的全局战斗不变量，并提供不引用宗门 ID 的原子测试。
- 宗门代码的架构注释、业务原因和扩展约束统一使用中文。
