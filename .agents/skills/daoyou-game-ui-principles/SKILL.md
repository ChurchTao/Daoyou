# 游戏 UI 设计原则

所有玩法都以玩家当前任务组织界面。信息完整不等于全部常驻；先做取舍，再安排层次和披露时机。玩家应能一眼辨认当前状态、可做的下一步和主要操作，不必先读一整套规则。

本原则适用于常规场景、独立战斗、地图、创角、详情与确认弹层。它决定信息何时、以何种优先级出现；布局、共享控件和具体展示字段继续遵守各自规范：常规壳用 [daoyou-game-ui](../daoyou-game-ui/SKILL.md)，物品预览用 [daoyou-item-preview](../daoyou-item-preview/SKILL.md)，其他布局见 [布局归属](../../../docs/game-layout-ownership.md)。

## 先明确当前决策

设计或改动前，先确定玩家所处阶段、当前目标、下一步操作，以及作出这次决定必须知道的事实。不要从接口字段或玩法规则清单直接生成页面。

- 每个任务区域有清楚的视觉重心；主操作服务当前目标，查看资料、历史和次级管理降低权重。并行任务和对比选择可以同时呈现，不机械限制整页只能有一个按钮。
- 先决定哪些信息应删除、合并或移到更合适的入口，再决定哪些需要折叠。把所有字段搬进一个默认收起的“完整规则”仍然缺少层次。
- 同一事实不在标题、状态、进度、说明段落和按钮旁反复表达。全局 HUD、导航已承担的信息，不在正文再复制一份。

## 按决策需要分级

| 信息 | 默认呈现与披露时机 |
| --- | --- |
| 当前任务 | 对象、当前状态、进度、主要操作与阻碍行动的原因优先可见，放在相关操作附近 |
| 当前决策依据 | 当前选择的实际收益、差异、必要条件和代价在选择时可见；提交前明确成功率、失败损失及不可逆后果 |
| 进一步理解 | 机制解释、计算方式、物种设定、历史和次级管理放入语义明确的详情、说明或管理入口，默认不抢主任务 |
| 未来机制 | 按实际阶段逐步披露，常规任务页只提示最近可达目标及简短条件；长期规划所需信息可在图鉴或规则入口主动查询 |

“次要”取决于当前任务，而非字段名称。路线比较、战斗目标选择等决策需要的数据应同时可见。玩家已主动打开的物品预览、规则页或图鉴可以更完整，但仍按用途分组，不能把关键效果、限制或当前比较依据再次藏到深层。

## 用 UI 表达状态与操作

- 进度与等待用进度条、阶段标记、剩余时间表达；数量与差异用对齐的数值或并列对比表达；当前可执行的动作由明确的操作控件承担。文案补充 UI 无法表达的条件或后果，不逐句复述控件。
- 进度、机会、收益和禁用态必须对应真实业务状态。未解锁、暂停、恢复中、失败和完成应有不同表现；不可达或机会已用尽的步骤不再作为当前目标高亮。
- 颜色、字号、留白和位置共同区分身份、任务、辅助信息。不要让每块内容都拥有同样醒目的标题、边框、底色和按钮；不要用增加卡片、标签或说明段落弥补没有取舍。
- 降低密度靠删减重复、重组与按需披露，不靠缩小字体或触控区域。图标、颜色和图形保留必要文字、状态语义与可访问名称，不能要求玩家仅凭颜色或陌生图标猜测。

## 在合适的时机披露

- 选定对象后展示它的条件与产出，进入当前培养或操作阶段后再展示对应机制；未选定的备选项保留必要差异，不同时铺开每项的全部预测与解释。
- 事件先呈现这一次发生了什么、当前有什么影响、是否需要处理；通用概率与完整事件规则在相关记录中按需查看，不在无关阶段常驻。
- 费用、失败扣费、概率和不可逆限制不能只放在悬停、折叠说明或提交后的反馈中。让玩家在确认前看见它们，并与确认操作保持可辨认的关联；触屏也必须可访问。
- 不为承载说明而给每次操作额外添加确认弹窗。能在原工作区完成选择、核对与提交时优先原地完成；是否需要单独确认由操作的实际风险和既有流程决定。
- 仅在操作前提未满足时解释当前阻碍，并说明可行的下一步。不要把所有未来限制堆在禁用按钮下，也不要只留一个无法理解原因的灰色按钮。
- 资料、规则和管理入口按玩家目的命名，如“植株资料”“已有收成与生产进度”，不使用含混的“更多”承载多种无关内容。展开后仍需分组，避免长段规则与多层嵌套折叠。
- 展开、选物、返回和关闭不能丢失当前对象、选择或上下文。关键操作及风险在窄屏中应易于找到，需要时使用抽屉底部操作区，避免被辅助说明、键盘或安全区遮挡；不强制所有页面采用同一种布局。

## 验收

对照本次变更涉及的真实状态检查，不以“字段都在”或“已经折叠”为通过标准：

- 首屏先看见的是当前任务，玩家无需阅读长段规则就知道下一步；可操作状态有明确入口，等待或禁用状态有可理解的原因。
- 当前阶段没有被未来机制、重复身份和说明挤占；主动展开的资料仍有清楚分组，所需规则能够找到。
- 对比所需的信息同时可见，确认前能看见实际收益、全部代价、概率及风险；精简后没有隐瞒重要条件或误述状态。
- 按变更范围覆盖初始、等待、可操作、暂停／恢复、失败和完成等状态，检查视觉重心及行动是否随状态改变。
- 在桌面和 360px 窄屏检查实际操作、滚动与展开后的布局，检查触屏、键盘焦点、返回与关闭；依照 [测试规范](../../../docs/testing.md) 验证，静态检查与运行验收分开记录。

审查或交付时简要说明首屏保留了什么、其他信息在何处和何时披露、哪些关键决策信息始终可见，以及已验证的状态和缺口。小改动不必为此另建文档。
